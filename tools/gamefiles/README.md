# atlas-gamefiles: the Map Maker's file reader

**Licence: GPL-3.0-or-later** ([LICENSE](LICENSE)). This folder, and the Atlas Map Maker installer that carries the program built from it, are under the GNU General Public License version 3, because they use [Soulstruct](https://github.com/Grimrukh/soulstruct) and [soulstruct-havok](https://github.com/Grimrukh/soulstruct-havok) (both GPL-3.0-or-later). The rest of this repository stays under the MIT licence. Nothing from this folder goes into the Atlas viewer or the Importer.

`atlas-gamefiles` reads a player's own game files: it reports what map data can be read from them (`check`), and makes an Atlas map pack from them (`make`, Dark Souls Remastered and Bloodborne 1.09). Players never run it by hand: the [Atlas Map Maker](../../apps/mapmaker/README.md) app runs it and shows the result.

## Check (Phase 0)

`atlas-gamefiles check <game folder> --out <output folder>`:

1. **Detects the game and version** from data files, not from one executable fingerprint:
   - Dark Souls Remastered: `DarkSoulsRemastered.exe` (its file version), `map/MapStudio/*.msb`, the Steam build id when `appmanifest_570940.acf` is two folders up;
   - Bloodborne: a dump folder with `eboot.bin`, `sce_sys/param.sfo` (title id and app version) and `dvdroot_ps4/map/MapStudio/*.msb.dcx`, and whether The Old Hunters maps (m34, m35, m36) are there;
   - Prepare to Die Edition is recognised and refused; anything else is "unknown" with the reason. A parent folder works too: it looks two levels down.
2. **Lists the areas** (one MSB map layout each) with parts by type, treasure events, the item lots they give (and how many of those are in the game's `ItemLotParam`), and bonfire or lamp candidates (Dark Souls: entity ids in the bonfire ranges and collisions' `attached_bonfire`; Bloodborne: collisions' `attached_lantern`; both unconfirmed). Also the range of part positions.
3. **Tries each geometry source** per area and records what worked, with counts and the first errors:
   - collision (`hAA_BB_CC_DD.hkxbhd` + `.hkxbdt`): Dark Souls Remastered's Havok 2015 meshes are read with soulstruct-havok's `MapCollisionModel`; Bloodborne's Havok 2014 compressed meshes (`hknpCompressedMeshShape`) are decoded by our own `havok2014.py`, which soulstruct-havok does not do, including the `.hkxbhd.patch` / `.hkxbdt.patch` pairs that replace entries of the same name;
   - navmesh: Dark Souls Remastered `.nvm` files in `mAA_BB_CC_DD.nvmbnd.dcx`; Bloodborne `hkaiNavMesh` entries in `.nvmhktbnd.dcx`, also decoded by `havok2014.py`, placed by the map's `.nva` table;
   - map piece models (`.flver`, `.mapbnd`): a sample of 12 per area (`--map-piece-sample`, 0 for all).

   Phase 0 is a check, not the full map, so collision is read from an evenly spaced sample of 12 files per area (`--collision-sample`, 0 for all), and every source stops starting new files after 45 seconds (`--source-budget`); either way it is marked `sampled`. The report records each source's time to open its binder (`openSeconds`), the reading time per file (`fileSeconds`: min, median, max) and the slowest file, so real parse speeds show up in a player's report.
   **Nothing can hang the check.** The geometry is read in a separate file reader process (`worker.py`, `reader.py`): one at a time, reused from source to source. It is this same program started again with a hidden command (`atlas-gamefiles reader`, or `python -m atlas_gamefiles reader`) as a plain child process with pipes of its own (jobs in on standard input, progress and results out on standard output, one JSON line each; the preview triangles in a temporary `.npy` file in the output folder, deleted once read), its standard error in `reader-log.txt` in the output folder, and on Windows no console window: the way the app starts the helper itself. (0.1.1 used multiprocessing's `spawn`; on a player's PC that child never started. See "Standard input" below.) The reader applies the same promises as the helper (no network, Soulstruct imported with `prepare_soulstruct`) before it reads anything, and ends when its standard input ends, so it never outlives the helper. It reports each start-up step (`booted`, `numpy`, `soulstruct core`, `soulstruct.havok`, `ready`); one not ready after 60 seconds is stopped, and every source then fails with the last step it reached (if only the Havok reader would not load, the reader starts again without it and only the sources that need it fail). It reports before it opens a binder, how long that took, and before each file; when it is silent for 5 seconds (`--heartbeat`), the helper writes a progress line that it is still on that file ("still reading h1000B0A10.hkx.dcx (collision file 3 of 12), 20 s"). A source still running after 90 seconds (`--source-time-limit`, 0 for none) is stopped: the reader is killed, the source is recorded as `timed-out` with the file it was on (`stoppedOn`) and the files done before it (`filesDone`), a warning is added, and the check goes on in a new reader. Shortly before either time limit, the reader writes every thread's stack to its log, so a report of a hang says where it hung. Cancel kills the reader at once. Only the result comes back, with at most 200,000 triangles per source for the preview.

4. **Draws one top-down preview PNG per area**: geometry shaded by height where it was read, dots for treasure, bonfire or lamp candidates, characters, objects and player starts. Right is +x and up is +z.
5. **Writes** `report.json`, `previews/<area>.png` and `atlas-check-report.zip` (both, the reader's log and a short README) into the output folder. The report's `diagnostics` section says how the helper ran: frozen or not, Python and helper versions, the Windows version, the temporary folder, how long importing Soulstruct took, and for the file reader how it was started, each start's steps with their times, the last step reached, and, when anything went wrong, the end of its log. Paths under the home folder start with `~`, in the report and in the zipped log.

Standard output carries one JSON object per line: `start`, `game`, `areas`, `progress` (with `fraction` and `message`), `area`, `warning`, then `done` (exit code 0), `cancelled` (3) or `error` (1, or 2 for a bad output folder). Everything else goes to standard error. With `--stdin-cancel`, writing `cancel` to standard input, or closing it, stops the check at once (the file reader process is killed).

**Standard input.** The helper (and the reader) keeps its standard input to itself: it reads it through a private copy, and the standard input that libraries and any program they start see is the null device (`events.claim_stdin`). On Windows it also never leaves a read waiting on the pipe: it asks how many bytes are there (`PeekNamedPipe`) and reads only those (`events.stdin_lines`). A read left waiting on a pipe there blocks every other use of that pipe, even a program asking what kind of file its standard input is as it starts. In 0.1.1, the helper waited on the app's pipe for `cancel` while its multiprocessing child, which Windows gives a copy of the helper's standard input, started. That is most likely why, on a player's PC, the child never got going and every geometry source failed with "it did not start within 180 s" (not confirmed on that PC; the CI step "Try the helper the way the app starts it" starts the helper the same way).

## Make map (0.2.0)

`atlas-gamefiles make <game folder> --out <report folder> [--maps-folder <folder>] [--areas m10_01,m15_01] [--config <file>] [--floor-overrides <file>] [--remake <area>] [--map-style <style>] [--no-3d] [--look-3d models|collision] [--scene-builder <atlas-scene program>]` makes the map pack and installs it in the maps folder the Atlas viewer reads (the app passes it; `make.py`, `world.py`, `floors.py`, `render.py`, `tiles.py`, `pack.py`). The same lines on standard output as `check`, plus `pack` (its folder, id and counts) before `done`. `--floor-overrides` names the player's own floor cuts (see [Floor cuts file](#floor-cuts-file)); `--remake` makes one area again (see [Making one area again](#making-one-area-again)). `--floor-method passages|cuts` chooses how floors are found for this make (see step 3); an area's own choice in the floor cuts file wins.

**Bloodborne** (`config/bloodborne.json`): Make map reads version 1.09 only (`detect.map_version_refusal`, from `sce_sys/param.sfo`) and refuses any other, or a dump whose version cannot be read, with an `error` line of code `game-version`; Check game files reads any version. The config's `mainAreas` (the sixteen main areas) are made, in that order; the Chalice Dungeons (`m29`), `m30` and `m99` are left out. Area names are Soulstruct's Bloodborne map names. Soulstruct reads the binders, DCX, map layouts, params (with its Bloodborne paramdefs), text tables and event scripts; the collision and navmesh triangles come from our own decoder (`havok2014.py`). The Bloodborne-specific rules are numbers and switches in the config, not code: how lamps are registered, lot chains, which treasure counts, no enemy drops.

1. **Layout and content.** Every area's MSB (the config's `skipAreas`, the `m99` debug maps, are left out); `ItemLotParam`, `EquipParamGoods` and `NpcParam` from the game params; item, NPC and place names and item descriptions from `item.msgbnd` (base and patch tables merged).
2. **Geometry, in full.** Each area's collision through the file reader process (every file, with progress, heartbeat, cancel, and a 5-minute limit per source); the navmesh where collision gives nothing (and, for automatic passages, beside it); markers only when neither does. A Bloodborne navmesh is placed by its `.nva` table and then by the map's offset (the MSB's `MapOffset` event): `navmesh.applyMapOffset` `auto` tries it as placed, with the offset and with the offset undone, and keeps the one with the most navmesh over collision floor (the report's `geometry.navmeshPlacement`). Each collision mesh is moved and turned by the MSB collision part that places it. The report's `placement` section checks that: the share of markers standing on a floor with the meshes as placed and as stored, and a verdict.
3. **Floors** (`floors.py`). Triangles flatter than `walkableSlope` are floor, steeper than `wallSlope` wall. The walkable surfaces are sampled on a 1 m grid; where one lies at least `clearance` (3 m) above another across `minStackedArea` (150 m²), a cut height is chosen that separates the most stacked ground while slicing the least, up to `maxFloors`. A connected piece of floor that a cut would slice is kept whole on one side when nothing stacked is lost. Walls are the wall triangles cut at `wallCutHeight` (1.3 m) above the floor beneath them. `floorOverrides` in the config can name floors, split or merge at given heights, or set the cuts by hand; the player's own floor cuts (`--floor-overrides`) replace an area's entry whole. The report's `floorPlan` has, per area, the cuts with who set each (`cutList`: `automatic`, `shipped` or `yours`), the override used (`overrides`), the area's floors without the player's cuts (`shipped`), cuts dropped because they left a floor empty (`cutsDropped`), and a height profile (`profile`: square metres of walkable floor per 0.5 m from `low`); each floor its cuts below and above (`between`), and `options.floorOverrides` the player's file and the areas that used it (`usedFor`). An unreadable file is a warning: the make goes on without it.

   **Automatic passages** (`passages.py`, `floors.method` `passages`; the default for Bloodborne, cuts for Dark Souls Remastered; either works for both games). For areas where one flat cut cannot separate ground that climbs past ground beneath it (bridges over streets, ramps that wind round a tower). Walkable ground is gridded on 1 m cells in fixed height bands (`band`, 3 m); a navmesh triangle counts only where collision floor lies within `navSupport` (1.2 m) under its centre and at least two corners, so stray navmesh adds nothing. Where one walkable surface lies more than `overlap` (2.4 m) above another across at least `minPassageArea` (6 m²), that is an overlapping place. Walkable triangles are joined into sheets by 3D connectivity (shared edges, or ground within 1.2 m), but a join is refused when it would put two storeys of the same overlapping place on one sheet. Each overlapping place's sheets are ordered upper and lower; where the two meet, the one that "shows" on the main floor is the upper by default, or the lower when the player chose it (`passages: [{x, z, show}]` in the floor cuts file). Sheets are given levels by what lies above what (longest path; a loop is broken and counted in the report), and each level becomes one floor, lowest first, the floor holding the largest sheet being the main floor. Each floor's `heights` (on its layer, when there are 3D maps) are its walkable triangles' lowest and highest points, kept in order so the viewer's 3D clipping and floor list work unchanged. The report's `floorPlan` has `method`, `passages` (each place: its centre, area, the levels and heights it joins, which shows and whether the player set it), `navmesh` (triangles read and kept) and `floorHeights`.

4. **Pictures** (`render.py`, `tiles.py`). One picture per floor at 8 pixels per metre (smaller for a large area, down to 2; one still over 6144 pixels is cropped to where most of its floor is): the floor shaded by height over the whole area's height range with light from the north-west, the floors below at 40 % behind it, walls as dark lines and a darker rim. Each picture is cut into the tile pyramid `@atlas/core` reads (`tiles/<area>/f<floor>/{z}/{x}/{y}.webp`, 256-pixel tiles, PNG when Pillow cannot write WebP). Each map stores its `worldTransform` (pixel to world x, z).
5. **Markers** (`world.py`). Bonfires from the event scripts' `RegisterBonfire` (with arguments filled in from the events that run them; Bloodborne's lamps from each run of the common event `bonfires.commonEvent`, 7000, whose arguments name the lamp object and its lit flag), named after the place they are in; every treasure item lot, one marker per item (category from the item type and the config's id ranges; consumables and souls in categories hidden by default; "In a chest." and "Appears later in the game." notes); bosses by model and area from the config; NPCs with a talk script; enemies whose drop lot has a flag and drops for certain (not for Bloodborne: `characters.drops` false). Bloodborne's treasure follows the lots numbered after its own (`items.followLotChain`), keeps only lots with a picked-up flag (`requireFlag`) and leaves out treasure an event shows later (`skipHidden`: scripted rewards); blood gems and runes are upgrade materials. Each has a stable id from the area and the MSB part, the event flag as `flagId` where there is one, and the floor whose height band holds it (`locate`: the surface from 1.5 m above it down to 6 m below).
6. **Pack** (`pack.py`). Manifest (schema version 2, `writtenBy` "Atlas Map Maker", attribution crediting Hunter's Atlas), maps with one layer per floor (the main floor first), regions per area and per place name, categories with Atlas icon names, item entities with descriptions, checklists (All bonfires, Bosses, Items by area, Rings, Key items) and guide notes. It is written to `<maps folder>/.<pack id>.making` (`.dark-souls-remastered.making`, `.bloodborne.making`) and swapped in only when complete; a folder there that the Map Maker did not write is never replaced. Nothing is written into the game folder, and cancelling leaves the maps folder as it was.
7. **3D maps** (`scene.py`, on unless `--no-3d`). Each area's collision (or navmesh) becomes a 3D model, in the same plain look as the flat map: each corner coloured on the same height ramp, darker on steep slopes and darkest on walls. The helper writes the triangles as a raw glTF file (one node per collision part, floors turned to face up) into the report folder and runs the Atlas scene builder on it: `atlas-scene`, built from [crates/atlas-scene](../../crates/atlas-scene) (MIT; see "Building a 3D map" in [docs/pack-file-format.md](../../docs/pack-file-format.md)), a separate program that the Map Maker installs next to this helper and names with `--scene-builder` (else `ATLAS_SCENE_BUILDER`, else the one next to this program). It lines the model up with the map (world x is the game's x, world y its z, height its y), leaves out the parts the config's `scene.drop` patterns name (none by default), cuts it into square cells of about `scene.cellTriangles` triangles with two coarser levels of detail, compresses them and checks them, into the pack's `scene/<area>/`. Each such map gets its `scene`, its markers their `height` (the game's y), and an area with two floors or more each floor's `heights` on its layer (from the cut below it to the cut above it); an area of one floor has none. Before the pack is installed, `atlas-scene check` checks its 3D side. When the builder is missing or fails for an area, that map stays 2D and the report says why; Cancel stops the builder at once. Without 3D maps the pack is as before.

   **The 3D look** (`--look-3d`, `models` by default; `collision` as above). With `models`, each area's 3D map is made from the game's own models (`models.py`, read in the file reader process as the source `models`, at most 15 minutes an area): every map piece part of the map layout places its model (`map/mAA_BB_CC_DD/*.flver.dcx`; Bloodborne: `mAA_BB_CC_DD_XXXXXX.mapbnd.dcx` binders) by its position, rotation and scale, each vertex first moved by its bone; the finest level of detail of each mesh (face sets of other levels and motion blur left out), turned so its front faces the way its normals do. Each material's diffuse texture is chosen by its MTD (`mtd/*.mtdbnd.dcx`: the sampler that reads the albedo, and its texture coordinates), else by the texture types the model gives, else by name; the MTD's `g_BlendMode` (else the MTD's name: `_Edge`, `_Alp`, water) says whether it is cut out, blended, water, or an effect (left out). Textures are found by name in the area's texture binders (`map/mAA/*.tpfbhd` + `.tpfbdt`, of which only the headers are read until an entry is needed), then loose TPF files, then the other areas' binders; each DDS picture (`dds.py`: Pillow reads DXT1, DXT3, DXT5, BC4, BC5, BC6H and BC7, with the old codes or a DX10 header; the `_SRGB` and `_TYPELESS` variants of BC1 to BC5 are read as their plain forms and 8-bit BGRA pixels here; Bloodborne's PS4 textures are given a header and put in order by Soulstruct first, GNF ones are not read) is kept once, at its own size, as PNG. `scene.write_textured_glb` writes them into the raw glTF file (one node per part, one primitive per material, texture coordinates, each picture once) and the builder keeps the textures (`textures.mode` `keep`: each at its own size at the finest level, halved for the coarser levels; cells are made smaller where one cell's pictures would be too heavy). Every model and texture is read on its own: one that fails is counted and named in the area's `models` entry (models read and failed, parts, materials and how their textures were chosen, texture formats, textures missing or failed, binders searched), and the rest go on. An area whose models cannot be read (none placed, none found, every one failed, or the builder refused them) is made from its collision, and its `scene` says why (`lookNote`); `scene.look` says which was made, and `summary.threeD.looks` counts them.

   **Textured map styles** (`--map-style textured|textured-outlines`). The game's models are read as above (with 3D maps or without), and the builder draws each floor from above (`atlas-scene draw`, as for a map made from a 3D model) in their textures, each texture taken from a copy about as fine as the pixel. `textured.py` gives each triangle its floor: what lies between the cut below the floor and its ceiling, which is the cut above it and, over the floor's own walkable ground, 3 m above that ground; surfaces facing down are on no floor unless their material is seen from both sides. So the roofs over a room are left out of its floor and the room shows. The rim, the walls and (for `textured-outlines`) the outlines are drawn over it, and the floors below faded under it, as for the other styles. An area whose models cannot be read, or without the builder, is drawn `shaded` (or `outlines`), and its entry says so (`mapStyle`, `mapStyleAsked`, `mapStyleNote`).

8. **Report.** `report.json` (kind `make`): per area the geometry read, floors (heights, size, triangles, wall lines, tiles), markers by category, markers not over any floor, bosses expected but not found, item lots missing from the item table (with a hint whether neighbouring rows exist), bonfire registrations, the placement check, the frame, and the 3D model (`scene`: triangles before and after, per level of detail, cells, files and bytes, seconds, the floors' heights, markers with no surface under them; `summary.threeD` and `pack.check3d` over all areas); `previews/<area>_f<floor>.png` (640 pixels, a dot per marker); and `atlas-make-report.zip`. No game text or game files: names stay in the pack.

### Floor cuts file

The Map Maker keeps the player's floor cuts in `floor-overrides.json` beside its settings, and "Save my floor cuts to a file…" writes the same shape. Per game id, then per area (`mAA_BB`), the same entry as the config's `floorOverrides`:

```json
{
  "$comment": "Atlas Map Maker floor cuts …",
  "dark-souls-remastered": {
    "m15_01": { "cuts": [3.2, 8.75], "names": ["Courtyard", "Gallery", ""] },
    "m10_01": { "cuts": [] }
  },
  "bloodborne": {
    "m24_01": { "method": "passages", "passages": [{ "x": 112.5, "z": -40.0, "show": "lower" }] }
  },
  "version": 2
}
```

`cuts` is every cut height in metres (in place of the automatic ones; `[]` is one floor), `names` the floor names lowest first (an empty name keeps the Map Maker's own), and `splitAt` and `mergeAt` work as in the config. Version 2 adds `version` at the top and, per area, `method` (`passages` or `cuts`: the area's own floor method, which wins over the one chosen for the make) and `passages` (for automatic passages: per overlapping place chosen by the player, its centre `x`, `z` in metres and which storey shows on the main floor, `upper` or `lower`; matched at the next make to the place that holds that point, else the place whose centre is nearest within 6 m; at most 256). Files without `version` (version 1) load as before. Keys starting with `$` are left out. To ship a player's cuts for everyone, copy each area's entry into `floorOverrides` of `config/<game>.json`.

### Adjust floors views

Make map keeps what finding floors needs of each area in the report folder (`floor-data/<mAA_BB>.npz`: the area's collision triangles, the markers' positions and categories, the floor settings; on the player's PC only, never in the report zip). `atlas-gamefiles floor-views <report folder> --area <mAA_BB>` (`floorviews.py`) loads it once and says `ready`: the height profile, the automatic and shipped cuts, the heights to show, the area's triangles for the panel's 3D view (16-bit corners between `min` and `max`, base64), a section from the south and from the east (one byte a pixel: walls by how many stand one behind another, walkable floor by how near; the panel colours it by floor as the cuts move), and the markers (position, type, colour). Floor data of version 2 also keeps the area's navmesh triangles and floor method (`ready` then has `method` and `navmeshTriangles`); version 1 data still loads. Then it answers each request line on standard input (`{"id": 1, "cuts": [4.5], "names": ["Low", ""], "outlines": false, "method": "passages", "passages": [{"x": 3, "z": 0, "show": "lower"}]}`) with a `views` line: the floors those cuts give (name, heights, walkable area, markers, and a small picture from above, with outlines when asked), the floor each marker is put on and the height of the surface under it, and the cuts used. For automatic passages it also gives `places` (the overlapping places, as in the report), `passages` (the choices used), `triangleFloors` (one byte a triangle: its floor, 255 for none; base64) for the 3D view, and `sectionFloors` (`x`, `z`: one byte a section pixel, the floor of the walkable ground seen there) so the panel colours the sections by floor. It ends when standard input ends. No game files are read.

**Map styles** (`make --map-style`, `render.MAP_STYLES`): `shaded` (the default), `outlines` (the walls and the edges of the walkable floor as light lines on a dark edge), `floors` ("Colour by floor": each floor in its own colour from `render.FLOOR_PALETTE`, Okabe and Ito's colour-blind-safe colours in the order the Atlas 3D view's Floor colours uses, darker low and lighter high within the floor), `textured` and `textured-outlines` (the game's own models in their textures, see step 7). `render.draw_floor` is the one place a style becomes a floor's picture, for `make`, `make-model` and `redraw`. An unknown style is refused (`error` with code `map-style`). The report has the style in `options.mapStyle` and per area (`mapStyle`); Make this area again can draw one area in another style.

### Making one area again

`make --remake <mAA_BB>`, run in the report folder of a make, makes that area alone again (reading every area's map layout first, so its markers come out as in the whole map) and puts its map in place of the old one in the installed pack. It refuses, with an `error` line that has a `code`, when the pack is missing (`pack-missing`), was written by another version (`pack-other-version`), or the report folder holds no report of this version that made the area (`report-missing`); the app then offers Make map. The area's new tiles and 3D model are written to a hidden `.<id>.remake-<area>` folder beside the pack and checked (`atlas-scene check`) there; its map is merged into the pack's JSON (`pack.merge_area`: its map, layers, regions, locations, guides and checklist entries replaced where they were, every other map's untouched, checklist entries of the same location keeping their ids, entities and categories those still used); then `pack.swap_area` writes each JSON file beside its place, moves the area's old `tiles/<area>/` and `scene/<area>/` aside, moves the new ones in, and swaps the JSON files in (the manifest last), putting everything back if any step fails. After it, `atlas-scene check` checks the whole pack. The report is the last make's with that area's entry, its warnings, the summary and the pack's counts made new, and `remade` set; its previews replace the area's old ones. Cancel before the swap leaves the pack and the report as they were.

The numbers and names that need choosing are in `config/dark-souls-remastered.json` (area names, floor settings and overrides, render settings, bosses with their flags, bonfire names, item category ranges): names and numbers only, no game data. The boss list and flags are written from public knowledge and not yet checked against real files; the report lists any boss it does not find.

## Make a map from a 3D model (`make-model`)

`atlas-gamefiles make-model <model file or level export> --out <report folder> [--maps-folder <folder>] [--name <name>] [--title <title>] [--up +y|+z|-y|-z|+x|-x] [--scale <metres per unit>] [--units <word>] [--textures keep|plain] [--double-sided auto|yes|no] [--floors ground|passages|none] [--floor-separation <m>] [--merge-gap <m>] [--cut-below <m>] [--max-triangles <n>] [--map-style <style>] [--floor-overrides <file>] [--remake] [--assets <export folder>] [--clutter <m>] [--keep-hidden] [--scene-builder <atlas-scene program>]` makes a map pack from a 3D model (glTF, OBJ, STL, PLY or ActorX), or from a game level the player exported (below) for the Map Maker's "Make a map from a 3D model…" (`model.py`). The 3D builder (`atlas-scene`) reads the file: `triangles` turns it to stand up and scales it to metres; the floors are found from those triangles (`floors.py`), by ground area unless `--floors` says otherwise; `draw` draws each floor from above in the model's own textures and colours for the textured styles (`render.draw_layer`'s `fill`; height shaded when the model has none); `build` makes the model itself the pack's 3D map (`scene/model/`). The pack (id from the name, `writtenBy` "Atlas Map Maker", attribution "Made with Atlas Map Maker from a 3D model") has one map with one layer per floor and no locations. A pack made from game files (by its attribution) is never replaced by one made from a model. The report is a make report with `source` `model`, the model's settings and what was read in `model`, and one area, key `model`, whose floor data is kept for `floor-views --area model`; `--remake` makes it again in place (floor cuts from `--floor-overrides` under the pack id, area `model`), and says `model-missing` when the file is gone.

**Ground area** (`floors.ground_cuts`, `floors.automatic` `ground`): the projected area of the surfaces facing up within `groundSlope` (30°) of level, in `groundStep` (1 m) bins of height; peaks strongest first, down to `groundShare` (a tenth) of the largest, at most `maxFloors`, none within `floorSeparation` (3 m) of a stronger one; each level is the highest 0.1 m step in its bin with at least half the bin's strongest step's area, so a slab's top is its level; levels closer than `mergeGap` (2 m) keep the stronger; each floor above the lowest is cut `cutBelow` (1.5 m, `--cut-below`) under its level. With `bothSides` (a model whose faces are seen from both sides), the faces facing down count as facing up.

Tests: `tests/test_model.py` with `tests/model_fixtures.py`, a made-up two-storey house with a yard written as OBJ (with its materials file and a made-up texture) and as STL in millimetres, Z up (`python tests/model_fixtures.py <folder>` writes them). The tests that read model files need the builder (`cargo build --release` in `crates/atlas-scene`, or `ATLAS_SCENE_BUILDER`); `ATLAS_SCENE_REQUIRED=1` makes its absence a failure.

### Game levels exported by the player

`make-model` also takes a whole level that the player exported from their own installed game with an export program they installed: the `.json` of an Unreal Engine level saved by **FModel**, or a Unity **`.unity`** scene exported as a project by **AssetRipper** (`levels.py`, `unreal.py`, `unity.py`). The helper never fetches game files and makes no network requests; it reads only the exported files, and writes nothing into the export folder. `inspect-level <level export> [--assets <folder>] [--clutter <m>] [--keep-hidden] [--max-triangles <n>] [--scene-builder <program>]` puts the level together in a temporary folder and answers with one `inspected` line, as `atlas-scene inspect` does, with the level's report as `level` (the Map Maker shows it before the map is made).

How to export, in short. **FModel**: set the output folder and the mesh export format (glTF `.glb`, or ActorX `.psk`/`.pskx`) with materials and PNG textures; save the level's (`.umap`'s) properties as JSON, and export the meshes it uses into the same `Exports` folder. **AssetRipper**: export all files as a Unity project, meshes as Unity's own `.asset` (or glTF), textures as PNG; choose `Assets/Scenes/<scene>.unity`. A scene that the export program writes as one glTF file is a model already: choose the `.glb` (Y up, metres).

The level is put together as **placements**: a mesh file, a 4 × 4 transform in the level's frame (glTF's: right-handed, Y up, metres, north -Z), a name and its materials' pictures. They are written as an Atlas level file (`.atlaslevel`, JSON) into the work folder, which the 3D builder reads like any model file (`crates/atlas-scene/src/level.rs`: each mesh file read once, placed as often as the level does, a mirroring transform turning its triangles over, every material seen from both sides). The map is then made as for a model, standing up already (`--up` and `--scale` are not used): floors by ground area, the textured floor pictures, and the 3D map with textures at full size at the finest level. The report's `model` holds `level` (`unreal` or `unity`), the settings and `levelReport`: meshes placed and different meshes, left out by why (`hidden`, `editorOnly`, `clutter`, `lowerDetail`, `noMesh`, `notRead`), not found (by name, with counts), types not understood, textures found and missing, notes. A `level` event line carries the same, and warnings say what was left out, not found and not understood.

- **Unreal Engine (FModel)**. The level's JSON is a list of exports (`Type`, `Name`, `Outer`, `Properties`); references are `{ObjectName, ObjectPath}` (the path ends with the export's index) or, from older versions, one string. Scene components are placed through `AttachParent` (a component without one hangs under its actor's `RootComponent`) by `RelativeLocation`, `RelativeRotation` (pitch, yaw, roll, as the engine's rotation matrix) and `RelativeScale3D` (missing: no move, no turn, scale 1), with `bAbsoluteLocation`/`Rotation`/`Scale`. Missing properties are taken from the component's `Template` or `Archetype` when that package's JSON is in the export folder too (a placed Blueprint's). Meshes: any component with `StaticMesh` (or `SkeletalMesh`, `SkinnedAsset`), each instance of `PerInstanceSMData` for instanced and foliage components, spline meshes placed without their bend, skeletal meshes in their rest pose; `OverrideMaterials` per slot. Left out with hidden surfaces: `bHiddenInGame`, `bVisible` false, `bRenderInMainPass` false, hidden actors (`bHidden`), volumes, and names of invisible walls and collision; editor-only components and actors always. Other components that look as if they draw something (`LandscapeComponent`, `ModelComponent`, water, procedural meshes) are counted as not understood. Unreal is left-handed, Z up, in centimetres: a point (x, y, z) is (x, z, y) / 100 in the level's frame, each transform turned the same way (P · M · P⁻¹), so the map shows the editor's top view (X east, Y south). Mesh files are found by their package path (`/Game/X/SM_A` as `<game>/Content/X/SM_A`), glTF first (taken to be as FModel writes it: Y up, metres), then ActorX (Y turned over, Z up, centimetres). A material with no picture in the mesh file is looked up by name: FModel's JSON (`TextureParameterValues`, `Parent`, a base material's `CachedReferencedTextures`), a material summary (`Textures`) or a `.mat` text file; the diffuse picture is the parameter named like `Diffuse`, `BaseColor`, `Albedo` or a texture named `…_D`, `…_BC`, found as PNG.
- **Unity (AssetRipper)**. The scene's YAML is read with PyYAML (MIT; every value as text). Objects are placed through `m_Father` by `m_LocalPosition`, `m_LocalRotation` and `m_LocalScale`; a `MeshFilter`'s mesh drawn by its `MeshRenderer` (or a `SkinnedMeshRenderer`'s, in its rest pose), with the renderer's `m_Materials`; a statically batched renderer places only its submeshes of the combined mesh, where that lies; a `LODGroup` keeps only its finest level. Left out with hidden surfaces: inactive objects (and those under one), disabled renderers, shadows-only renderers, objects with a mesh and no renderer (a `MeshCollider` is placed only when hidden surfaces are kept) and names of invisible walls; `EditorOnly` objects always. `Terrain`, `SpriteRenderer` and prefab instances are counted as not understood. Files are found by the GUIDs of their `.meta` files: Unity's own mesh `.asset` (its vertex channels, 2019 and earlier layouts, 16- or 32-bit indices, submeshes) is written as glTF into the work folder; `.glb`, `.gltf` and `.obj` meshes are read as they are (taken to be mirrored in x as Unity glTF exporters write them); FBX is not read (the report says to export meshes as glTF or `.asset`); Unity's built-in cube, sphere, cylinder, capsule, plane and quad are made here. A material's texture is `_MainTex`, `_BaseMap`, `_BaseColorMap` or the like, its colour `_Color` or `_BaseColor` (sRGB). Unity is left-handed, Y up, in metres: a point (x, y, z) is (x, y, -z) in the level's frame, so north is Unity's +Z, as its top view shows; each mesh's triangles are turned over with it.

What is not known without a real export: these follow the export programs' documented and commonly seen file shapes, with made-up test exports only. Unknown fields are ignored, a missing transform is no transform, and whatever is not understood is reported rather than guessed.

Tests: `tests/test_levels.py` with `tests/level_fixtures.py` (a made-up FModel export and a made-up AssetRipper project: `python tests/level_fixtures.py <folder>` writes them), including the handedness of both engines on the map.

## Draw all areas again (`redraw`)

`atlas-gamefiles redraw <pack folder> --out <report folder> [--map-style <style>] [--floor-overrides <file>] [--floor-method passages|cuts] [--scene-builder <atlas-scene program>] [--stdin-cancel]` draws every 2D floor of a map pack again from the pack's own 3D maps, with no game files (`redraw.py`), for the Map Maker's "Draw all areas again". For each map with a `scene`, the 3D builder reads the model back out of the pack (`atlas-scene unpack <pack> <map id> <out.glb>`: each cell's finest level present, meshopt decoded, as one raw model in the world), then reads it as any model file (`atlas-scene triangles`). Its floors are found as `make` finds them, with the player's cuts for the map's area when there are some, else from the pack's own floors (its layers' `heights`; automatic passages again where they overlap), and drawn through `render.draw_floor` in the style asked for (the textured styles too, drawn by `atlas-scene draw` as for `make-model`, for a map not turned against the world), at the map's own size and `worldTransform`, into its layers' own tiles. A pack the Map Maker made (`writtenBy`) takes the floors as they now are, layers and locations with them; any other pack keeps its layers, and a map whose floors would change in number is left. Lines: `start`, `maps`, `progress`, one `map` line per map (`redrawn`, or `reason`), `warning`, then `done` (or `cancelled`, exit 3; `error`, exit 2). Nothing is changed until every map is drawn: the tiles are written to `.<pack>.redraw` beside the pack and swapped in by renames, the old ones kept in `.<pack>.redraw-old` until all is in place and put back on failure. `report.json` has `kind` `redraw`, per map what was drawn or why not, a summary and the 3D check of the pack afterwards.

Tests: `tests/test_redraw.py`, on a pack `make` made from the made-up game folder.

## Promises, enforced in code

- **No network.** Every socket connection and name lookup in the process raises (`safety.block_network`).
- **The game folder is only read.** The output folder may not be inside it (or contain it), and nothing is copied from it: the report holds counts, file names, coordinate ranges and error messages, and the previews are drawn from coordinates.
- **A map pack goes only into the maps folder**, which may not be inside the game folder (or contain it), through a hidden staging folder there, replacing only a pack the Map Maker wrote.
- **Nothing else is written.** Soulstruct normally reads and writes a config file and a log file in the user's AppData (or next to a frozen executable) and loads an Oodle DLL from other games' folders. `safety.prepare_soulstruct` imports it with those paths pointed at an empty temporary folder, its logging set-up replaced and DLL loading hidden.
- **What the executable must not carry is checked at build time.** The PyInstaller spec takes only Soulstruct's code, its instruction and field definitions (JSON), type stubs and Havok type lists, and fails if the Oodle DLL, any bundled `.exe`/`.dll`, Havok templates or paramdef/material binders got in.

### Tests use made-up files only

`tests/fixtures.py` writes made-up game folders with Soulstruct itself: MSB map layouts, an ItemLotParam, item name tables, collision meshes in an HKXBHD/HKXBDT pair and a navmesh binder, all with invented names, ids and a few triangles. `python tests/fixtures.py dsr <folder>` writes one by hand (CI uses it to try the built executable). `python tests/fixtures.py dsr-map <folder>` adds what Make map needs: a two-storey made-up area (a ground floor with a building, a rooftop 9 m up, one of its collision meshes moved and turned by its part), event scripts registering bonfires, chests and corpses, a boss, an NPC, an enemy with a guaranteed drop, and goods, NPC and place tables. `tests/test_make.py` makes a pack from it; `tests/test_scene.py` makes its 3D models with the builder (`cargo build --release` in crates/atlas-scene first, or name it in `ATLAS_SCENE_BUILDER`; without it those tests are skipped, unless `ATLAS_SCENE_REQUIRED` is set, as in CI); CI also makes one with the built executable and validates it with `pnpm --filter @atlas/pipeline validate-pack`. `python tests/fixtures.py dsr-textured <folder>` adds made-up models and textures to that area: a ground plane, a roof whose vertices stand on a bone 9 m up, a crate moved, turned and scaled by its part with a cut-out leaf and a mesh whose texture is nowhere, and a file that is not a model; its textures are DXT1, DXT5, BC1 sRGB and BC7 (DX10) pictures of one colour each, in a texture binder, another area's binder and a loose TPF. `tests/test_game_models.py` reads them, makes their 3D map (each texture at its own size at the finest level) and draws the textured styles; CI makes its pack with the built executable. What Soulstruct 2.6.0 cannot write is tested with a mock, or left out, and says so in the test:

- materials (MTD): Soulstruct's MTD writer fails, so the made-up models have none, and their materials are told apart by texture types and MTD names, as without an MTD;
- Bloodborne MSBs: Soulstruct's writer leaves part offsets unfilled, so the Bloodborne fixture's map layout is a Dark Souls one, read with a mocked class;
- Bloodborne collision and navmesh (Havok 2014): Soulstruct does not write them, so `tests/havok_fixtures.py` writes made-up packfiles byte by byte (a compressed mesh placed by a body, a navmesh, an `.nva` table). `python tests/fixtures.py bloodborne <folder>` writes a made-up 1.09 dump: a bridge over a street in a collision binder with a `.patch` pair, its navmesh, lamps run by common event 7000, lot chains, made-up names. `tests/test_make_bloodborne.py` makes a pack from it; `tests/test_passages.py` checks automatic passages on invented shapes (a bridge, ramps, a four-storey keep).

No real game data is used in tests, committed, or shipped.
