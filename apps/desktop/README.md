# Atlas desktop

The desktop app is a [Tauri 2](https://v2.tauri.app/) shell around the same static build as `apps/web`. It adds one window, a small Rust protocol that serves data packs to it, a maps folder shared by every Atlas app on the computer plus pack folders the person chooses, native file dialogs for progress export and import, and, in builds that include importers, "Add a map" from a web page. It shows the map images that are in a pack's folder, wherever they came from. The plain Atlas app is a viewer: it cannot fetch map images from other servers. A downloader for packs whose map images live on a tile server, and saving them from a map page, are only in builds made with `ATLAS_ENABLE_DOWNLOADS=1` (see "Building another app from the shell").

## Prerequisites

All platforms need Node.js and pnpm as in the root README, plus Rust (stable, 1.90 or newer) from [rustup](https://rustup.rs/).

- **Windows 10 or 11**: Microsoft C++ Build Tools with the "Desktop development with C++" workload, and the MSVC Rust toolchain (`rustup default stable-msvc`). WebView2 ships with current Windows.
- **macOS**: Xcode, or just the Command Line Tools (`xcode-select --install`).
- **Linux (Debian or Ubuntu)**:

  ```sh
  sudo apt install libwebkit2gtk-4.1-dev build-essential curl wget file libxdo-dev \
    libssl-dev libayatana-appindicator3-dev librsvg2-dev
  ```

  Other distributions: see [Tauri's prerequisites](https://v2.tauri.app/start/prerequisites/).

## Run and build

From the repository root:

```sh
pnpm desktop:dev     # window on the Vite dev server, with hot reload
pnpm desktop:build   # release build and installers
```

`desktop:dev` starts Vite on port 1420 (`--strictPort`, so it stops rather than attach to another server) and opens the window on it; packs come from the dev server, as in the browser. For a window with map image downloads, run `ATLAS_ENABLE_DOWNLOADS=1 pnpm desktop:dev --features downloads` (the variable is for the web app, the feature for the shell).

`desktop:build` builds the web app and demo pack, prepares `apps/desktop/dist` from it (`scripts/prepare-frontend.js`), compiles the Rust shell and writes installers to `apps/desktop/src-tauri/target/release/bundle/`: NSIS `.exe` on Windows, `.app` and `.dmg` on macOS, `.deb`, `.rpm` and `.AppImage` on Linux. Tauri CLI options can follow, for example `pnpm desktop:build --debug --no-bundle` for a quick debug build without installers.

Rust checks, from `apps/desktop/src-tauri`: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test`, and the last two again with `--features downloads` for the code of a build with downloads. They work on a fresh clone; nothing has to be built first.

### Building another app from the shell

A build can give the app its own name and identifier, so it installs next to the plain Atlas app instead of replacing it:

```sh
ATLAS_APP_NAME="My Atlas" ATLAS_APP_IDENTIFIER=org.example.my-atlas pnpm desktop:build
```

`scripts/build.js` checks both (set both or neither; the identifier must differ from `dev.atlas.desktop`), writes them to `src-tauri/tauri.identity.conf.json` (ignored by git) and passes it to `tauri build` after the bundling config. The name becomes the product name, the window title, the installer's name and the name shown in the top bar. Such an app keeps its own app data, and so its own progress and settings of the page, but shares the maps folder and the shared settings file (below) with every other Atlas app.

Map image downloads are switched on the same way, at build time, with `ATLAS_ENABLE_DOWNLOADS=1` (unset or `0` leaves them off, anything else is refused):

```sh
ATLAS_ENABLE_DOWNLOADS=1 ATLAS_APP_NAME="My Atlas" ATLAS_APP_IDENTIFIER=org.example.my-atlas pnpm desktop:build
```

It turns on "Download map images" and "View map page and save images as I browse" (see the sections below), in every layer at once:

- `scripts/build.js` passes `--features downloads` to `tauri build`. Only with the shell's `downloads` Cargo feature is that code compiled in (`src/tiles/download.rs`, `downscale.rs`, `manager.rs`, `src/pageview/`, and the HTTP client): without it the binary has none of it, and its commands (`tiles_*`, `download_settings_*`, `view_*`, `sites_*`) do not exist.
- `build.rs` lists those commands only with the feature, and only then reads `capabilities/downloads/main-downloads.json`, which grants them to the main window; `capabilities/main.json` grants the commands of every build. A capability that names a command the build does not have would stop the build, so the file is chosen at build time.
- The web build that `tauri build` runs first reads the same variable (`apps/web/vite.config.ts`) and folds it into the bundle as the constant `__ATLAS_DOWNLOADS__`. Without it the download panel, its settings, the map page actions and their card are left out of the bundle, not only hidden: a map without its images just says that its image is not installed, and the Maps dialog offers neither downloading nor saving.
- `desktop_info` says whether the shell has downloads (`downloads`), and the web app offers them only when both agree.

Without it, the default, the app still shows map images already in a pack's folder (downloaded by an earlier version or by a build with downloads), moves those of version 0.2.0, counts them and deletes them ("Delete downloaded images…"), deletes maps and keeps the activity log. `node scripts/check-binary.js [binary]` checks a built binary: it fails when a viewer holds download code (the names of its commands, the downloader's User-Agent or the saving script), or when a build with downloads lacks it. Which one it expects is what `ATLAS_ENABLE_DOWNLOADS` says when set, else what the last `pnpm desktop:build` recorded in `src-tauri/atlas-build.json` (ignored by git), else a viewer; the smoke and Windows start-up tests check the same way, so a builder sets the variable for the build only. CI and the release workflow run it.

Importers are added the same way, at build time: `ATLAS_BUNDLE_IMPORTERS` takes comma-separated paths of importer modules (absolute, or relative to the repository root). `scripts/prepare-frontend.js` loads each in Node to check it against the contract in `packages/importer-api` (and refuses modules that import Node built-ins), copies it to `dist/importers/<id>.js` and lists it under `importers` in `config.json`. A build without it has no importers and shows no "Add a map".

### Desktop tests

Five WebDriver tests drive the built app through [tauri-driver](https://v2.tauri.app/develop/tests/webdriver/). They need `cargo install tauri-driver --locked` and the platform's WebDriver: on Linux the package that provides `WebKitWebDriver` (`webkitgtk-webdriver` on newer Ubuntu and Debian releases, `webkit2gtk-driver` on older ones), `xdotool`, and `xvfb-run` without a display. They run on Linux; see below for Windows. Screenshots go to `apps/desktop/test-results/`. On Linux, the tests run the app with `XDG_DATA_HOME` and `XDG_CONFIG_HOME` in a temporary folder, so they start from a first launch and leave your own data alone, and with a stand-in system browser that only records the links it is asked to open.

- `pnpm --filter @atlas/desktop test:e2e` (smoke test, on a `pnpm desktop:build` with the demo pack and without downloads): the map, its tiles and markers load; progress can be saved (IndexedDB works); the pack protocol answers range requests; the shell's commands answer. It checks that the binary holds no download code, that `desktop_info` says so and that the download and map page commands are refused. On Linux it also exports progress through the native save dialog and imports it back through the open dialog (typing into them with `xdotool`), checks that a guide link opens in the system browser while the window stays on the app, that the plain app has no "Add a map", and opens a pack folder through the native folder picker; that pack has no map images, and the notice only says so, with no download; and the Maps dialog, which also lists a pack added from a web page, offers no download, no map page and no saving. It expects downloads when the last `pnpm desktop:build` recorded them in `src-tauri/atlas-build.json`, or as `ATLAS_ENABLE_DOWNLOADS` says when it is set (a stale `src-tauri/target/release/packs/e2e-remote` from a build for the other tests makes it fail: rebuild without it).
- `pnpm --filter @atlas/desktop test:e2e:download` (download test, Linux, on a build with downloads): downloads map images from a mock tile server on `127.0.0.1:4431` (`ATLAS_E2E_TILE_PORT` to change it) through the app's interface, over three launches: the middle of the map asked for first, a refusing server (the panel names the refused image and its address, and the Activity log dialog shows the refusal and copies exactly the lines of the log file it shows), Standard detail with one corner answered the way an object store answers for an image it does not have (counted as not on the server, the four tiles under it never asked for), an upgrade to Full detail with pause and resume, the app closed mid-way and the job picked up after a restart, and the last game remembered. It checks every request the server saw (one per tile, the User-Agent, no cookie), the status files, and that markers sit on dots the server paints into its tiles. Build it with the test pack first:

  ```sh
  pnpm --filter @atlas/desktop e2e:pack     # writes packs/e2e-remote/ and packs/test-isles/ (ignored by git)
  ATLAS_ENABLE_DOWNLOADS=1 ATLAS_BUNDLE_PACKS=e2e-remote,demo pnpm desktop:build --no-bundle
  xvfb-run -a pnpm --filter @atlas/desktop test:e2e:download
  ```

  `node apps/desktop/e2e/tileServer.js` runs the mock server on its own, to try the pack by hand.

- `pnpm --filter @atlas/desktop test:e2e:import` (maps library and import test, Linux), on the same build with the demo importer and the test pack `test-isles` added (`ATLAS_BUNDLE_PACKS=e2e-remote,demo,test-isles ATLAS_BUNDLE_IMPORTERS=packages/importer-api/demo/demo-importer.js`; `e2e:pack` writes `packs/test-isles/` too, a made-up game built from the demo site's pages with the demo importer, with its page data). The demo site runs on `127.0.0.1:4432` (`ATLAS_E2E_SITE_PORT` to change it; the demo importer's list of worlds and `test-isles` name that port). Before the first launch it writes what an earlier version and the person could have left behind: a half-done version 0.2.0 download in the old app data folder, and a shared settings file remembering a copied pack folder with its images (under a path with spaces and non-ASCII letters), a folder with a second pack of an id already shown, a folder that is gone and a folder that is not a pack. It checks that the old download moves into the pack folder and finishes without fetching anything twice, that download settings are saved to the shared file, the Maps dialog's locations and their states, the hidden duplicate and its reason, forgetting a location without deleting files, and the copied pack's own images. Then it adds maps from a made-up map site on `127.0.0.1` (`e2e/demoSite.js`): an address no importer knows, a page whose data appears after a while, a second map of the same game, the first page again after the site changed, a game that comes with the app, data in the wrong shape, cancelling, and waiting too long, and it downloads the imported game's map images into its pack folder. The made-up page tries to call the app, read its packs, open a window and leave for another site, and reports what happened; the test checks that each was refused. A second launch checks that everything is remembered and deletes the imported pack. Then it pastes several addresses at once: two maps of one made-up game, one of another, a game that comes with the app, a page whose data never appears, a repeat and an address no importer knows. It checks that the unknown address is shown before anything opens, that the pages are asked for once each in the order given, one at a time and at least 3 seconds apart (from the activity log's times), that the run goes on past the pages not added, the state of each, the summary, the game shown at the end, a single offer to download map images, and the run's lines in the activity log. `node apps/desktop/e2e/demoSite.js` runs the site on its own.

- `pnpm --filter @atlas/desktop test:e2e:delete` (delete test, Linux), on the same build as the download test. Before the first launch it puts a made-up game "My Game" into the maps folder and a `.deleting-*` folder as a delete leaves behind when a file stays in use. It checks that the left-over folder is removed at start; that **Delete downloaded images…** on the bundled test pack says how many images go, removes them and only them, and the map asks for them again; that **Delete…** on "My Game" during a slow download says the download is stopped first, deletes the folder mid-download with nothing left behind and no request after it, and that the app goes on working; and, after a restart, that both stay that way. `ATLAS_E2E_SHOTS=<folder>` also copies the pictures of both confirmations there.
- `pnpm --filter @atlas/desktop test:e2e:view` ("View map page" and "Save map images as I browse" test, Linux), on a build with downloads. It needs `python3` as well, to send a window the close request its close button would (there is no window manager under Xvfb). It serves a made-up map site and its image server on `127.0.0.1` (`e2e/mapPageSite.js`; `node apps/desktop/e2e/mapPageSite.js` runs them on their own) and writes a pack made from two of the site's pages into the maps folder, with one map image already in it. It checks that the Maps dialog lists the pages, that "Open in my browser" hands the recorded address to the system browser, that addresses the pack does not record are refused, and that plain viewing writes nothing. With saving on, a page that loads its images with `fetch` and `XMLHttpRequest` while "zooming in": each image lands in the pack where the downloader puts it, byte for byte, the image already there is kept, a marker icon and a level the pack does not use are ignored, the status file, the shrunk level and the manifest are brought up to date, the pack's lock is held so a download cannot start, the page cannot call the app, read packs, open windows or leave its site, three images at the map's edge, answered the way an object store answers for an image it does not have before the page loads the rest of their level, get the downloader's "not on the server" marker, a count on the card and a line in the activity log, the map shows the saved images, and the image server saw every image asked for exactly once. A page that shows its images with `<img>` elements and a `no-cors` request gets "could not be saved" and nothing written, and closing its window stops saving and frees the pack.

CI is set up to run the smoke test on the default build, and the other four on a build with downloads, on Linux; that Linux job is switched off for now (the `desktop` matrix in `.github/workflows/ci.yml` lists Windows only), so run them locally on Linux when you change what they cover. On Windows, CI runs `pnpm --filter @atlas/desktop test:e2e:windows` instead (`e2e/windows.js`), on the default build: it checks that the binary holds no download code (the same check as `scripts/check-binary.js`; on a build with downloads, that it holds it), then starts the built app with a temporary WebView2 profile and checks from outside that the window opens with the app's title, that the embedded browser starts the app's page, and that the app is still running and responding ten seconds later. It saves a picture of the desktop to `apps/desktop/test-results/desktop-windows.png`, which CI uploads, for a person to look at. It does not look inside the page: an Edge WebDriver has to match the installed WebView2 exactly, and both it and a direct DevTools connection rely on `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`, which WebView2 does not apply to an app that passes browser arguments of its own, as Tauri does.

The first name in `ATLAS_BUNDLE_PACKS` is the game shown on first launch; after that the app opens the game picked last. Any pack folder in `packs/<id>/` can be bundled this way.

## Android

The same shell builds an Android app, a viewer for Android 10 (API 29) and later, with the identifier `dev.atlas.android` and the name "Atlas" (`src-tauri/tauri.android.conf.json`, which Tauri merges over `tauri.conf.json` for Android builds). The desktop app's identifier and behaviour do not change.

It needs, besides Node.js, pnpm and Rust: Java 17, the Android SDK and NDK with `ANDROID_HOME` and `NDK_HOME` set (see [Tauri's prerequisites](https://v2.tauri.app/start/prerequisites/#android)), and the Rust target `aarch64-linux-android`. Then, from the repository root:

```sh
pnpm android:build --target aarch64
```

`scripts/build.js android` creates the Android project with `tauri android init` when `src-tauri/gen/android` (ignored by git) does not exist, then runs `tauri android build --apk` with the other arguments. The APK, unsigned, lands in `src-tauri/gen/android/app/build/outputs/apk/`. `bash scripts/sign-apk.sh <unsigned.apk> <signed.apk>` aligns and signs it with `zipalign` and `apksigner` and verifies the signature: with the key in `ANDROID_KEY_BASE64` (a keystore, base64), `ANDROID_KEY_ALIAS` and `ANDROID_KEY_PASSWORD` when they are set, else with a key made for that run only, which cannot update an app signed with another key. The version code follows the app version (major × 1,000,000 + minor × 1,000 + patch), so a newer build installs over an older one signed with the same key. The build refuses `ATLAS_ENABLE_DOWNLOADS=1`, `ATLAS_BUNDLE_IMPORTERS` and `ATLAS_APP_NAME`/`ATLAS_APP_IDENTIFIER`.

How it differs from the desktop app:

- **Packs that come with the app** are part of its web build (`packs/<folder>/` in `dist`), served with the page from `http://tauri.localhost`, not resources served by the `atlas-pack` protocol: an Android app's resources are inside its package, not a folder. They must use folder tiles, since the Android WebView answers byte ranges from the app itself and so cannot read PMTiles archives; the build sets `ATLAS_DEMO_TILES=xyz` for the demo, and `scripts/prepare-frontend.js` refuses a pack with a `.pmtiles` file for Android.
- **The `atlas-pack` protocol** is served at `http://atlas-pack.localhost/<id>/`, as on Windows, for packs in the maps folder.
- **The maps folder and the shared settings file** are in the app's own storage (`Atlas/Maps` and `Atlas/settings.json` under the app's data folder). The page keeps the `http` scheme (`http://tauri.localhost`), so progress in IndexedDB stays where it is from one version to the next.
- **Not on Android:** folder dialogs (choosing the maps folder, adding pack folders), showing folders in a file manager, progress export and import (Android's dialogs give `content://` addresses that the shell cannot read or write yet), the import window and "Add a map", moving the map images of version 0.2.0, map image downloads, and exporting map pack files or picking one to import (the import commands that take a path are there, waiting for Android's file picker to be connected). The commands for them answer "This is not available on this device." and `desktop_info` says `folders`, `progressFiles` and `imports` are false, so the web app shows no Maps button, no export or import of progress files (it says so in the Profiles dialog) and no "Add a map".

`node scripts/check-apk.js <app.apk> [--packs demo] [--forbid <text>]...` checks a built APK and the frontend it was built from (`dist`): the native library holds no download code (as `check-binary.js` does), the app comes with exactly the packs named, `config.json` lists no importers, and no file contains a forbidden text. CI's Android job runs it, and checks the package name, the app name, the minimum Android version and the 64-bit ARM library with `aapt2`. CI also signs that APK with a throwaway key and checks it again. Running the app on a phone or an emulator is not part of CI.

The `Android release` workflow (`.github/workflows/android-release.yml`, run by hand with the version in `apps/desktop/package.json`) builds the APK with the demo pack only, signs it (with the repository secrets `ANDROID_KEY_BASE64`, `ANDROID_KEY_ALIAS` and `ANDROID_KEY_PASSWORD` when they exist, else with a throwaway key, which the release notes then mention), runs the checks above, and attaches `Atlas-<version>-android.apk` to the release `android-v<version>`: a draft unless its `draft` input is turned off. No signing key is ever committed to this repository.

## How packs are served

PMTiles archives are read with HTTP range requests. Tauri's built-in protocol for the bundled frontend (`tauri://localhost`, or `http://tauri.localhost` on Windows) ignores the `Range` header and always answers `200` with the whole file, which the PMTiles reader rejects. So the desktop build does not embed packs in the frontend:

- `scripts/prepare-frontend.js` copies the web build without `packs/` and writes an explicit `packs` list into `config.json`, one entry per pack in the build's `packs/index.json` (set by `ATLAS_BUNDLE_PACKS`), each pointing at the `atlas-pack` protocol: `atlas-pack://localhost/<id>/` on Linux and macOS, `http://atlas-pack.localhost/<id>/` on Windows (WebView2 serves custom schemes that way). The app then never requests the index.
- `src-tauri/tauri.build.conf.json` ships the web build's `packs/` folder as app resources. It is only merged in by `tauri build`, so Rust checks do not need a web build first.
- `src-tauri/src/packs.rs` registers each bundled pack folder under its folder name and serves `<scheme>/<pack id>/<file>` from it, with single byte ranges, `ETag`, CORS headers (the page and the protocol are different origins), and no access outside registered folders (no `..`, hidden files or symbolic links that leave the folder).

Pack folders in the maps folder and in locations the person added are registered the same way, under their pack id, and served from the folder itself. Only the main window may use the protocol: requests from any other webview (such as the import window) are answered with 403. The first path segment `import/` (any case) is never served, so page data kept by "Add a map" stays out of what the map loads. Nothing is listed, and nothing is written through the protocol.

A pack that comes with the app and has no remote map images (the demo world) is served from the app's resources, which are never written to. If something has to be added to such a pack, it goes to an **overlay** folder in the app's data folder, `<app data>/packs/<pack id>/`, which the protocol looks at first. Packs whose map images can be downloaded are installed into the maps folder instead (see below), so their images end up in their own folder. `<app data>` is `~/.local/share/<identifier>` on Linux, `%APPDATA%\<identifier>` on Windows and `~/Library/Application Support/<identifier>` on macOS.

## Maps folder and other locations

Every Atlas app on a computer reads one **maps folder**, wherever it was built and whatever its identifier:

| System  | Default maps folder                                       | Shared settings file                                |
| ------- | --------------------------------------------------------- | --------------------------------------------------- |
| Windows | `%LOCALAPPDATA%\Atlas\Maps`                               | `%LOCALAPPDATA%\Atlas\settings.json`                |
| macOS   | `~/Library/Application Support/Atlas/Maps`                | `~/Library/Application Support/Atlas/settings.json` |
| Linux   | `$XDG_DATA_HOME/atlas/maps` (`~/.local/share/atlas/maps`) | `$XDG_DATA_HOME/atlas/settings.json`                |

The defaults are local folders, not ones that a cloud service syncs. Each entry of the maps folder is a complete pack folder: the pack files, the map images downloaded for it at its layers' own tile paths, their status files (`offline-tiles/`), page data kept by an import (`import/`), and the app's lock, unfinished-download record and, for a pack imported from a map pack file, that file's description (`.atlas/`). Nothing in it names the computer, the user or an app, so a pack folder can be copied elsewhere, or to another computer, and opened there.

The **Maps** button (folder icon in the top bar) opens a dialog that shows:

- the maps folder, with **Change…** and **Open folder**. Changing it never silently moves gigabytes: after choosing a folder the app offers **Move my maps there** when the packs can be moved by renaming (same drive; every pack is checked before any moves, and a pack that is downloading stops it), and **Use it for new maps only** otherwise or when preferred, in which case the old folder stays listed as a folder of packs and can be moved by hand;
- every pack shown, where it comes from (the app, the maps folder or an added folder), its folder, and **Show**, **Open folder**, **Update from the site…** (games added from web pages with an importer of this app; see "Updating games" below), **Rebuild** (imported packs, from the page data kept with them), **Export…** (see "Map pack files" below), **Details** (where the game's data came from and when its pages were last read, the pack version, what it holds, at what detail and when its map images were downloaded, and the map pack file it was imported from, if any), **Delete downloaded images…** for every pack with a folder, and **Delete…** for packs in the maps folder that do not come with the app (see "Deleting maps and map images" below);
- **Update all…** above the packs, when any game can be updated from its site, and **Import map pack file…** (in the desktop app without downloads, **Add a pack file…**; see "Adding a pack file in the app without downloads" below);
- packs that are not shown, and why;
- **Games in other folders**: one game's folder added with **Add a game’s folder…** (anywhere on the computer) and folders of games added with **Add a folder of games…**. They are remembered between runs and between apps. A location that is gone (for example an unplugged drive) stays listed as "Not found" with a plain message, and comes back when the drive does; a folder that is not a pack, or holds none, says so. **Remove from list** forgets a location and never deletes files.

Packs are read as untrusted: only folders whose `manifest.json` is a pack manifest of version 1 or 2 with a usable id are listed (at most 4 MB), the web app validates every file with the pack schema, symbolic links are not followed out of a folder, hidden folders are skipped, and the protocol's path checks apply. Nothing is written into a pack folder that was opened for viewing unless the person starts a download or an import for it.

**Pack files read where they lie.** A map pack file (`.atlaspack`) does not have to be imported to be shown. The app reads the pack files in the **packs folder** (by default `Packs` beside the default maps folder, `packs` on Linux, created when missing; **Open packs folder** in the settings; it can be changed, see "Changing the packs folder" below) and in the folders of games added with **Add a folder of games…**, sub-folders included (another app may keep them as `<game>/<game> - <site>.atlaspack`), but not in a folder whose name begins with a dot, inside a pack folder or in the maps folder; a file whose name ends in `.part` is never read. Each file is checked as an import checks it, its list of contents when it is opened and each file's content at its first read (see `src/packfile/inplace.rs` and [docs/pack-file-format.md](../../docs/pack-file-format.md#reading-a-pack-file-where-it-lies)), and listed from its description; a file that cannot be used is listed under "Pack files and folders that Atlas could not read" with the reason, as is each folder a limit left out (at most 1,000 pack files and 100,000 files and folders for one folder, 4 folders down). Only the tables of contents of the few packs read last are kept in memory. The protocol serves its pack files, map images and pictures from the file itself, with byte ranges, and reads a file that another app replaced while Atlas runs from the new file. Atlas never changes or deletes a pack file, moves or renames one only when the person changes the packs folder and asks to move its files (below), and writes nothing beside it: the person's own lists, locations, pages, notes, photos and guide links of the game are kept in the maps folder by the game's id, as for a pack folder, and found marks in the app's storage, so a newer file of the same game keeps them. For a game read from a pack file, export, refreshing it from its site, building it again, map image and photo downloads, map pages, the editors of a map made in the app, deleting it and deleting downloaded images are not offered or answer with a sentence that says why. In the app with downloads, **Import a pack file…** puts it into the maps folder, where it can be changed; the desktop app without downloads unpacks no pack file and says only why. To take it out of the list, delete or move the file, or remove the folder it is in from the list.

**Changing the packs folder.** On a desktop (Windows, Linux, macOS; never Android, whose packs live in the app's own storage), Settings, under "Games in other folders", shows the packs folder with a "Default" badge while it is the default, **Change packs folder…** (the system's folder dialog) and, once another is chosen, **Use the default folder**. Both apps offer it, the viewer and the app with downloads. The choice is kept as `packsFolder` in the shared settings file (the table above), so every Atlas app on the computer reads the same packs folder, and each follows a change at once, without a restart: the Library, the folder watcher (which stops watching the old folder and watches the new one), **Add a pack file…**, **Write the pack file** of a map made in the app, old folders and the keeper of packs (below). Another program that puts pack files where Atlas reads them should read `packsFolder` from that file: a full path when the person chose a folder, absent (or `null`) for the default folder, `Packs` beside the settings file (`packs` on Linux). A value Atlas cannot use (empty, not a full path, not text, longer than 4,096 characters, or one that goes up a folder with `..`) counts as the default, with one line in the activity log. Only the default folder is made when missing: a folder chosen that cannot be found (as on a drive that is not connected) is never made, since its path would then be made on another drive; the settings say "Not found", and **Add a pack file…**, **Write the pack file** and the keeper of packs say why nothing was written. Choosing a folder only asks first (`library_choose_packs_folder`, `library_default_packs_folder`): the question names the packs folder now and the new one, how many pack files the old one holds and their size, and offers **Move the pack files there**, **Leave them where they are** or **Cancel** (`library_apply_packs_folder`, the folder checked again first). Refused, each with a sentence: the packs folder itself, a file (a pack file or another), a pack folder or a folder inside one, the maps folder or a folder inside it or around it, a folder that is listed under "Games in other folders" or lies inside one (remove it there first), a folder inside the packs folder now, and a folder Atlas cannot write to (a small file is written there and removed to find out). Not while a pack file is saved, added or imported; in the app with downloads the keeper of packs stops its run first. The code is `src/library/packsfolder.rs`.

- **Move the pack files there** moves the pack files Atlas reads in the old folder, as the look above finds them (sub-folders included, never a `.part` file, a folder whose name begins with a dot or a pack folder), and nothing else, into the new folder at the same place below it. On the same drive each file is renamed. Across drives each is copied to a `.part` name in the new folder, checked (the same size, and its description still reads), renamed to its name, and only then deleted from the old folder. A file that is in use, or whose copy fails, stays where it was and is named in the settings with why; the move goes on with the others. A file of the same name in the new folder (or one another program is writing there as `.part`) is never written over: the file moved gets ` (2)`, ` (3)` and so on, as an added pack file does. Sub-folders the move emptied, and the old folder itself once empty, are removed; a folder that still holds anything stays.
- **Leave them where they are** changes the setting only. The pack files left in the old folder are no longer shown, unless the person adds that folder under "Games in other folders".
- **Paths kept elsewhere** follow a moved file: the list of pack files opened (`packFiles`), the pack file each working folder of a map made in the app was opened from (`.atlas/editing.json`), and the files this app wrote of maps made here (`made-packs.json`). Another app's own record cannot be updated from here, so **Write the pack file** also looks for a file kept at a path that is gone under its name in the packs folder now, and takes it when it is the same file (the same `exportedAt`); otherwise it writes a new file as when the file is gone.

The shell's tests (`src-tauri/src/library/packsfolder/tests.rs`, and the setting's in `src/settings.rs`) check each refusal, a move on one drive with a name taken, a file in use and files that are not pack files left alone, the copy across drives with its check, a damaged file and an original that cannot be deleted, leaving the files where they are, the default folder again, and the paths kept elsewhere after a move. The browser test `apps/web/e2e/packsFolder.spec.ts` drives the settings against a stand-in shell.

**Opening a pack file from the file manager.** The Windows installer of the plain Atlas app registers the `.atlaspack` file type (`bundle.fileAssociations` in `tauri.windows.conf.json`). A build with its own name and identifier registers no file type (see `scripts/build.js`), so that with two apps from this shell installed side by side a pack file always opens in Atlas, whichever was installed last; such a build still shows a pack file it is started with. Opening such a file, or starting Atlas with its path, shows it: the file is read where it lies, never copied or imported (`Library::open_pack_file`). In the app with downloads, **Import a pack file…** stays the way to put it into the maps folder; in the desktop app without downloads, **Add a pack file…** copies it into the packs folder. A file in a folder Atlas reads already is simply shown. One elsewhere is added to the list of pack files opened, kept in the shared settings file (`packFiles`, at most 100, the oldest dropped first), listed in the settings under "Pack files you opened" and read at every start like the packs folder. It leaves that list when the person presses **Remove from list** (which deletes no file), or by itself when the file is gone while its folder is there (deleted, moved or renamed; the activity log says so); while its whole folder cannot be found, as on a drive that is not connected, it stays listed as "Not found". When the game's id is shown already from elsewhere, the rule above decides, and the sentence says which one is shown and why. A pack file in the maps folder is refused with a sentence that says why. The arguments are read as untrusted (`src/receive/args.rs`): Atlas takes exactly one path, of an existing plain file whose name ends in `.atlaspack`, runs nothing, and leaves every other argument out (an option, several paths, a folder, a missing file), writing what it left out to the activity log. The app without downloads also reads three options another program can start it with, read in the same way (see "Atlas in the background" below); every other option is left out with its line. The Linux bundles and macOS register no file type yet: Tauri's Linux desktop entry starts the app without the file's path (its `Exec` line has no `%F`) and installs no MIME type for `.atlaspack`, so it would need a desktop entry and a MIME file of its own.

**One Atlas at a time.** On Windows and Linux, a second start of the same app (same identifier) hands its arguments to the Atlas running and ends (`tauri-plugin-single-instance`): the running one comes to the front and shows the pack file named, if any. Two apps from this shell, with their own identifiers, still run side by side. Not on Android.

**Pack files that arrive, change or go** are noticed while Atlas runs, without **Look again** (`src/receive/watch.rs`). The folders Atlas reads are followed with the system's file events (`notify`: one watch per folder on Linux, one watch over each folder of games on Windows, so that no watch holds a sub-folder open); an event counts only when it is in a folder Atlas reads and names a pack file, the settings file or a folder, never a `.part` file or a name beginning with a dot. Events are gathered until none came for 1.5 seconds (at most 10 seconds), so a file written through a `.part` file and a rename is looked at once, when it is complete. Then a cheap look lists the folders and the files' sizes and times, without opening a file; only when that changed is the Library read again, and only when the listing changed is the web app told (`library-changed`, with the listing and a number that grows with each change). Atlas also looks when its window gets the focus (at most every 5 seconds), and every 30 seconds while it has the focus for a folder where events may not come: a network share, a removable drive, a folder that cannot be found, or one whose watch failed. Nothing runs while nothing arrives and the window is in the background, and no file is held open. In the web app, when the pack file of the game shown is replaced by another version, a quiet note says so, with **Load it** (which keeps the map, location, page and found marks) and **Not now**; when it goes, a sentence says why and the Library opens; a pack file that arrives and cannot be read is listed under "Pack files and folders that Atlas could not read". Map images and pictures are served from the file now listed at once, while the pages and locations shown stay those loaded until **Load it**.

**One pack per id.** When two folders hold packs with the same id, one is shown: a pack that comes with the app and has no remote images first, then the maps folder, then the added locations in the order they were added, then pack files. A pack folder always wins over a pack file. Of two pack files with the same id, the one whose pack was changed last (`pack.updated` in its description) is shown, then the one made last (`exportedAt`), then the first by path. The others are listed under "Not shown" with the folder or file that won. Packs are never merged.

**Packs that come with the app.** An app whose bundled packs have remote map images (built with such packs in `ATLAS_BUNDLE_PACKS`) installs them into the maps folder at start-up, when the maps folder has no pack with that id, or replaces only their pack files when the bundled version is newer (other files are never touched; downloaded map images stay, renumbered when the new version moves a layer's edges, see "Downloading map images"). A bundled pack may come with the page data it was made from (`import/` and the manifest's `source`), so that it can be refreshed from its site like an imported pack (see "Refreshing a game that comes with the app" below); that page data is installed with it, and replaced with the pack files when the bundled version is newer. The demo world stays in the app's resources.

**Locks.** Downloads, imports, moves and the start-up move from version 0.2.0 hold an operating system lock on the pack folder's `.atlas/lock` (`File::try_lock`), so two apps or windows never write the same pack at once; the second gets a plain message. The lock is released however the app ends. The map keeps reading a pack while another app downloads into it.

**The shared settings file** holds the maps folder, the remembered locations, the pack files opened, the download settings and when an app that reads sites last started, as JSON:

```json
{
  "format": "atlas-settings",
  "version": 1,
  "mapsFolder": null,
  "locations": [
    { "path": "E:\\Maps\\My Game", "kind": "pack" },
    { "path": "D:\\More maps", "kind": "folder" }
  ],
  "packFiles": ["C:\\Users\\me\\Downloads\\Example Game.atlaspack"],
  "downloads": {
    "parallel": 2,
    "pauseMs": 250,
    "requestsPerMinute": null,
    "kilobytesPerSecond": null,
    "photos": "full",
    "photosWithMap": true
  },
  "siteReaderStartedAt": "2026-01-02T10:00:00Z"
}
```

`mapsFolder` null means the default. `siteReaderStartedAt` is written by an app with downloads at each start, before it reads the maps folder; an app without downloads keeps it as it is and never offers the folders of that maps folder for removal while it is there (see "Old folders" below). It is left out until such an app has started; an older app that rewrites the file drops it until the next start of the app with downloads, which is why the Sites folder and the working folders themselves count too. Every change reads the file again first and writes it through a `.part` file and a rename, so two apps changing different settings do not undo each other; a file that cannot be read counts as the defaults and is replaced on the next change. Progress is not in it: each app keeps progress in its own web storage.

**Pages linked to the map.** The person's links between a game's pages and its map (see "Pages linked to the map" in the [main README](../../README.md#pages-linked-to-the-map)) are kept in the maps folder as `<gameId>.guide-links.json`, beside the game's folder and not in it, so updating or rebuilding the pack never touches them. `guide_links_read` returns the file's text, or nothing when there is none (at most 8 MB; the file must say `"format": "atlas-guide-links"` and the game's id); `guide_links_write` writes it through a `.part` file and a rename, and with `keepCopy` first keeps the file as it was as `<gameId>.guide-links.<time>.json` (when some choices in it could not be read). Changing the maps folder carries the file over with the game. The browser and Android keep the same JSON in IndexedDB.

**Games under one title.** Which games are shown under one title (see "One title for several sources" in the [main README](../../README.md#one-title-for-several-sources)) is kept in the maps folder as `game-groups.json`, one file for every game. `game_groups_read` returns the file's text, or nothing when there is none (at most 4 MB; the file must say `"format": "atlas-game-groups"`); `game_groups_write` writes it through a `.part` file and a rename, and with `keepCopy` first keeps the file as it was as `game-groups.<time>.json` (when some titles in it could not be read). The web app reads the file again before each change. Changing the maps folder carries the file over. Android has no maps folder (`desktop_only`); the browser and Android keep the same JSON in IndexedDB.

**Own pages.** The person's own guide pages, sections and changes to the pack's pages (see "Editing pages" in the [main README](../../README.md#editing-pages)) are kept in the maps folder as `<gameId>.my-pages.json`, beside the game's folder and not in it, so reading the wiki again or rebuilding the pack never touches them. `own_pages_read` returns the file's text, or nothing when there is none (the file must say `"format": "atlas-own-pages"` and the game's id); `own_pages_write` writes it through a `.part` file and a rename, and with `keepCopy` first keeps the file as it was as `<gameId>.my-pages.<time>.json` (when some pages in it could not be read); `own_pages_delete` deletes it when the game is deleted with its lists. Not on Android, where the web app keeps the pages itself. Changing the maps folder carries the file over with the game. The browser and Android keep the same JSON in IndexedDB. The photos the pages show are own photos, kept as below.

**Own notes.** The person's notes on the locations of a game (see "My notes" in the [main README](../../README.md#my-notes)) are kept in the maps folder as `<gameId>.my-notes.json`, beside the game's folder and not in it. `own_notes_read` returns the file's text, or nothing when there is none (the file must say `"format": "atlas-own-notes"` and the game's id); `own_notes_write` writes it through a `.part` file and a rename, and with `keepCopy` first keeps the file as it was as `<gameId>.my-notes.<time>.json` (when some notes in it could not be read); `own_notes_delete` deletes it when the game is deleted with the person's locations, types and notes. Not on Android, where the web app keeps the notes itself. Changing the maps folder carries the file over with the game. The browser and Android keep the same JSON in IndexedDB. The photos the notes show are own photos, kept as below.

**Sites.** In a build with downloads (Atlas Importer), the person's site rules files (see `packages/importer-api/site-rules/`) are kept in a folder `Sites` beside the maps folder (`sites` on Linux), each as `<site id>.atlas-site.json` or `<reader>.reader.atlas-site.json`, at most 64 KB and 200 files. `sites_list` returns the folder, each file's text (or why it could not be read) and which files are switched on; `sites_pick` asks for a file in a native dialog and reads it, its size checked before it is read; `sites_add` keeps a file the web app has checked under the name its contents give it, through a `.part` file and a rename; `sites_remove` removes one, with its switch; `sites_switch` keeps the switches; `sites_save` asks where to save the guide to writing a file or its schema and saves it. The switches are kept in the folder as `sites.json` (`"format": "atlas-sites"`), not in the app's settings, so that an older app that rewrites its settings keeps them: `on`, the person's files switched on, each with the SHA-256 digest of the text switched on (a file changed since counts as off), and `off`, the files an importer comes with that were switched off. The shell never reads a file outside the folder by itself, and never runs anything in one: the web app checks each file, and the importers only read what it says.

**Own photos.** Photos a person adds to a step of their own list or to a location of their own are kept beside the game's folder, never in it: `<maps folder>/<gameId>.my-pictures/own.<letters and digits>.<jpg|png|webp>`, each shrunk to at most 1280 pixels wide before it is kept. The own lists and own locations files name them by id (`<gameId>:picture:own.…`) in their `pictures`, with the file `pictures/own.….<ext>`. The commands are `own_pictures_read` (the bytes of one file), `own_pictures_write` (base64; at most 8 MB a photo and 4,000 a game), `own_pictures_list`, `own_pictures_delete`, `own_pictures_delete_all` and `own_picture_pick` (the system's open dialog, PNG, JPEG or WebP; not on Android, where the web file input is used). Only names of that exact form are read or written, and the content must match the extension. A photo no own list, location, page or note names any more is deleted a little later (two minutes after a remove, or once a session a few seconds after a game opens); deleting a list, a location or the game with "Also delete my lists, guides and guide links" deletes its photos. When the maps folder changes, the photo folders move with the own files. In the browser and on Android the photos are kept in IndexedDB, as the setting `ownPicture:<gameId>:<file>` with an index `ownPictures:<gameId>`.

### Deleting maps and map images

Both actions ask first, in plain words: what goes, how many map images and roughly how large (counted from the files on disk), that a running download is stopped first, and what stays. In the Library, More names the row for what the game is (**Delete this wiki**, **Delete these maps**, **Delete this game** for one made in the app), and its sentence and the question both say that only that game goes and, for a game shown under one title, that it leaves the title and the title's other sources stay. Deleting a wiki (a game of pages made by an importer that fetches pages) also forgets what the app keeps of the wiki's site in that importer's wiki notes (see "Wikis no importer knows, and how a site is read" below): its list of pages, the pages that could not be read, the pages left out, the links and other names of its pages, its pages kept for later, the way chosen to read it and a licence confirmed for it, picked out by the site's key (`siteInfoOf`), so the importer's other wikis keep theirs. When another wiki in the Library is read from the same site, those notes stay, and the question says so. **Start this wiki again from the beginning**, in More on a wiki (not while pages are being read or a game is built again), asks first, then deletes the wiki as above, keeping the person's own pages, notes, lists and found marks and its membership of a title (a title keeps a source that is away, so the wiki shows there again once read again under the same id), and opens the steps of adding at its start address, asking how its pages are read. The result, or why nothing was deleted, is said in plain words too.

- **Delete…** (`library_delete_pack`) works whatever state the pack's download is in: unfinished, paused, stopped by a refusal or running. A running or paused download is cancelled and the shell waits until it has really stopped (its last files written and closed, the pack's lock released; at most a minute) before anything is deleted; the job, its record of an unfinished download and anything else kept for the pack id are forgotten. The pack folder is renamed to a hidden `.deleting-<id>` folder next to it, so no Atlas app lists it any more, and then removed. On Windows a file that another program holds open (a virus scanner, a file window, the other Atlas app reading it) can make the rename or the removal fail for a moment, so both are tried again for about two seconds. A folder that is still held stays hidden and is removed when an Atlas app next starts. If even the rename keeps failing, the pack's manifest is removed first (so it is not a pack any more and drops out of every list), the folder is marked with `.atlas/delete-pending`, what can go goes, and the next start removes the rest. Only packs directly inside the maps folder can be deleted, not packs that come with the app (they would be installed again at the next start) and not packs in other locations (use **Remove from list** for those, which deletes nothing). A pack that another Atlas window or app holds (its lock) is not deleted; the dialog says so.
- **Delete downloaded images…** (`library_delete_images`) removes only what a download wrote and keeps the pack, its locations, checklists and progress: every tile of every downloadable layer at the layer's own path (with its `.404` and `.part` companions), the layers' status files in `offline-tiles/`, the record of an unfinished download, and the image summaries in the manifest. Folders are removed only when they are empty afterwards; nothing is deleted recursively, and images that came with a bundled pack stay. It works for every listed pack whose folder can be written, including a game that comes with the app and was installed into the maps folder, and stops a download of the pack first in the same way. Images that stay in use are left and counted in the result.

Neither follows a symbolic link or junction out of the pack folder: a linked folder on the way to a file is skipped, and a link is removed itself, never what it points to. The start-up clean-up looks only at entries directly inside the maps folder: `.deleting-*` folders, `.importing-*` folders that an import left when the app was closed during it (when no app holds their lock), and marked folders without a manifest that no app holds.

### Two apps, one maps folder

The plain build of this repository is "Atlas" (`dev.atlas.desktop`). Another build of the same shell, with its own name and identifier and with importers (see "Building another app from the shell"), installs next to it. Both list the same maps folder and the same remembered locations, so a game added or downloaded in one shows up in the other by itself (see "Pack files that arrive, change or go" above; a game folder added by the other app shows up when its settings file changes), or after **Look again**. Progress stays per app. The app with downloads keeps each map and wiki it reads from a site as a working folder in the maps folder; the app without downloads reads every map, wiki and guide from its pack file, so it never offers such a folder for removal (see "Old folders" below).

### Old folders

The desktop app without downloads (a "reader": `library::READER`, `readsPackFilesOnly` in the web app) keeps each map, wiki and guide for a game as a pack file and unpacks none into the maps folder any more. The folders that earlier versions unpacked there are still shown, and a folder is shown before a pack file of the same game (see "One pack per id"). Nothing in them is converted. Its settings have a section **Old folders**, after the folders of games, that lists them for removal (`src/oldfolders.rs`, `library/OldFolders.tsx`, `state/oldFolders.ts`). The app with downloads and the Android app have no such section, and the commands refuse there.

- **What is listed.** Only pack folders directly inside the maps folder: never an added location (a pack folder the person added as a location of its own is left out even when it is in the maps folder), never a pack file and never a game that comes with the app (the demo, by its id). Each row shows the title, the folder, its size on disk and whether a pack file of the same game is read (the one shown, or, while the folder is shown, the pack file shown once the folder is gone, with its path). The size is counted off the async runtime, one folder after another once the list is shown ("measuring…" until then), never following a link, within 1,000,000 files and folders and 20 seconds per folder; a size stopped by a limit says "at least".
- **A working folder of an app that reads sites** (`is_working_folder`): a folder with page data kept by "Add a map" (an `import` entry, in any case), with an unfinished download (`.atlas/download-job.json`), or whose manifest names an importer or the pages it was read from (`source.importer`, `source.pages`) without having been imported from a pack file (no `.atlas/pack-file.json`, which an import writes), and any folder whose entries cannot be read. **When the maps folder holds one, or the shared settings name `siteReaderStartedAt`, or the Sites folder is there** (`site_reader_here`), the section says in one sentence that another app that reads sites uses this maps folder, and offers nothing at all.
- **Maps made here** (`is_made_here`): the manifest says `madeInApp`, and the folder was not imported from a pack file, or it is a working folder opened for editing from its pack file here (`.atlas/editing.json`, see "Maps made here as pack files"). Their folder is the map itself. They are listed apart, only when **Also list the maps made in Atlas on this computer** is ticked (it is not by default), marked "Made here, exists only here" when no pack file of the game is there, and never taken by **Remove all listed…**.
- **Removing.** **Remove…** on a row, and **Remove all listed…** (when more than one is listed), ask first in the section, naming the folders (the first five, then how many more), how many, and how much room they take as far as it is measured, and saying what becomes of each game: shown from its pack file, or no longer in the Library (for a game made here without a pack file: deleted for good). `library_remove_old_folders` lists the folders again and removes only those still listed under the same name and game id, refusing each while a download of the game runs or its files are moved; each goes with the safe delete of **Delete…** (renamed to `.deleting-<id>`, tried again for a while on Windows, finished at the next start when a file is held; see "Deleting maps and map images"), under the folder's lock. The person's own lists, locations, pages, notes, photos and guide links, kept beside the folder by the game's id, stay, and so do the found marks; the section says so. Afterwards the games are listed again, so a game whose folder went is shown from its pack file, and the game shown is opened again from there. Each removal is written to the activity log.

### From version 0.2.0

Version 0.2.0 kept downloaded map images in an overlay in its app data folder, `<app data of dev.atlas.desktop>/packs/<pack id>/` (`tiles/`, `offline-tiles/`), and unfinished jobs in `<app data>/downloads/<pack id>.json`. At start-up, every app looks in that folder explicitly (whatever its own identifier) and moves each overlay into the pack folder of the same id in the maps folder, which the bundled pack has just been installed into: files are moved one by one by renaming, or copied to a `.migrating.part` file and renamed when on another drive, status files last; the job record becomes `.atlas/download-job.json`; the old folder is removed when empty. It holds the pack's lock while it works, is safe to interrupt and continues on the next start; files already in the pack folder are kept. Overlays of packs that are not in the maps folder (for example the demo world) stay where they are. While a pack's images are being moved, the Maps dialog says so.

## Map pack files

A **map pack file** (`.atlaspack`) is one game in one file: its pack files and its map images up to a chosen level of detail, to copy to another computer or to Atlas for Android and import there, for example where the game's map site cannot be reached. Every build has it, including the plain viewer and the Android app: it copies files the app already has and never fetches anything.

**Export…** on a game in the Maps dialog opens a dialog that says what the file is for and offers the three levels of detail of map image downloads (Overview, Standard, Full detail), each with its number of map images and the file's size, worked out from the files on disk without reading any image. A detail is offered only when every downloadable layer has all the levels it needs; otherwise it is shown greyed out with the layers that are not downloaded ("Not downloaded: Surface (East Field)."). Layers whose images all come with the pack (folder tiles with no remote source) are put in whole at every detail, and the dialog says so. A game whose map images are a PMTiles archive cannot be exported, and the dialog says why (one large archive file, which a map pack file does not carry and Atlas for Android cannot read). Export is refused while a download of the game is running or paused, or its files are being moved. **Export** asks where to save, with `<pack id>-<detail>.atlaspack` as the name, shows the progress with **Cancel**, and ends with the file's path and size, the number of map images, and when the data was read from the game's pages and the images downloaded. Dates are shown in local time, with the exact time in UTC as their tooltip.

**Personal data is never in a map pack file**: no found marks, ticks, profiles, presets or settings (they are in the app's web storage, not in the pack folder), no page data or style sheets kept by "Add a map" (`import/`) and nothing from `.atlas/`. A pack's pictures (`pictures.json`, files in `pictures/`) go in only when they may be passed on: a picture marked `"shareable": false` (kept for the person's own use) is left out, file and entry both. The Export dialog's **Also save my progress beside it** (off unless ticked) writes a second file next to the map pack file, `<name>.progress.json` for `<name>.atlaspack`, after the map pack file is complete. It is exactly what **Export all profiles** writes: the progress of every game and profile, since the progress export cannot be limited to one game (the dialog says so). Import it with **Import from file…** in the Profiles dialog. If it cannot be written, the map pack file is still there and the result says which part failed.

In the app with downloads and in Atlas for Android, **Import map pack file…** opens a file dialog and reads only the file's description (`atlaspack.json`, the first entry) before anything is written. The dialog shows the game, its version and contents, the detail and number of map images, where its data came from, when its pages were read and its images downloaded, and the app that made the file and when. When a game with the same id is installed, both are shown side by side, with a sentence on which is newer: by when their data was read from the game's pages, then by pack version, then by when the file was made against the installed game's own last change (what is not recorded is never guessed; when nothing tells, the dialog says so). Importing data older than the installed game takes a deliberate second click ("Replace with the older file"). Importing a game that is in the maps folder replaces it in its own folder: found marks are kept, since progress is kept by game id, and its pack files and map images are replaced by the file's. A game that comes with the app is imported only in a version at least as new as the app's, and when the app serves it from its own files (all its map images come with it), only in a newer one; it goes into the maps folder and is shown in place of the app's, as a game refreshed from its site is. A game in an added folder is left as it is and shown from the maps folder instead. Import is refused while a download of the game runs, or its files are moved. Afterwards the game is listed and shown.

The import treats the file as untrusted. Before anything is written it checks every entry: the name must be a plain relative path (no `..`, no absolute path or drive letter, no `\`, no hidden segment such as `.atlas`), and one of the pack's JSON files (at most 64 MB each, 256 MB together, as for packs on disk), a status file (`offline-tiles/<layer>.json`, at most 1 MB), a map image at a path one of the pack's own layer templates gives (at most 16 MB) or its empty `.404` marker, or a picture that the file's `pictures.json` lists (at most 16 MB), or, from version 7, a small picture of a map that the description lists (`preview/<name>.jpg`, right after the description, a JPEG of at most 512 KB, checked and then left out of the pack folder); no symbolic links, at most 4,000,000 entries; the manifest's id must be the description's. There must be room on the disk for the unpacked files plus 64 MB. The pack is unpacked into a hidden `.importing-<id>` folder in the maps folder, under that folder's lock, with the manifest last, and renamed into place when complete; a pack it replaces is first renamed to `.deleting-<name>` and renamed back if the swap fails. A failure or **Cancel** leaves the maps folder as it was. The description is kept with the pack as `.atlas/pack-file.json` (`{ "importedAt", "fileName", "header" }`), for **Details**.

**Adding a pack file in the app without downloads.** The desktop app without downloads keeps a pack file a file: **Add a pack file…** (in More on a game, in the Library, beside **Open packs folder** in the settings, and in the touch layout's Games) copies it into the packs folder, where it is read where it lies like any pack file there (`src/packfile/add.rs`). The dialog shows what the file holds, as for an import, and says that it is copied into the packs folder and under which name, and which pack of the game is shown once it is added; when the game is there already, both are compared side by side with a sentence on which is newer, and nothing is replaced.

- The copy is written as `<name>.part` in the packs folder (never read), in chunks with its progress in bytes and **Cancel** between them, synced, then checked as an import checks a file: the description and its id, every entry's name, type and size, each entry read to its end (so its CRC is checked), and the manifest, whose id must be the description's. Only then is it renamed to its name (tried again for a while, as on Windows a file can be held for a moment). There must be room for the file plus 64 MB. A failure, a full disk, a damaged file or **Cancel** leaves nothing in the packs folder.
- **A file with the same name.** When the packs folder has a file of that name with the same size and the same description, it is the same pack file and nothing is copied. Otherwise the copy is named `<name> (2).atlaspack`, `<name> (3).atlaspack` and so on (at most 100 names; a name whose `.part` is there is skipped), and the dialog says so. A pack file in the packs folder is never replaced, renamed or deleted.
- **A pack with the same id.** It is added all the same. Which one is shown is the rule of one pack per id above: a folder of the game before any pack file, and of two pack files the one whose pack was changed last. The dialog says which before, and the result after.
- A file chosen from inside the packs folder is not copied; it is only checked, and its own things are taken in.
- The person's own lists, locations, types, pages, notes, photos, guide links and title a file carries (`mine/`) are taken in exactly as an import takes them, kept in the maps folder by the game's id.

### The format

A map pack file is a ZIP archive (with ZIP64 records when its size, offsets or number of entries need them) that holds the pack folder's contents at its root:

1. `atlaspack.json` (deflated), always the first entry, so it can be read without the rest of the file. Besides what the example below shows, it says what another app needs to show a card for the file without unpacking it: `game` (the title the game is shown under, with other games when it is grouped whether or not the file carries the group, and its `system`), `personalUse`, `source.name` (the site its pages were read from: the manifest's `source.site`, else the site its guide pages name most, else the host of its first page), `maps` (each map's `id`, `name`, `width`, `height`, `locations` and small picture), `guides` (the pack's pages as a `guide` or a `wiki`, with their number) and `cover`. See [docs/pack-file-format.md](../../docs/pack-file-format.md) for every field, and the `atlas-pack` crate (`crates/atlas-pack`) that reads them;
2. from version 7, a small picture of each map that has images in the file, `preview/<name>.jpg` (a JPEG, at most 512 pixels on its longest side and 512 KB), stored, right after the description, drawn from the map's own images in the file. A map without images, or whose images cannot be read, has none, and making one never stops an export. A file with small pictures is version 7; one without stays at the version of what else it carries. An import checks them and keeps them out of the pack folder;
3. the pack's JSON files that exist (`manifest.json`, `maps.json`, `layers.json` and the others listed under "Data packs" in the main README), deflated. `layers.json` is unchanged, so a layer keeps its remote source and an Atlas with downloads can fetch the levels left out later. In a version 2 manifest the image summary of each downloadable layer (`contents.maps[].layers[].images`) is rewritten to what the file holds (`levels`, `complete`: every level of the layer, `files`, `bytes`, `updatedAt` kept); every other field and the field order are kept, and a version 1 manifest is left as it is;
4. each downloadable layer's status file, `offline-tiles/<layer local id>.json`, rewritten to the levels in the file, with its time kept;
5. the map images of every folder layer at the layer's own `url` filled in, in any order of placeholders, with the `.404` markers of those levels, stored as they are (they are compressed already). A downloadable layer has the levels from its `minZoom` up to the detail's top level (the top level minus 2, 1 or 0, as for downloads); the map enlarges the top level it has when zoomed in further. Other folder layers are included whole. A game with no map has no map images;
6. the pictures in `pictures/` that `pictures.json` marks `shareable`, stored as they are, with `pictures.json` rewritten to list only those. A picture's copy for pages (`pageCopy`) is never in the file, and a carried picture's entry is written without it, so pages on the other device show the picture's file. A picture listed with a `remote` address keeps its entry even when its file is not there or not shareable, so an Atlas with downloads can fetch it later. Only when **Include downloaded photos** was ticked, the pictures kept for the person's own use (`shareable: false`: location photos and the pictures of guide pages that an Atlas with downloads fetched) go in too, still marked `shareable: false`; the tick box is offered only when the game has such pictures on this computer, says how many and how large, and is off until ticked. Such a file is for the person's own devices, not to pass on. **Pictures in the file** (offered when the game has pictures to carry, and only by the desktop app, as Android makes no map pack files) chooses **Full size** (first chosen each time the dialog opens: the pictures as this computer keeps them, with how many and how large) or **Smaller**: before anything is written, each picture is made at most 1,280 pixels wide and 4,096 tall, its shape kept and never enlarged, the width Atlas kept every downloaded picture at before pictures were kept at full size and the one the app makes a person's own photos, so a tall picture such as a long table stays readable. A picture with no see-through part and at least 256 pixels on one side is saved as a JPEG of quality 85, named `.jpg` in the file and in its `pictures.json` alike (unless another picture of the list has that name, when it keeps its type), with the `width` and `height` of its entry made those of the smaller picture; one with see-through parts, or a smaller one (an icon, whose edges a JPEG would blur), keeps its type; a JPEG is saved again only when it is made narrower; a GIF, a file that is not of the type its name says and a picture that would not get at least 10% smaller stay as they are. Up to four pictures are made at a time and the dialog counts them ("Making the pictures smaller: 40 of 252"); **Cancel** stops it then too. The pictures on this computer and the person's own photos (`mine/pictures/`, at most 1,280 pixels wide already) are never changed, and the file is the same version of the format as one at full size, so Atlas 0.11.0 and every older app that reads the format opens it. The activity log says how many pictures were made smaller and their bytes before and after. Importing needs nothing new: a reader takes every picture `pictures.json` lists;
7. only when **Include my lists, locations, types and photos** was ticked: `mine/my-lists.json` and `mine/my-locations.json` (the own files of the game), `mine/guide-links.json` (the links between guide pages and the map), `mine/my-pages.json` (the person's own guide pages and changes to the pack's, see "Editing pages" in the [main README](../../README.md#editing-pages)), `mine/my-notes.json` (their notes on the game's locations, see "My notes"), `mine/game-group.json` (the title the game is shown under with other games, and their ids, see "One title for several sources"), and `mine/pictures/own.….<ext>`, the own photos those files name (at most 8 MB each, 4,000 and 512 MB in all). Importing on the desktop or on Android adds them to the person's own: the photos first, then the lists, locations, links, pages and notes, and last the title. The description then says `"version": 6` and counts them in `mine` (`lists`, `locations`, `types`, `areas`, `photos`, `guideLinks`, `pages`, `sections`, `notes`, and `group`, true when the title is in it); a file without a title stays version 5 with notes or a guide page linked to one location alone, a file without notes, and without a guide page linked to one location alone (guide links version 2), stays version 4 with own pages, version 3 without them, one with own lists and locations and neither photos, links nor pages version 2, and one without anything of one's own version 1, so an older app reads every file it can.

Every entry has the time the file was made (in UTC, since ZIP times have no zone) and the permissions `0644`. Atlas reads versions 1 to 7 of the format; a file of a newer version is refused with a message that names the app and version that made it, and a file whose first entry is not a description of format `atlas-pack-file` is "not an Atlas map pack file".

`atlaspack.json`, for a made-up game:

| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `format`, `version` | `atlas-pack-file`, `1`.                                                                                                                                                                                                                                                                                             |
| `packId`, `title`   | The game, as its manifest names it.                                                                                                                                                                                                                                                                                 |

| `files`, `bytes`    | The entries after the description, and their size unpacked.                                                                                                                                                                                                                                                         |

### Maps made here as pack files

Only in the desktop app without downloads (a reader). A map made in the app from pictures (**New map from a picture…**, see `src/owngame.rs`) is made and changed in a working folder in the maps folder; once the person is done, it becomes a pack file and Atlas reads it from that file like any other (`src/madepack/`, `state/madePacks.ts`, `components/MadePackConfirm.tsx`). Every command answers with why not in the other builds.

- **Write the pack file…** is offered for a map made in the app whose folder was made on this computer or opened for editing here (`ListedPack.madeHere`): in the Library's game pane (its card and More) and on the Games screen of the touch layout. One confirmation first, which says where the file goes, which of the person's own things go in it, that it is checked before it takes its place, and that the folder is removed after. Then the map is written at full detail with every map image and the person's own things of it (`mine/`: lists, locations, types, areas, guide links, pages, notes, the title it is shown under and the photos these show, and the photos kept for their own use), as `<file>.part` beside its place, checked whole as an import checks a file (`import::check_whole`), checked to carry own things exactly when there are some, and renamed into place (tried again for a while, as on Windows a file can be held for a moment), then read back there. Only then is the working folder removed, with the delete of a pack folder (`Library::delete_folder`); the person's own files beside it in the maps folder stay. Any failure, and **Cancel** while it is written, leaves the folder as it was and says why. When another app that reads sites uses this maps folder (`site_reader_here`), the file is written and the folder kept, and the message says why.
- **Where it goes.** Over the pack file the map was opened from (below) when that file is still there; else over the file this computer wrote of it last, when that file is still the one it wrote (same `exportedAt`); else a new file in the packs folder named `<Game title>.atlaspack`, made safe for Windows and at a free name as the keeper of packs names its files. A file there whose `pack.updated`, then `exportedAt`, is later than the version opened is never written over without asking: the confirmation says so and offers **Replace** or **Cancel**. The file there is looked at again just before the rename, so a file that arrived meanwhile is not written over either.
- **Open for editing…** is offered for a map read from a pack file whose manifest says `madeInApp` (the Library learns it from the manifest it checks when it opens the file). It unpacks the file into a working folder in the maps folder with the import's code and checks, and writes `.atlas/editing.json` there (`"format": "atlas-editing"`: the file's path, its `pack.updated` and `exportedAt`, when it was opened). A folder of a game is shown before any pack file of it, so the map is read from the folder and changed like any map made here, and the Library says in one line that it is open for editing and that **Write the pack file** finishes it. **Close without writing…** removes the folder after one confirmation and leaves the pack file as it was; it is refused when the pack file is not there any more, since the folder is then the only copy. A pack file not made in the app is never opened for editing.
- **The maker's own things on another computer.** A pack file of a map made in the app that carries `mine/` and is read where it lies offers them in one line ("This pack file carries 42 locations and 2 lists made with the map.") with one button, **Add them to yours**, in the game pane and in the note that another version of the file arrived; they are never taken by themselves. They are read with the import's limits and checks (`import::read_mine`) and added through the same merge as an imported pack file's own things. Whether they were added or not wanted is remembered per version of the file (`exportedAt`), and they are never offered on the computer that wrote that very file. Opening a file for editing adds those this computer does not have yet.
- **What this computer remembers** is in the app's data folder, `made-packs.json` (`"format": "atlas-made-packs"`): each pack file it wrote (game id, `exportedAt`, path) and each version whose own things were added or not wanted. It and `editing.json` are read as untrusted: at most 1 MB and 64 KB, at most 1,000 entries of each list, every field checked, a path used only when it is absolute, names a `.atlaspack` file outside the maps folder that is a file and not a link, and whose description names the same game. A file that cannot be used counts as empty.
- **Commands**: `made_pack_plan`, `made_pack_write` (with `replaceNewer`), `made_pack_open_plan`, `made_pack_open`, `made_pack_close`, `made_pack_mine_offer`, `made_pack_mine_take`, `made_pack_mine_choose`. Writing and opening are pack file jobs: `packfile_progress` says how far they are and `packfile_cancel` stops them.
- **Tests**: `src-tauri/src/madepack/tests.rs` (a made map written with its own things, written back over the file it was opened from, a newer file refused until Replace, a file that fails its check and a cancel leaving the folder untouched, opening for editing and closing without writing, a pack file not made in the app, the records read as untrusted, and the maker's own things offered once on another computer and never on the one that wrote the file), `apps/web/src/state/madePacks.test.ts` and `apps/web/e2e/madePacks.spec.ts`.

## Guidebooks

A **guidebook** is a published guide the person has as one file, a PDF or a CBZ (a ZIP of pictures of pages). One game's guidebooks are in a pack file of their own, a pack of guidebooks (version 8 of the format, see "Guidebooks" in `docs/pack-file-format.md`), so a large pack of maps is never written again to add one. Any other pack stays at version 7.

**Where they show.** A pack of guidebooks is read where it lies, in the packs folder or a folder of games, like any pack file; Atlas for Android imports it as it imports any pack file, and reads its guidebooks from the folder it unpacks. Its guidebooks show with the game whose title is the pack's game title (compared without regard to case, space and punctuation, as `--show-game` compares them), with the games the person put under one title with it (`game-groups.json`), and in Guides of each of those games: a list on the landing page with each guidebook's title and what it is ("PDF, 212 pages, 148 MB"), and in the Library a **Guidebooks** card in the game's pane. A pack of guidebooks joined to a game by its title is not listed apart. One that joins no game is a game of its own in the Library (its type is **Guidebooks**), which opens on its guidebooks. A game whose only pages are guidebooks opens Guides on their list, with a search of their text.

**The reader.** Pressing a guidebook opens it over the whole window: page by page or scrolling, zoom with the buttons, Ctrl and the wheel, Ctrl and + or −, or two fingers, **Fit width** and **Fit page**, a page to go to, **Contents** (the PDF's own outline; a CBZ has none), **Back** to the page before a jump (a link, the contents, a page typed, a page found), and **Find**. Esc closes it; the Android app's Back goes back to the page before a jump, then closes it. The page each guidebook was left at, and page by page or scrolling, are remembered on this device. It is in every layout (the standard one with a mouse or with fingers, and the classic one, from the Library), in both themes.

- PDF pages are drawn with pdf.js (`pdfjs-dist` 4.10.38, Apache-2.0), bundled with the app; its worker is a module worker of the app's own (`apps/web/src/guidebook/pdfWorker.ts`), so the Content Security Policy needs no change. pdf.js runs with scripting off (`isEvalSupported: false`, no XFA, and the scripting sandbox never loaded), so a PDF runs no script. A link to a web page in a PDF is an ordinary link the app's guard opens in the system browser; a link to a page of the guidebook goes there. Fonts a PDF does not hold, and the character maps of some East Asian text, are not bundled, so such text may show in a plain font.
- CBZ pages are its pictures (JPEG, PNG, WebP, GIF, AVIF), in the natural order of their names (`p2` before `p10`), each read when it is shown and inflated in the page when it is deflated. At most 20,000 pictures, each at most 64 MB, and a central directory of at most 16 MB.
- The file is never read whole: the web app reads it in parts through the pack protocol's range requests, each answer checked to be the part asked for, of the file's size. A damaged file, or one that cannot be read, shows a sentence in the reader.

**Search.** **Find** lists the pages that have every word typed, goes to the next and previous one, and marks the words on a PDF page where its text says they are. Guides' search and the map's search show the pages of the game's guidebooks that have the words, beside guides and locations; pressing one opens the reader there. The text of a guidebook's pages comes from its text file in the pack when it has one; otherwise, for a PDF, from the PDF's own text, read in the web app the first time it is opened and kept on this device (IndexedDB), so it is read once. A CBZ without a text file, and a PDF of pictures of pages, have nothing to search: Atlas reads no text out of pictures.

**Add a guidebook… (desktop only).** In Guides (and its Library card), **Add a guidebook…** asks for a PDF or CBZ file in a native dialog (`guidebook_pick`), which the shell checks (its type by name and first bytes, its size, its pages) and serves to the web app at a one-time address of the pack protocol while it is picked. A dialog asks for its title, the file's name offered. For a PDF, the web app then reads its pages and the text of each with pdf.js, showing how far it is; the shell (`guidebook_add`) writes the game's pack of guidebooks, `guidebooks-<game id>`, in the packs folder: a new file named `<Game title> guidebooks.atlaspack` through a `.part` file, or the pack Atlas wrote for the game before, written again with the new guidebook after its others. The guidebook's file is copied into the pack as it is; the picked file is never changed. A pack of maps is never touched. **Cancel** forgets the picked file (`guidebook_forget_picked`). Atlas for Android adds no guidebooks.

**Remove this guidebook…** asks first, and is offered only on a pack of guidebooks Atlas wrote: its `pack.writtenBy.name` is `Atlas`. The pack is written again without it, or deleted when it was its last guidebook (`guidebook_remove`). A pack another app wrote is never changed; to drop it, delete the pack file.

A pack of guidebooks is not exported (**Export** says why): to pass guidebooks on, copy the pack file they came in. The Rust side is `src-tauri/src/guidebooks.rs` (the commands, naming and joining the packs Atlas writes) and the `atlas-pack` crate (`write_guidebook_pack`, `rewrite_guidebook_pack`, counting pages); import and reading in place take the guidebooks' entries only stored and of their listed size. The web side is `apps/web/src/state/guidebooks.ts`, `state/guidebookData.ts`, `state/guidebookTexts.ts` and `apps/web/src/guidebook/`.

**Tests**: the crate's `guidebook_tests.rs` (writing and reading back, counting the pages of a PDF, its object streams too, and of a CBZ, adding and removing, every refusal), the shell's `src-tauri/src/guidebooks/tests.rs` (listing and serving in parts, a deflated or wrongly sized guidebook refused, an Android-style import, Add and Remove, another app's pack never changed, the picked file served), `apps/web/src/state/guidebookData.test.ts`, `apps/web/src/guidebook/*.test.ts`, and the browser test `apps/web/e2e/guidebooks.spec.ts` (opening from Guides, pages, zoom, contents, search in the reader, in Guides and in the map's search, a CBZ, a pack of a game not here, Add and Remove). Every PDF and CBZ in them is made by the test.

## Magazines

A **magazine** comes from another app that keeps the person's magazines: per magazine title, a pack file of its issues (`magazines-<name>`, version 10 of the format, see "Magazines" in `docs/pack-file-format.md`), each issue a PDF or a CBZ with the text of its pages, a small cover picture and the games it covers with their pages. That app writes it with the crate's `write_magazine_pack`; Atlas only reads it, never changes or exports it, never reads a CBR file and never reads text out of pictures. Atlas 0.25 to 0.27 list such a file as unreadable, made in a newer format.

**Where they show.** A pack of magazines is no game: it is not in the list of games. **Magazines** (in the Library, under the list of games; in Games on Android and in a browser) opens the shelf over the whole window: every magazine title with the cover of its newest issue, then a title's issues newest first with their covers, date and pages. Esc and the Android app's Back go from a title's issues to every title, then close it. The shelf is with the list of games because magazines are of no one game, as the list of games is; Guides is the shown game's. An issue opens in the guidebook reader (same zoom, page by page or scrolling, remembered page, Find), its **Contents** the games it covers with their pages, then the PDF's own contents.

**With a game.** Guides (under the game's guidebooks) and the game's Library pane list **In magazines**: each issue that covers the game, newest first, with the pages about it ("pages 12–15"), opening the reader at the first of them. An issue's game is matched by its `gameId` when a game here has that id (and the games under one title with it), else by title, compared as guidebooks join their game, and by system when both name one. Guides' search and the map's search show the pages about the game in those issues that have the words, from the text in the pack.

The web side is `apps/web/src/state/magazines.ts`, `state/magazineData.ts` and `apps/web/src/guidebook/Magazines.tsx`; the shell lists the pack (`magazines` in the listing) and serves and imports its issues, text and covers as it does guidebooks. **Tests**: the crate's `magazine_tests.rs`, the shell's `src-tauri/src/guidebooks/magazine_tests.rs`, `apps/web/src/state/magazineData.test.ts` and the browser test `apps/web/e2e/magazines.spec.ts`, whose made-up magazines (`e2e/magazineFiles.ts`) are drawn by the test.

## Keeping packs up to date in a folder

Only in a build with downloads (Atlas Importer). The setting **Keep packs for Game Repo up to date** in Settings is for Game Repo, another app, which reads pack files from its `Maps and Guides` folder: with it on, the app keeps a pack file of each map and wiki read from a site on this computer, each map made in the app here and each map Map Maker made, in Game Repo's `Maps and Guides` folder (or one folder the person chooses), and writes it again when the game changes. The code is in `src-tauri/src/keep/`.

- **Which games.** The game folders in the maps folder that were not imported from a pack file (`.atlas/pack-file.json`), each by where it came from (`keep::sort`, in this order):
  - **Read from a site on this computer**: page data (`import/`), or a manifest that names an importer or pages. Its pack never carries the person's own things, whatever its manifest says.
  - **Made in the app here**: the manifest says `madeInApp`. Its pack carries the person's own things of it (`mine/`: their lists, locations, types and areas, guide links, pages, notes, the title it is shown under and the photos these show), as the export's "your own things" does.
  - **Made by Map Maker**: the manifest names `Atlas Map Maker` as its writer (`writtenBy.name`), the same mark Map Maker itself goes by before it replaces a folder. Its pack carries no own things, and its file's name names no site.

  The others are listed with why they are left out: a game that comes with the app, a game whose other folder is shown instead, a game imported from a pack file (a map opened for editing too: its pack file is the one to keep), a game that is none of the three, and a game whose map images are one archive file. Pack files and the folders the person added are not listed.

- **The folder.** By default, Game Repo's own `Maps and Guides` folder in the library Game Repo has open now, so the two apps meet without a folder being chosen; the packs folder only when Game Repo is not on this computer. The person may choose another (**Choose folder…**, in the system's folder dialog, so the page never names a path); the switch turns it on in the folder shown, with "Default: Game Repo's Maps and Guides folder" or "Default: the packs folder" beside its path while none is chosen (`folderDefaultFrom` in the status, `gameRepo` or `packsFolder`).
  - **Finding Game Repo** (`keep/gamerepo.rs`). Its settings file, `config.json` in `%APPDATA%\io.github.drflgd.gamerepo` on Windows (`%USERPROFILE%\AppData\Roaming` when `APPDATA` is not set), `~/Library/Application Support/io.github.drflgd.gamerepo` on macOS and `$XDG_CONFIG_HOME/io.github.drflgd.gamerepo` elsewhere (`~/.config` when that is not set), is read fresh each time the default folder is asked for, so a library Game Repo switches to is followed. It is read as untrusted: no file, one that cannot be read, one larger than 1 MB or one that is not a JSON object means Game Repo is not on this computer. Only its `library` is looked at: a full path (text, not empty, absolute, no `..`, at most 4,096 characters, no NUL) gives `<library>/Maps and Guides`; none (missing or `null`) gives `Game Repo/Maps and Guides` in the home folder (`USERPROFILE` on Windows, `HOME` elsewhere), as Game Repo itself does. A `library` that is anything else means Game Repo is here but its library cannot be used: packs go into the packs folder, and the activity log says why once.
  - **Missing folders.** Game Repo's library folder that is missing (a drive or a network share that is not connected) is never made, and packs never go into the packs folder instead: the run writes nothing and says why, as for a missing folder chosen, and the packs are written once the library is there again. In a library folder that is there, `Maps and Guides` is made when missing, as Game Repo makes it when its page first opens; the packs folder as the default is made when missing too.
  - **Chosen and default.** A folder chosen stays as chosen, whatever Game Repo has open and wherever the packs folder is. The default folder chosen in the dialog (Game Repo's `Maps and Guides` folder, or the packs folder when that is the default) counts as the default, and so does a folder chosen that is the default at a start, so it follows Game Repo's library or the packs folder from then on. While Game Repo is on this computer, the packs folder chosen in the dialog is kept as a folder chosen, and follows a change of the packs folder; while the packs folder is the default, a change of it is followed by itself, so new packs are written into the new one.
  - **A change of folder.** The record of the packs written is kept for one folder; when the folder changes (another chosen, or the default moving, such as from the packs folder to Game Repo's at the first start after Game Repo arrives, or to another library Game Repo opened), it keeps the packs whose file is in the new folder as it was written (the same `exportedAt`, as after a move of the packs folder), so a pack is known by its id wherever its file lies and is not written again as a new one, and it drops the others, so a pack whose file stayed in the old folder is not taken for one the person removed and is written into the new folder. The files in the old folder are left where they are, never moved or deleted.
  - Refused: the maps folder, a folder inside it or around it, and a pack folder (one with a `manifest.json`). **Open folder** shows it in the file manager.
- **When.** **Write all packs now**; by itself once a change to a game is finished; and a check of every game 15 seconds after each start, then daily or weekly as the person picks (**Check the folder**). A change is a page saved by a session or an update, a download of map images or photos that starts or ends, images saved from its map page, its downloaded images deleted, a pack file imported over it, the titles games are shown under, or another maps folder; for a map made in the app, also a map or level added, the map renamed, a map deleted, and the person's own lists, locations, guide links, pages, notes or photos of it saved or deleted. It counts as finished once nothing touched the game for 30 seconds and nothing still works on it: no download of it is queued, running or paused, its files are not being moved, its map page is not saving images, and no session is reading pages (the import window is open, or a page was fetched in the last 30 seconds). So one session gives one write, not one per page. The shell sees all this itself: its commands tell the keeper, and it looks at the downloads, the import window and the map page every 2 seconds. The web app takes no part in it.
- **What changed** is told by a fingerprint taken from the folder's listings alone, never by opening an image (`keep/fingerprint.rs`): every file of the game folder (not in `.atlas/` or `import/`, no name beginning with a dot, no `.part` file, never through a link) with its path, length and modified time, folded into a 64-bit FNV-1a hash that does not depend on the order of the listing, with the title the game is shown under. For a map made in the app, the person's own files beside its folder count the same way: `<id>.my-lists.json`, `<id>.my-locations.json`, `<id>.guide-links.json`, `<id>.my-pages.json`, `<id>.my-notes.json` and every file in `<id>.my-pictures/`, never through a link. A download's images change neither the manifest's `updated` nor, until a level is complete, any status file, so `updated` alone would miss them.
- **The look into the folder** (`keep/folder.rs`). The whole folder and its sub-folders, at most 8 folders down, 200,000 files and folders and 5,000 pack files. Only files ending in `.atlaspack` (in any case) are read, and of each only its description (the first entry, at most 4 MB). Folders whose names begin with a dot, pack folders and links are not looked into, and every other file is left alone. A pack is known by the `packId` of its description wherever it lies and whatever its name. A look that a limit or a folder that could not be read cut short says so in the activity log, and then no pack is written as a new one in that run, since its file may lie in what was not read.
- **What is written where** (`keep/plan.rs`):
  - A game whose pack is not in the folder and was never written by this computer: a new file in the folder `No game yet` (made when missing), named `<Game title> - <Source>.atlaspack` from the description's `game.title` (else the pack's own title, else its id) and `source.name` (else the pack's own title when it differs from the game's; else the name is the game's title alone). A map made in the app or by Map Maker names no site, so its file is `<Game title>.atlaspack`. The name is made safe for Windows: `<>"|?*` and control characters become spaces, `:` becomes `-`, slashes become `-`, spaces are run together, it has no dot or space at its end and at most 100 characters before the extension, and `_` is added to a name Windows keeps for a device, such as `CON` or `LPT1`. A name that is taken (in any case), or whose unfinished file is there, becomes ` (2)`, ` (3)` and so on, so no file holding another pack is ever written over.
  - A copy whose `pack.updated` is earlier than this computer's: replaced where it lies, under its own name.
  - A copy whose `pack.updated` is later: left alone, and listed as newer in the folder.
  - A copy of the same change: the file this computer wrote last (its `exportedAt` is the one in the record) is written again only when the game's fingerprint changed; a file another computer wrote is written again only when the game changed on this computer after that file was made (its `exportedAt`), and is otherwise as new as this one. A copy is never replaced by one with fewer map images of the same change.
  - Several copies of one game: the one whose pack was changed last (then the one made last) is kept up to date; the others are listed as other copies and left alone.
  - A pack this computer wrote (or found in step with its own copy) that is not in the folder any more: the person removed it, so it stays removed, listed as not in the folder with **Write again**. That writes it where it lay when its folder is still there, else into `No game yet`.
  - The folder cannot be found (a drive or a network share that is not connected): nothing is written and nothing is counted as removed, and the status line says so. A run that failed as a whole is tried again every 5 minutes, so the packs are written once the folder is there again or the drive has room.
- **How a pack is written** (`keep/write.rs`). One at a time, on the keeper's own thread, never the async runtime. At full detail, with every map image on this computer (for a game whose download is not over, the images there, with only the complete levels listed in the description) and the photos downloaded for the person's own use when the game has them. With the person's own things (`mine/`) only for a map made in the app here, never for a game read from a site or made by Map Maker; the check below also checks that the file carries own things exactly when it should. It is written beside its target as `<name>.atlaspack.atlas-importer.part`, once there is room for it on the drive; then checked as an import checks a file (the description and its id, every entry's name, type and size, every entry read against its checksum, and the game in its manifest); then, when the game's fingerprint did not change and no newer copy arrived meanwhile, renamed over its target. The same rule holds on the same drive, another drive and a network share, so a pack is never half written under its name and there are never two. A rename that fails (another program holds the file open) is tried again after 0.25, 0.5, 1, 2 and 3 seconds, then given up for this run: the unfinished file is removed, the game is listed as failed with why, and it is tried again at the next check. Whatever stops a write, its unfinished file is removed.
- **While a game is busy.** A write does not hold the pack folder's lock, since a lock would make a download or a page saved into the game fail. Instead, a write stops as soon as the game becomes busy (a change to it begins, a download of it starts): its unfinished file is removed, the pack in the folder stays as it was, and the game waits until the change is finished. A pack whose game changed while it was written is not used either.
- **Unfinished files.** Only files whose names end in exactly `.atlas-importer.part` are ever removed, at each check, and only when they are older than 10 minutes, since a younger one may be another computer's write in progress. Other `.part` files are left alone. Apart from renaming its own finished file over a pack and removing its own unfinished files, the app never moves, renames or deletes anything in the folder.
- **The setting and the record** are two files in this app's own data folder on this computer, never in the shared settings and never in the chosen folder: `kept-packs.json` (`"format": "atlas-kept-packs"`: on or off, the folder, how often it is checked) and `kept-packs-record.json` (`"format": "atlas-kept-packs-record"`: the folder it is for, the last check, and for each pack where it lies, when it was written, its `exportedAt` and `pack.updated`, the game's fingerprint, its map images and its size). Each computer keeps its own. Both are read as untrusted: at most 64 KB and 8 MB, at most 5,000 packs, every field checked, entries that cannot be used dropped; a file that cannot be read counts as empty, and the activity log says so. A record of another folder starts again.
- **What the person sees.** The switch, the folder, **Write all packs now** (and **Stop** while a run is under way), how often the folder is checked, one status line, and each game with its state: up to date (when it was written and where), waiting (and why), being written, newer in the folder, not in the folder (with **Write again**), left out (and why), or failed (and why). The Library shows one line while a pack is written. Nothing asks the person anything by itself: a run that fails as a whole (the folder cannot be found, the drive is full) gives one notice, and everything else is in the list and the activity log.
- **Activity log** (area `library`): the setting changed; each pack written (the game, the file, its map images, its size and how long it took); each game left alone and why, once until that changes; each failure; a write stopped; unfinished files removed; a look cut short; a setting or record that could not be read.
- **Commands** (only in a build with downloads): `kept_packs_status`, `kept_packs_choose_folder`, `kept_packs_set`, `kept_packs_write_all`, `kept_packs_write_again`, `kept_packs_cancel`, `kept_packs_reveal`. The event `kept-packs-changed` brings each change of the state to the main window.
- **Tests**: `src-tauri/src/keep/tests.rs` (the record, the fingerprint, the look, the names, the rules, finding Game Repo's `Maps and Guides` folder from a made-up settings file, and the keeper writing made-up games into a folder: by default into Game Repo's folder (its library, or `Game Repo` in the home folder), into the packs folder without Game Repo or with a library that cannot be used, nothing made or written while Game Repo's library is missing, a folder chosen winning over the default, the default moving from the packs folder to Game Repo's with the old files left where they are, a new pack, one moved by the person, one changed, one removed and written again, a newer one, a missing folder, a busy game, a change during a write, a file held open, a map made here written with its own things while a game read from a site and a map made by Map Maker are written without, and the made map written again when its own things change), `apps/web/src/state/keptPacks.test.ts` and `apps/web/e2e/keptPacks.spec.ts`.

## Downloading map images

Only in a build with downloads (`ATLAS_ENABLE_DOWNLOADS=1`, see "Building another app from the shell"). A build without them, such as the plain Atlas app, says "Map image not installed" on such a map and offers nothing more; it shows the images a build with downloads put into the pack folder, and the Maps dialog can delete them.

A pack may ship without its map images when its `xyz` layers name a remote source (`tiles.remote` in `layers.json`: an `https` URL template and, per pyramid level, which remote zoom and tile offset it maps to). The desktop app with downloads then offers **Download map images** on the map's "not installed" notice, and a **Map images** button once some are there. The plain web build never shows either.

- **Detail**: Overview, Standard or Full, the top level minus 2, 1 or 0 (never below the lowest remote level). Each choice shows its image count, what is left to fetch, and a rough size and time from typical tile sizes and the polite pace below. Choosing more detail later fetches only the new levels.
- **Order**: the lowest remote level of every layer first, so each map is usable early; then upwards. Within a level, the middle of the map first and outwards from there: the tiles one remote tile up covers (2 × 2, its "children") are asked for together, and these groups go by their distance from the middle of the level, in proportion to its width and height; within a group the tile nearest the middle comes first, and ties go top to bottom, left to right. The order is the same every time, so a resumed job carries on where it stopped. The middle is the part of a map most likely to be on the server; the edges of a grid padded beyond the picture often are not. Levels below the lowest remote level are built from it by 2×2 downscaling (Lanczos3), with a neutral dark background where a child tile is missing; JPEG (quality 85), PNG and WebP (lossless) tiles are written in the layer's own format.
- **Where**: tiles go into the pack's own folder at the layer's own `url` filled in, for example `<maps folder>/<pack id>/tiles/<map>/<z>/<x>/<y>.jpg`, each written to a `.part` file first and renamed when complete. After each level, and when the job ends, a version 2 manifest's `contents.maps[].layers[].images` is updated (levels, complete, file count and bytes); every other field and the field order are kept, and version 1 manifests are left alone. A tile the server answers with 404 or 410 leaves an empty `<tile>.404` marker and is never asked for again.
- **Images that are not on the server**: besides 404 and 410, an object store that lets nobody list its contents answers a request for an image it does not have with HTTP 403 and a small XML error document whose code is `AccessDenied`. Atlas counts that answer as "not on the server" only when all of these hold: the status is 403; the type is `application/xml` or `text/xml`; the body, after an optional `<?xml …?>` declaration, is one `<Error>` element holding only simple text elements (`<Code>`, `<Message>`, `<RequestId>`, …) and exactly one `<Code>AccessDenied</Code>`; and the same host has already sent images of the same layer, in this download or in an earlier one (an image of the layer is on disk). Before that, the same answer is a refusal like any other and stops the job at once, so a server that refuses Atlas altogether still stops it at the first request. A 401, any other 403 (another code, a web page, plain text) and every other answer are handled as before. When a tile is not on the server, the tiles under it on the next level (same remote zoom plus one, its four children, for levels the layer lists) are marked missing too and never asked for. The level summaries in the activity log and the summary of a finished download say how many images were not on the server and how many were not asked for.
- **If the server starts refusing**: when 64 of these "access denied" answers come in a row with no image in between, the job stops as a refusal ("it may have started refusing downloads"). Above the lowest level, an honest store answers at most 6 in a row (3 children of one tile and 3 of the next, at most 6 per parallel download in the order answers arrive), and the lowest level is a few tiles across, so 64 leaves room while costing a refusing server at most 64 more requests. Markers from these answers are only written to disk with the next image or when the job ends; when the job stops this way, the markers since the last image are dropped, so those images are asked for again next time instead of being wrongly recorded as missing.
- **Status file**: one per layer at `<pack folder>/offline-tiles/<layer local id>.json`, served as `<pack URL>offline-tiles/<layer local id>.json`:

  ```json
  {
    "format": "atlas-tile-status",
    "version": 1,
    "layerId": "demo:layer:surface",
    "levels": [0, 1, 2, 3],
    "nativeMinZoom": 0,
    "nativeMaxZoom": 3,
    "complete": false,
    "updatedAt": 1767225600000
  }
  ```

  `levels` lists every complete level; `nativeMinZoom` to `nativeMaxZoom` is the unbroken run from the layer's `minZoom` (null while the lowest level is not ready), which the map passes to Leaflet as `minNativeZoom` and `maxNativeZoom` and uses in place of its tile probe. The map rereads it while a download runs, so new levels show without a restart, and a later upgrade fetches only what is missing.

- **When an update moves a layer's edges**: an import or refresh of a game (a map page, **Update from the site…**, **Rebuild**) or a newer version of a game that comes with the app may give a layer another image size, `maxZoom` or list of remote levels while its remote source (`urlTemplate`) and tile size stay the same, for example when an importer finds that a map's picture reaches further than its markers. The images already downloaded are then renumbered rather than fetched again. Each image and `.404` marker of a listed level of the old layer is the remote tile (sourceZ, x + offsetX, y + offsetY); when the new layer lists that remote zoom and the tile lies inside its image, the file moves to its new number, otherwise it is removed. The levels made by shrinking are removed and built again from the moved images, the status file is written again from what is on disk (a remote level is complete when each of its tiles is an image or a marker, and the shrunk levels when the lowest remote level is), and so is the manifest's image summary. An enlarged image is usually not complete then, so **Download map images** offers the rest and fetches only the new images. Until that download, the status file names the unbroken run of levels that have images as the range the map shows (`nativeMinZoom` to `nativeMaxZoom`, with `complete` false and only the complete levels in `levels`), so the map goes on showing the kept images, scaled down for the zooms below them, even when the new layer's lowest remote levels are ones the old layer did not list and nothing of them is downloaded yet. A map opens on the area its places take up, with a margin, when that is clearly less than its image (`placesFocus` in `@atlas/core`, in every build), so an image with wide empty borders does not open small in a corner of the view. Both the pack folder and the game's overlays (`<app data>/packs/<pack id>/`, for a game that comes with the app, which move into the pack folder at the next start) are renumbered. The files go through `.atlas/renumber/<layer local id>/` in that folder, never served, with `journal.json` recording both layouts: under the pack's lock, the images are set aside under their old numbers and the new tile paths cleared before the new pack files are written, and moved to their new numbers afterwards. When the app stops on the way, the next import of the game and the next start-up go on from the journal, finishing the move, or putting the images back when the pack files were never written; an image is never left at a wrong number, and anything lost is fetched again by the next download. When an image cannot be set aside, everything is put back and the update is refused with a plain message. A layer whose remote source or tile size changed is left as before, and a change of the layer's own tile `url` template alone builds its shrunk levels again, as before. Each step goes to the activity log (area `import`, or `library` for a newer bundled version and at start-up). The Rust side is `tiles/renumber.rs`, called from `library.rs`.
- **Resuming**: tiles already on disk are skipped. Pause, resume and cancel act at once; cancel keeps what was downloaded. A job that was stopped or interrupted, by an error or by closing the app, is recorded in `<pack folder>/.atlas/download-job.json` (`{ "packId", "detail", "stopReason" }`, plus `stopDetail` after a refusal or a web page, see below; for a bundled pack served from resources, `<app data>/downloads/<pack id>.json`) and offered again after a restart, by any Atlas app; the record is removed when the job finishes or is cancelled.
- **One download at a time**: a download started while another one runs, in the same app, waits in line ("Waiting for <game> to finish"); the panel shows the line, and a waiting download can be cancelled. The next one starts when the running one finishes, stops, is cancelled or is paused (after its requests in flight have ended); a paused download that is resumed runs at once if nothing has started meanwhile, or joins the end of the line. Across apps, the running download holds a lock on `download.lock` in the shared folder (`File::try_lock`); a download whose turn has come while another Atlas app holds it waits ("Another Atlas app is downloading") and tries again every 3 seconds. The lock is let go when the download finishes, stops, is cancelled or paused, and by the system when the app ends, however it ends. Waiting downloads are recorded like unfinished ones, so after a restart each is offered again. If the lock file cannot be opened at all, the download goes ahead and says so in the activity log.
- **Download settings**, in the panel and shared by every Atlas app through the settings file, so they pace everything this computer downloads: parallel downloads (1 to 4, default 2), the pause after each request per parallel download (100 ms to 5 s, default 250 ms), and optional caps on requests per minute (10 to 600) and on speed (50 to 50,000 KB/s), and the size location photos are kept at (`photos`, **Location photos**: **Full size**, the default, or **Smaller (1,280 pixels wide)**, see "Downloading location photos"; a value an app does not know counts as full size), and whether a map's location photos are downloaded after it is added (`photosWithMap`, **Download location photos with a map**, on by default). There is no unlimited setting; values outside the bounds are refused, and a hand-edited file is pulled back into them. The size and time estimates follow the settings. A running download follows a change at once (pause, caps and fewer parallel downloads), except that more parallel downloads start with its next level.
- **Polite by design**, whatever the settings: an honest `User-Agent: Atlas/<version>` (for example `Atlas/0.3.2`) with `Accept: image/*`, no cookies and no browser-imitating headers; network errors and 5xx answers retried up to 5 times with doubling waits (2 s up to 60 s); a 429 answer pauses every worker for its `Retry-After` (up to 15 minutes); the job stops with a plain reason on 401 or 403 (no way to bypass a refusal; the one exception is an object store's "no such image" from a server that has already sent images of the layer, above), on an HTML answer (a login or error page), when the disk refuses a write, or after 10 failures in a row (an answer over 16 MB or that is not an image counts as a failure). Remote sources must be `https`; plain `http` is accepted only for `127.0.0.1` and `localhost`, for tests.
- **When the server refuses**: on 401, 403 or a web page (or after 64 "access denied" answers in a row, which the panel also says), the panel says which image it was (layer, level, column and row, counted from 0, and whether it is at an edge of the map), shows its address to copy, how many images this download had saved before it and what the server answered (selected headers and the start of a text body), with **View log**. This is kept in the job record as `stopDetail`, so it is shown again after a restart. Nothing about the request changes: the job still stops at the first refusal and does not retry.

The Rust side is `src-tauri/src/tiles/` (`pyramid.rs` tile maths matching `pyramidLevel` in `@atlas/core`, `download.rs` the polite downloader, `downscale.rs`, `renumber.rs` images of a layer whose edges an update moves, `measure.rs` measuring an imported map's picture (see "Measuring a map's picture"), `status.rs`, `store.rs` the overlay, `images.rs` where downloaded images are, `manager.rs` jobs and progress; only `pyramid.rs`, `status.rs`, `store.rs` and `images.rs` are in a build without downloads), and `src-tauri/src/downloads.rs`, through which the maps library stops a download before deleting and finds the images to delete in either build; the web side is `apps/web/src/desktop.ts`, `state/downloads.ts`, `state/mapImages.ts` and `components/DownloadPanel.tsx`, and `features.ts` for the build flag.

## Downloading location photos

Only in a build with downloads. A pack's `pictures.json` may list pictures with a `remote` address and no file yet (see "Data packs" in the [main README](../../README.md#data-packs)). The plain app shows "Photo not downloaded" in their place and never fetches them. A build with downloads offers **Location photos…** on each game in the Maps dialog: how many photos the pack lists, how many are not on this device yet and the servers they come from, and **Download location photos**. Nothing is fetched until it is pressed, or until a map is added (below).

**With a map.** While the download settings say **Download location photos with a map** (`photosWithMap`, on unless turned off), adding a map whose locations or list entries have photos to be fetched later starts the same download for its game (`state/mapPhotos.ts` in the web app; a session of several pages starts it for each game once its pages are read). It starts only once the game's map image download is over (done, stopped or cancelled; a paused one is waited for) or when there is none, never beside it; when the person starts a download of the same game's map images while the photos are downloading, the photos are paused so the map images go first, and go on once those are over (unless the person resumed them meanwhile). It never starts a second download while one of the game's photo downloads is under way or paused, and never by itself after one of this session stopped at a refusal or a problem or was cancelled. The add dialog says so ("Its location photos are downloading now, …"). For a game added before, a location's card shows **Download the photos of this game** in its "Photo not downloaded" box, which starts the same download when pressed (also after an earlier stop: the person asks for it). A build without downloads shows neither.

The photos are fetched by the same downloader and in the same line as map images (`photos_plan`, `photos_start`, `photos_pause`, `photos_resume`, `photos_cancel`, `photos_snapshot`; the job's key is `<pack id>#photos`; `downloads_jobs` lists them with the map image jobs, each with when it ended as `finishedAt`): one at a time whatever the parallel setting, with the pause of the download settings, `User-Agent: Atlas/<version>` and nothing else, the same rules for hosts (`https`, or `http` to this computer only), redirects, retries and refusals, stopping on a refusal with the same details, and every start, stop and end in the activity log. Pause, resume and cancel act at once; a cancelled or stopped job keeps the photos it saved, and starting again fetches only those still missing. Each photo is checked to be an image, shrunk to at most 1280 pixels wide (4,096 for a picture kept at full size and for a location photo, below; decoding at most 16,384 pixels a side and 256 MB) and written to the file its entry names, in that file's format (JPEG, PNG, WebP or GIF), through a `.part` file. An SVG drawing (XML whose outermost element is `svg`, not sent as a web page) is a picture too: it is drawn once with `resvg` (MIT or Apache-2.0) at four times the size it states, its longer side between 64 and 1,024 pixels, and kept in the file's format, on white for a JPEG. A drawing of more than 4 MB is not drawn; text is drawn with the computer's fonts; nothing in a drawing is run, and a file or address it names for a picture inside it is never read. One that cannot be drawn counts as failed and the download goes on. A GIF with more than one picture in it (a GIF that moves) is kept exactly as it came, at its own size, when it is at most 24 MB, the guard of every download, and gets no copy for pages, so a page shows the file itself at the size the page gives it; a GIF with one picture only is kept as a GIF, made at most as wide as any other picture. A GIF larger than 24 MB is not downloaded, as no picture over the guard is: the download stops reading it there, and a picture of a page falls back to the copy the page shows, as below, which is kept moving when it moves and is small enough. Should a GIF that moves ever reach the app larger than the guard, it is kept as its first picture. The app serves a `.gif` file as `image/gif`. A page shows a GIF that moves still, with a **Play** button, when the computer asks for less motion. A map image that is an SVG drawing counts as failed, without stopping the download as a web page does. While the Maps dialog is open, each photo shows as soon as it is saved; one saved with the dialog closed shows when the game is opened again. They are the person's: a picture marked `"shareable": false` never goes into a map pack file.

**Pictures kept at full size.** A picture whose entry names the address the page showed it at (`shownAt`, on the same host as its `remote`) is a wiki's picture kept at full size: its `remote` is the full file. The job asks for that file in place of the copy the page showed, one request a picture as before, and keeps it up to 4,096 pixels wide; when the entry names a copy for pages (`pageCopy`), the job makes that copy from the file it got, at most twice the size the page shows it at, and writes it beside the file (a copy that cannot be made is left out, and pages show the file). When the full file is missing (404 or 410), refused (401 or 403), not a picture or larger than 24 MB, the job asks once for the copy the page showed (`shownAt`) after the usual pause, keeps it as the picture's file, and does not ask for that picture's full file again while the app runs: later jobs ask for the copy shown straight away. A refusal of that copy stops the job as any refusal does, and a web page in place of the full file stops it at once, as before. Nothing else is asked for: no other address, no retry around a refusal. When a game is built again and its `pictures.json` is saved, the files in `pictures/` that no entry names any more (by `file` or `pageCopy.file`, with their `.part` and `.404` files) are removed, so a picture listed again at full size under a new name does not leave its old file behind; a photo's copy for cards (below) stays with its photo.

**Location photos at full size.** A picture that a location or a list entry names as a photo (`photos` in `locations.json` or `checklistItems.json`) is kept at full size too while the download settings say **Location photos: Full size** (the default): up to 4,096 pixels wide, with the same 24 MB guard and one request a photo. With **Smaller (1,280 pixels wide)** it is made at most 1,280 pixels wide, as before. A photo whose entry names neither `shownAt` nor `pageCopy` gets a copy for cards: `pictures/<name>.page.<type>` beside its file (`pictures/m1.jpg` has `pictures/m1.page.jpg`), made by the job from the file it kept, at most 1,280 pixels wide, never with a request of its own, and only when the file kept is wider than that (cards then show the file). The location's card, a list entry and the cards of a Photo guide show that copy where it is there and the file otherwise; pressing a photo shows its file. A pack file never carries the copy, and **Smaller** in a pack file makes the photos themselves at most 1,280 pixels wide. Photos downloaded before stay as they are: the Library's **Location photos** card counts the photos on this computer that are exactly 1,280 pixels wide (made smaller when they were downloaded; a narrower one was kept at its own size) and, while the settings say **Full size**, offers **Download again at full size** (`photos_start_again`), which asks the site once for each of them, with those not there yet, one at a time with the pause of the download settings, and replaces each file with what comes. A refusal stops it as any refusal does, and a photo the site no longer has stays as it was. A person's own photos are never changed.

**The map's icons.** A picture that a type names (`picture` in `categories.json`, the icon of the map the pack was read from) is fetched by the same job, kept at most 256 pixels wide. A picture with a `cut` is that part of its downloaded file: the job cuts it, and cuts the other icons of the same sheet that are not here yet from the same answer, so a sheet is asked for once. A part outside the file is refused and recorded as missing. **Get this map's icons** on the game's This map's icons card (`photos_start_types`) starts the job for those pictures alone, for a game read before they were downloaded; `photos_plan` counts them (`typePictures`, `typePicturesRemaining`). A pack file leaves them out unless the person ticks **Include this map's icons** (`includeTypePictures` of `packfile_export`; `typePictures` and `typePictureBytes` of `packfile_export_options`).

## Adding maps from web pages

In a build with importers, the **Add a map** button (map icon in the top bar) asks for the address of a map page. The importer contract is in `packages/importer-api` (`src/index.ts`, with a made-up example in `demo/demo-importer.js`): an importer has an id, a title, `matches(url)`, a `pageReader` (the source text of a function that reads what it needs from the page) or `fetch` (addresses the app fetches itself, see "Pages read by fetching" below), and `convert(pageData, context)`, which turns the page data into a pack.

1. The address must be `https` (or `http` on `127.0.0.1`/`localhost`, for tests), with no user name or password, and an importer must recognise it; otherwise the dialog says so.
2. The shell opens the page in a separate, visible window titled "Add a map – <site>", with the platform's own browser engine and user agent, in a private session (`incognito`: no cookies or storage kept from or shared with anything else). Tauri's own start-up script is present in every webview, but the window has no capability, so every command it might send is refused ("not allowed by ACL"), and the pack protocol answers it with 403.
3. Every two seconds the shell evaluates the page reader in the page (`eval_with_callback`), wrapped so an exception counts as "not there yet". When it returns a value, the value is kept in the page as JSON text and the shell pulls it out in slices of one million characters, capped at 64 MB in all, and checks that it is JSON. The page is never given a way to send anything to the app; the app only pulls the reader's result out.
4. The dialog shows that it is waiting, for how long, and after 20 seconds explains that the page may be asking the person to sign in, to confirm they are a person or to wait, which they can do in that window, or cancel. The app does not click, retry, reload, hide the window or change anything about it to get past such a check. When the importer's wait (300 s unless it sets 30 to 900 s) runs out, or the person closes the window, the import ends with a plain explanation and nothing is written.
5. The page data goes to the importer's `convert` in the app's window. What it returns is checked (`checkOutcome`): its shape, the pack against the pack schema and its integrity rules, the pack id against the manifest. Packs that come with the app are refused, unless the importer refreshes them (see "Refreshing a game that comes with the app" below). The shell checks the pack id, the file names (only the pack's own JSON files), sizes and JSON again, takes the pack's lock, writes the page data (`import/<page key>.json`, listed in `import/index.json` with its address, time and map) and the pack files, the manifest last, into `<maps folder>/<pack id>/` or into the folder the imported pack already has. It refuses to replace a pack that was not imported, or that another importer made.
6. The new pack is listed, its game and the imported map are shown, and the result lists the game, the map and the counts, with **Download map images…**.

**Several addresses at once.** The address box takes several addresses: one per line, or separated by spaces or commas. They are trimmed and exact repeats are dropped; one address works exactly as above. More than 25 are refused with a plain message. Each address is checked against the importers as a single one is; when some are not recognised, the dialog lists them before anything opens and offers to add the rest, leaving those out. The app then works through the pages in the order given, one at a time, in the same import window and with the same limits as a single page (`src/state/importRun.ts` in the web app; the shell only gets the usual `import_open`, `import_poll` and `import_close` calls, so nothing about the window changes): open the page, wait for its data as above, add or refresh the map, close the window, and wait 3 seconds (`RUN_PAUSE_MS`) before opening the next. The dialog lists every address with its state: waiting, open (with the hint to look at the window when the page takes a while), added or refreshed with the map's name, not added with the reason, or not started. A page is never opened twice and never retried.

- The run goes on to the next page when a page's data does not appear within the wait, the importer refuses the data, the game comes with the app, or saving that map fails; that page is shown as not added, with the reason.
- It stops when the person closes the page window (as for a single page; pages done stay done) or closes the dialog; when they press **Stop**, after the page that is open now (or at once between pages); and when two pages in a row end without their data, since a site that asks a person to step in on every page, or refuses, would do the same for the rest. Pages not reached are shown as not started.
- At the end the dialog sums up the run ("3 maps added, 1 refreshed, 1 not added"), and the game of the last map added is shown, with its map. Map images are offered once for the run: **Download map images…** for the game shown; when maps of several games were added, the dialog says to choose another game in the top bar to download its images.

**A game's address.** An importer may also read a game's own page, the one that lists its maps (`games` in the contract: `matches`, a `pageReader`, `convert`, and `gameAddress`, the game page of one of its map pages). Pasting such an address alone opens it in the import window exactly as a map page (same window, limits, wait and stop rules; the activity log says it is opened "to read the list of the game's pages"), and its `convert` returns the game's name and its pages: each with its address, a kind (`map`, or a word of the importer's, such as its site's name for checklists or guides), a name and an optional group heading. The app checks that list (`checkGameListing`: at most 500 pages, each `http(s)` on the game page's site, each map page one the importer's `matches` accepts, no repeats) and shows it with tick boxes, maps first: each page marked **New** or **Already added (will be refreshed)**, and pages the importer does not read listed as **Not supported yet**, unticked and disabled. Everything the importer can add is ticked to start with; **Add N maps** (or **Add N pages**) runs the ticked pages as a run of several addresses, below. A game address pasted with other addresses is refused with a plain message, as is the address of a list of games.

**A site's list of games.** An importer may offer its site's list of games (`catalogue`: an address, a label, `matches`, a `pageReader` or `fetch`, and `convert`), and more lists through `catalogues`, a function that returns them: one for each site that a rules file describes, say, each with the site's name as `site` (at most 50, each address once, checked as `catalogue` is; `catalogueAt` finds the list of an address). A game page that needs a reader of its own gets it from `games.pageReaderFor`. **Add a map** then shows a button with each list's label (and pasting the list's address does the same): the app opens the list (one page), checks what `convert` returns (`checkCatalogue`: at most 2,000 games, each with the pack id it would get, a name, an address on the same site that is a game page or, for a game with one map, a map page the importer reads, and optional search words), and shows it with a search box and tick boxes, nothing ticked, marking games already in the maps folder. For the ticked games it reads each game page in turn (a game with one map needs none) and shows all their pages in one list to tick, as above. The list is kept on the device once it has been read (with the time, among the device's settings, per importer and list): the button then shows the kept list at once, without opening the site, says when it was read, and offers **Update the list**, which reads it from the site again and keeps the ticks of games still listed. Pasting the list's address always reads it from the site. A kept list is checked like a fresh one before it is shown, and is read again when it does not pass or the importer's list has another address now; it counts as no page in the 25. A list may be read by fetching (`fetch`, as below), and a list with `pastedOnly` has no button and is not kept: it is read only at an address the person pastes that its `matches` accepts, for lists of one form at many addresses (a list page for each system of a site, say), whose `address` only names them. Such a list page may list games that are each an anchor on it (`…/index.html#Name`), each game's address being the page at its anchor.

**Adding the games of a list one at a time.** With more than one game ticked in a list of games, **Add the ticked games one at a time** shows a plan before anything is read (`src/state/gameSession.ts`, `src/components/GameSession.tsx`): the games ticked, and what the list says of them before anything is fetched (`CatalogueGame.maps`, `bytes` and `system`, all optional, checked by `checkCatalogue`), added up, with the free space on the drive of the maps folder (`library_free_space`, in every build); when the sizes the list gives already need more than is free, it cannot start. It also shows the system each game added is filed under (the System tag of the Library): the game's own, else the list's (`SiteCatalogue.system`), else what the person types, never over a system the person gave the game already. When the list names one system for every game ticked, the plan fills it in as the list's, to change there. Then, for each game in turn, it reads its game page (a game with one map needs none) and adds, as a go of its own, every page of it the importer can add that is not in the maps folder yet (only maps, for an importer that reads page by page). Between two pages it waits the pause of the site's rules file (`SiteInfo.pause`), never less than the app's own, and reads one page at a time. A page fetched for an address at one of its anchors (the importer names the page without its fragment) is asked for once in the session, as is each site's `robots.txt`, not once for each game: the games of a list page that are each an anchor on it share one answer, kept only until the session ends, only when it did not refuse, and only up to 32 million characters (`src/state/anchoredPages.ts`; a go of several such addresses asks once too). A game whose address is a page at an anchor counts as in the maps folder only when that anchor, or the whole page, is. It stops at the first refusal, when the page window is closed or **Stop adding games** is pressed, and after two games in a row whose pages gave no data. A game added is shown with the game here of the same title (tidied, as the Importer's offer compares titles), only when one game here has that title or every game that has it is under one title already; two games of one session are never matched. The end lists each game, why it stopped, and the games it could not match, each opening its game in the Library to put it together by hand. What is left is kept on this device (the `gameSession` setting), and **Add a map** offers to continue it (games done are skipped, and pages already in the maps folder are not read again) or to forget it. A site read only as the person browses it cannot be added this way, and the plan says so when started.

**Jobs: imports saved to run later** (in a build with downloads, where they are listed in Downloads; `src/state/importJobs.ts`, `src/components/ImportJobs.tsx`). **Save as a job** sits beside Add in the address box (map page addresses only: a game's address or a list of games is opened, and its pages or games are saved from there), beside Add in a list of pages (the pages ticked), and in the plan of games to add one at a time (the games left, with the system). Nothing is read when a job is saved. A job keeps what it reads and how, never the pages read, among the device's settings with the Importer's others (`importJobs`, at most 100 jobs of at most 2,000 pages or games each). Downloads lists the jobs, each with what it reads and how many pages or games (and the maps and size the list gave), how it went the last time, and **Start**, **Rename…**, **Change…** (the addresses of its pages, or its games and their system) and **Remove…** (what it added stays). A job is read as the importers and the sites' rules files are when it runs. One whose site needs the person, because it is read only as they browse it or shows its pages only to a person who confirms it in the window, cannot run by itself: it says so and cannot be started. Jobs started while one runs wait their turn and run one after another, with the pause the site's rules file asks for (never less than the app's own) between the last page of one and the first of the next; a refusal, a closed window or Stop ends the queue, and the jobs left say so. A job does not start while other pages are being read.

**25 pages at a time** counts every page opened in one go: the game pages and the list of games too. Games that would not fit are left for later and named; ticks beyond the limit are taken off the last pages, with a plain message, and ticking more than fit is refused until some are unticked. The pause between pages holds across the reading of the lists and the run that follows. Pages the app fetches itself, with no window (an importer with `fetch`), are not counted against the 25: a go of them has no page limit, so every page ticked is read in one go, one at a time with the pause between requests and under the site's `robots.txt`, and the person watches the count ("12 of 9,400 done") and stops the go when they choose; when the go is stopped or the site refuses, the pages not read are kept and offered as "Read them".

**Updating games.** **Update from the site…** on a game in the Maps dialog, offered for games added from web pages with an importer of this app, reads the game's page again: the importer's `gameAddress` of any page the game was made from. It lists the game's pages as above, new maps marked **New**; pages the game was made from that the game page no longer lists are listed too. When the importer has no game page for it, or it cannot be read, the pages the game was made from are listed instead (unticked when the game page could not be read). **Update all…** first lists every such game, all ticked; it then reads their game pages one at a time with the pause between them, and lists all their pages in one list, so all the ticked pages are refreshed or added in one run with the same limits and stop rules, and one summary at the end. Nothing is read or updated unless the person asks for it.

**Pages that become checklists.** A page may become a checklist of a game that is in the maps folder rather than a map: `convert` then returns `checklistId` instead of `mapId` (exactly one of the two), and the summary's `checklist` gives its items and the rows it left out. The importer decides which pages do this, and a map page may as well bring a game's checklists with its map. The result says "Added “Name” to Game, a checklist of N items", with the rows left out until their maps are added.

**Pages read by fetching, that become guides.** Only in a build with downloads. An importer whose site offers its text to programs (an API, a feed, plain pages) may read pages without a window: instead of a `pageReader` it names, for each page, the addresses to fetch (`fetch.addresses(url)`, at most 4, each on the page's site; `games.fetch` does the same for a game's contents), and the app fetches them itself (`fetching.ts` in the contract). The shell's `import_fetch` command (main window only) asks as the app, `Atlas/<version>`, with no cookies, no sign-in and no referrer, follows at most five redirects and only on the same site, waits at most 30 s and keeps at most 8 MB of text; the web app reads the site's `robots.txt` first, once per site in a go (or in a session of games added one at a time), and never asks for an address it does not allow for `Atlas` (or `*`); it waits 2 s before each request after the first and 3 s between pages, as in any run. An answer of 401, 403, 407, 429, 451 or 503, or one with `Retry-After`, stops the whole go at once with a plain message ("…so this app stopped at once and read no more pages"), and so does a failure with `stop: true` from the importer, for a page that asks to confirm the reader is a person; nothing is tried again or around it. Every answer goes to `convert` as `{ "fetched": [{ url, finalUrl, status, contentType, text }] }`. An importer may also refuse addresses outright (`refuses(url)`, a plain reason), before anything is opened: the dialog shows the reason and adds nothing. An importer that fetches may still name pages to be opened in a window instead (`fetch.inWindow(url)`, with a `pageReader` for them that gives the same `{ "fetched": […] }`): for a site that asks its readers to confirm they are a person, which only the person can do, in the window; the app waits and never answers such a check. Those pages open one at a time and are not counted against the 25 either: a go reads the pages ticked like fetched pages, and keeps the rest when it is stopped. In a go, such pages share one window (`src/state/pageWindow.ts` in the web app): the first page opens it in front, as any page (`import_open` with `keep`); each later page of the go on the same site is loaded in that same window (`import_navigate`), which is not closed and reopened, not focused and not brought to the front, so the person can put it aside or minimize it and keep working. The window closes when the go ends, is stopped or fails, and the person closing it stops the go, as before. A page read alone, outside a go, and map pages (importers without `fetch`, and pages whose map picture is measured) still get a window of their own each, closed once read. Pages of a kept window are asked for their data every half second (`KEPT_POLL_MS`) rather than every 2 s, so a page is read as soon as it has loaded, and the pause between pages of a go read in the kept window is 1 s (`WINDOW_PAGE_PAUSE_MS`, the pace such sites ask of archiving programs: about 2 seconds a page with its loading), shorter than the 3 s of any other run (`RUN_PAUSE_MS`): it starts when a page has been read, the window moves only after it, and it is never skipped. Map pages in a window, and pages the app fetches itself, keep their pauses. The shell runs the reader in a kept window only once a page load that started after it was told to move has finished, ignores load events of the page before, and hands the data over only when the document's address is the page asked for or another page of the same site the site led to from it, never the page shown before (`Visit` in `src/imports.rs`); the web app checks that address again. A site may show the page asked for at the address of the page shown before (a second name of that page, which the page's own script moves to that page's address): once a load of the page asked for has started, the window holds another document, so a load that ends at an address of the page before counts and its data is handed over, marked `forwarded`, which the web app's check lets through. Every answer of the reader also carries the document's time origin (`performance.timeOrigin`, one value per document); the shell keeps that of the page before and never hands over data read from that document, whatever its address. When a loaded page gives no data for 8 seconds (the site's check, which only the person may answer), the window asks for the person's attention in the task bar or the dock, once per page and without taking the focus or being un-minimized, and the app's status says the page window is waiting for them; the wait (`waitSeconds`) and the rule that two pages in a row without data stop the go are unchanged. A download of a pack's photos that is under way stops while the pack's files are written and starts again after, so pages can be added while the pictures of earlier pages are still coming in.

`convert` may then return `guideId` instead of `mapId` or `checklistId` (exactly one of the three): the page became a guide of the game, usually a game with no map. The result says so and offers **Read it**, which opens the page in the Guides section. When the page was chosen from a game's contents, `context.listed` gives its title there and the heading it was under, so the importer can file it under that section. In such a contents nothing is ticked at first; a heading ticks or unticks its pages, and **From here on** ticks a page and every page after it. **Select all** and **Select none** above the list tick or untick every page of every game listed that the app can add. The same two buttons stand above every list of pages or games to tick: the Library's screen of a wiki, where they act on every page its filter shows, under every heading, open or closed, and beyond the first 200 rows of a heading; a site's list of games, where they act on the games its search shows; and the games to update. Each is disabled when it has nothing to do, and the sentence beside them says how many are shown and how many of those are ticked. Pages a go did not read (it was stopped, or the site refused) are kept, per importer, in the app's settings: **Add a map** lists them, with how many pages are left, **Read them**, which reads them all in one go, and **Forget them**; so does the end of each go. For a wiki with no game in the Library (its sessions kept no page) the button is **Forget this wiki**: after asking, it also forgets everything the app keeps of the wiki's site, as deleting a wiki does. Nothing goes on by itself: each go is started by the person. Pages a stopped go did not reach go back to the front of that list.

**The wiki screen.** A game read page by page by such an importer opens in the Library as its wiki screen: its pages under the headings of the wiki's contents, each read, not read, could not be read (with why) or left out, with a filter for each; the page chosen beside them (its text when it was read, "Changed by you" when the person changed it, **Read again**, **Edit**, which opens it in Guides with the page editor, and **Leave out**); and **Read n pages** for the pages ticked, which reads them as one go, one at a time with the pause. A heading's box ticks every page shown under it, the pages listed under the heading and those found on them, read before or not (a page read before is then read again), never a page left out; with a filter on, only the pages that filter shows. It is ticked when all of them are and in between when some are. Nothing is fetched when the screen opens.

**Wikis no importer knows, and how a site is read.** An importer may also read addresses no importer knows by their site, as a general reader (`general(url)`: true for an address it would read only that way, such as a page of any wiki on a host it has no rules for). Such an address goes to it only when no importer knows it: `findReader`, `findImporter` and `findGameImporter` in the contract try every importer that knows an address first (as a page, then a game page, then a list of games), whatever their order, and an importer that throws in `general` counts as knowing it. Nothing is read because an address was typed. An importer may say, from the address alone, what the site is (`siteInfo(url)`, checked by `siteInfoOf`): a key the app keeps the person's choices for the site under (lowercase, at most 200 characters, such as the host), the ways its pages can be read, its default first (`fetch`, "By itself": the app fetches them as above, `robots.txt` obeyed; `window`, "In a window of this app": each page opens in the page window, kept for a go, where the person answers a site's check themselves), and a notice of one or two sentences that the app shows where the site is added and on its wiki screen, such as what the site's terms say. A way the importer cannot read in is dropped (`fetch` needs `fetch`, `window` a `pageReader`); an importer that says nothing reads as before. When a site offers more than one way, or a notice, adding it first shows them and asks how to read it (**Read it**), before anything is read, and asks again each time it is added while no game read from that site is in the Library (a wiki whose sessions kept no page, or one deleted), with the way chosen before ticked and, when the app still keeps notes or pages for later of the site, **Forget what it remembers**; the choice is kept per site with the importer's wiki notes (`wikiSites:<importer id>` in the settings), shown and changed on the wiki screen (not during a go), and the app never changes it by itself. A page refused while the app fetched it stops the go as before, and the message says the person can choose to read the wiki in a window instead; nothing is tried again or around it. Whatever stopped the reading of such a site, the failure, and the end of a session or of browsing that kept no page, offer **Choose how its pages are read**, which shows the question again; nothing is read until the person goes on. The way a page was read reaches `convert` as `ImportContext.reading`. **Licences the person answers for:** a failure may ask the person for the site's licence (`askLicence: true`), for a page that states none. The app then asks which licence the site is under, with three answers: **A known licence** (one of the Creative Commons licences it offers, `CONFIRMABLE_LICENCES`), **Fill in** (the words to show, 1 to 200 characters, such as permission from the site's owner, with who gave it, the date, the `https` address of its terms and a note, all optional) or **Blank** (nothing is recorded about permission, and the pages are kept for the person's own use), with **Confirm and read** or **Not now**; the page waits, and nothing of it is kept until they answer. The answer is kept for the site (shown on its wiki screen, with **Change it** and **Forget it**; a licence kept by 0.12.0 or 0.13.0 has no type and is a known licence, as then) and given to `convert` as `ImportContext.confirmedLicence` (`SiteLicence`: `basis` absent or `confirmed`, `permission` or `none`) for every page of the site from then on, so the page is read with it; the guide's `source.licenseConfirmed` then says a known licence was confirmed by the person, and Guides says so beside the licence ("confirmed by you"), while `source.licenseBasis` says the licence was filled in (Guides shows the words, linked to the terms) or that none was recorded (Guides says "No licence recorded. Kept for personal use."). A game with such a page is marked for personal use (see the main README). **Not now** adds nothing and ends the go. The contract's demo folder has a made-up importer of this kind (`other-wikis-importer.js`). **Sections other names lead to:** the app tells `convert` it keeps a manifest's `idSections` (`ImportContext.keepsIdSections`), the section of its page another name of a page leads to (see "Data packs" in the main README); an importer writes it only then, since an app that does not say so refuses a pack with it.

**Browse and keep.** A site may also be read as the person browses it (`browse`, "As I browse"), when its importer has a `browseReader`: the reader the window runs on each page the person opens, which gives the page's data, or nothing for a page it does not keep (one that is not an article, or that shows the site's check). For a site whose terms allow no programs, it may be the only way the importer offers; then the app never fetches its pages or reads them in a go, and an update or a go that meets it says so; on its wiki screen **Start browsing** takes the place of **Read n pages**. Choosing it and pressing **Start browsing** (when the wiki is added, or on its wiki screen) opens the page in the app's window (`import_open` with `browse`), visible, in front and incognito, with no cookies shared with the app's own requests, as any page window. The shell then treats each page load the person makes as a visit of its own (`Visit::browsing` in `src/imports.rs`): it runs the reader only once that page has finished loading (or has been loading for 10 seconds: a page may never finish what it loads besides its own document, advertising say, and the reader says whether what it reads is there; a window the app moves from page to page waits 4 seconds for the same), at most once per page load, and hands its data over only when the window still shows that page; it never asks for the person's attention, and it refuses `import_navigate`: the app never opens, moves to or fetches a page itself, and the window stays on its site as before. The web app asks for the data every half second and keeps each page once per browsing (by its address without its fragment, so pages told apart by their query are each kept), and only pages its importer counts part of the site browsing started on (the same `siteInfo` key: not another language's wiki on the same host, say): converted and saved as any page (`ImportContext.reading` is `browse`), never with a pause or a go. A strip in the Library and the add dialog say "Kept: <title>" with the number of pages kept, and what happened to a page that was not kept; the pages a kept page links to are listed on the wiki screen as found, not read. Browsing ends when the person closes the window or presses **Stop browsing**; a licence the person does not confirm ends it too. **Pictures shown in the page:** an importer reading a page as the person browsed it may hand over pictures the page showed, read from the page as it loaded them (`ImportSuccess.pictureFiles`: `{ file, data }`, the bytes in base64, each a picture the pack lists, `pictures/…png`, `.jpg`, `.jpeg` or `.webp`; at most 4 MB each, 100 a page and 24 MB in all, checked by `pictureFilesOf` in the contract). The web app passes them only for a page read browsing (`SaveImport.pictures`), and the shell checks the names, that each file's bytes are of the type its name says and the same limits again, and writes them in the pack's `pictures/` before its other files; the pack lists them without a `remote` address, and the app's own picture download is not started for a page read browsing. A picture a page shows from another site cannot be read from the page, so it stays words and the importer's notice says so. The demo importer reads the pictures its test pages show this way.

**Style sheets of a wiki's pages.** An importer may have the style sheets its pages use kept with the game (`styleReader` in the contract, see `styles.ts`), so that the app can lay the wiki's fetched pages out as a browser shows them (`ImportContext.layOut`, in a build with downloads; see the root README). They are used nowhere else: they change nothing in how a page is shown, they are never loaded as a style sheet of the app, and nothing inside them is followed (no `@import`, fonts or pictures). The web app reads them back with `library_style_texts` (main window, downloads builds only), in the index's order, and puts them into its closed frame as text, with `@import` left out and every `url()` made empty. They are kept once per game, as plain text, in the game's folder: `import/styles/index.json` lists each sheet (its address, or none for a `<style>` block of a page; when it was kept; its size; how it was got, `fetch`, `window` or `browse`; and the page's mark of its text) and the sheets left out and why (`leftOut`: too large, no room, from another address the page could not hand over, on another host, not allowed by `robots.txt`, refused, not reached, or not asked for because the session stopped), and each text is a file named by the app from a hash of the text (`<32 hex digits>.css`), never by the site (`src/styles.rs`). A sheet is kept once: the same address with a changed text replaces the one kept, and the same text is stored once whatever its address. One sheet is at most 4 MB and all of a game's at most 16 MB (and 500 sheets); what does not fit is noted in the index, not kept. How they come: for a page read in the app's window (`window`, `browse`), once the page's data has been read the shell runs the importer's style reader once in that same page (`import_run_once`: only while the window still shows the document the data was read from, by its time origin, and the page cannot call it), with the marks of the sheets kept already, so the page hands over the text of a sheet not kept yet and only the address of one from another address, whose rules a page cannot give; the reader changes nothing in the page and makes no request. For a page the app fetched (`fetch`), the web app takes the page's `<style>` blocks from the page data and, once the pages of the session are read (never before), fetches the sheets the page links to (`<link rel="stylesheet">`) that are on the wiki's own host, once per game, with `import_fetch` and the rules of pages: `robots.txt` obeyed, one at a time with the pause, and a refusal, or a page in place of a sheet (such as a check that the reader is a person), stops asking for that wiki's sheets; nothing is tried again or around it. A sheet a page read in the window could not hand over is fetched the same way after a session, only in a build with downloads, only for the way `window` and only from the wiki's own host or a host its importer names (`SiteInfo.fileHosts`); for the way `browse` the app fetches nothing by itself, so such a sheet is only noted. A session that stopped before its end asks for no sheet. The shell writes them (`library_keep_styles`, main window only), and the activity log says in one line what was kept or why not, when anything was; a sheet that cannot be kept never fails a page, holds up a session beyond its pause or asks the person anything. In the Library, **What this wiki holds** says "Style sheets kept: 4, 1.2 MB in all." when there are any. Building a game again from its saved pages and **Delete downloaded images…** leave them alone, deleting the game removes them with its folder, the pack protocol never serves them (`import/`), and a map pack file never holds them. An importer without a style reader has none kept, and a game with no `import/styles/` is as before.

**Pictures: full size or as the page shows them.** Only in a build with downloads, on a wiki's screen in the Library, for a wiki whose importer can keep its pictures at full size (`picturesWithPages` in the contract): **Pictures** chooses **Full size** (the default, `DEFAULT_PICTURE_SIZE` in `state/readingWays.ts`) or **As the page shows them**, with one sentence on what it costs (a larger game folder, one request a picture either way). It is kept per site with the importer's wiki notes (`wikiSites:<importer id>`, `pictures`) and reaches `convert` as `ImportContext.pictureSize` (`full` or `shown`), for every page read and for **Build again from saved pages**, which uses the choice of the moment. The context has it only in an app that keeps a picture's `shownAt` and `pageCopy`; an importer writes them only then. With full size, a picture the page showed shrunk is listed with its full file as `remote`, the shrunk address as `shownAt` and a copy for pages; a picture the page shows at its own size, or whose shown size the page does not give, stays as before. A wiki read before keeps its pictures until it is built again, when they are listed and downloaded anew at the size chosen and the old files are removed.

**Following links.** Above **Read n pages**, and where the pages of a wiki are chosen the first time, one choice says how far a go follows the links of the pages it reads: **Only the pages ticked**; **And the pages they link to** (first chosen), which also reads the pages the ticked pages link to, but not the pages those link to; or **And every page those lead to**, which keeps following the links of every page read until no new page is found or the person stops the go. It is kept per importer in the app's settings (`wikiFollow:<importer id>`), and applies to **Read them** too; **Read again** and **Try again** read their one page only. While a go runs, the pages the importer gives as `links` of a page read are added to the end of the same go: only pages the same importer `matches` (and does not refuse), never a page left out, read before or already in the go (so a page that could not be read is not tried again in it), each once; a go has no page limit, so the bar's count ("12 of 9,400 done, 3,100 found by links") is what to watch, and Stop ends the go after the page open now. Pages found and not reached stay listed as "Found on <page>, not read". They are read like the others, one at a time with the pause; Stop, **Pause everything**, a refusal and a page that asks to confirm the reader is a person stop the whole go as before, and the pages found and not reached are not kept for later (they stay listed as found). The go's count grows as pages are found, and the strip and the summary say how many were found by links ("Reading page 12 of 40, 28 found by links"). Links are only ever followed inside a go the person started. What it shows comes from this computer: the pages the pack was made from, and notes the app keeps in its settings (never exported), per importer: `wikiContents:<importer id>` (each wiki's contents as last read, by the page key of its address: `{ address, game, readAt, pages: [{ url, title, group? }] }`), `wikiFailed:<importer id>` (pages that could not be read, by page key: `{ url, message, at }`), `wikiPageLinks:<importer id>:<page key>` (the addresses one page read links to, a record per page, so a change writes only the pages read since the last write, every 10 seconds during a go; version 0.6.1 kept them all in one record, `wikiLinks:<importer id>`, which is still read, moved to records per page and emptied) and `wikiLeftOut:<importer id>` (the page keys left out). These notes keep at most 100,000 pages each, far more than a large wiki has: the bound is only there against an importer that goes wrong. A heading of the wiki screen with thousands of pages shows them 200 at a time, with **Show … more**. A page left out is never ticked or read, by the wiki screen, a later choice of pages or the pages kept for later, until it is taken back in; a page read before is also hidden from Guides among the person's own pages (`hidden`). For the pages it links to, `convert` may return `links`: the addresses of the other pages of the same site the page links to, which the app keeps (at most 1000, on the same site, each once, without fragments; `checkOutcome(value, pageUrl)`) and offers as "Found on <page>, not read". A call that also writes other pages kept with the pack again, from their saved data (after the importer changed how it writes pages, say), may return their links too, as `writtenAgain: [{ url, links }]`: each `url` a page of the same site as the page read, its `links` kept as `links` are, at most 100,000 pages (`MAX_WRITTEN_AGAIN`), each once, without the page read; an entry out of shape is left out and the page is still added. The app records them as the links of those pages, also after "Build again from saved pages", and leaves their other notes as they are; nothing is read because of them. "Changed on the wiki" is not shown: telling would mean reading every page again.

**Refreshing a game that comes with the app.** An importer that sets `refreshesBundledGames` may refresh a game that comes with the app, from a map page, a game address or **Update from the site…**. The refreshed pack must have a newer `packVersion` than the one that comes with the app and keep every map it came with (the web app and the shell both check, and nothing is written otherwise), and the importer must keep the ids the same; it is written into the maps folder with its page data, keeping the map images already there (renumbered when the refresh moves a layer's edges, see "Downloading map images"). A game whose bundled pack has no remote images (served from the app's resources) is copied into the maps folder with its own images first. At start-up the refreshed copy is kept (and shown instead of the bundled one) while its `packVersion` is at least the bundled one's; an app whose bundled pack is newer replaces the pack files and page data as above, and keeps the images. An importer without `refreshesBundledGames` gets a plain message that the game comes with the app, as before. `IMPORTER_API_VERSION` stays 1: all of this is optional, and an importer written for 0.3.3 works unchanged.

**Pictures that come with pages.** An importer that sets `picturesWithPages` reads pages whose pictures belong to them (a wiki's pages, say). In an app built with downloads, the pictures a page lists to be fetched later are then fetched right after the page is added, and after the last page of a go of several, without the person asking again: it is the same download as "Download location photos" (one picture at a time, the pause of the download settings, `Atlas/<version>`, the same rules for hosts, redirects and refusals, every start and end in the activity log), started by the app instead of the button, and the Maps dialog shows it, pauses it and cancels it as before. Each picture shows on its page as soon as it is saved. Pages added while a game's pictures are still coming in have theirs fetched when that download is over. An importer without it is unchanged: its pictures wait for the button. An app without downloads ignores it.

**Measuring a map's picture.** Only in a build with downloads. Some sites do not say how large a map's picture is, so an importer may ask the app which tiles of one zoom of the map's image set exist (`ImportContext.pictureTiles`, optional: the context has it only when the shell downloads map images, and an importer must work without it). The importer gives the image set's address template (as a layer's `tiles.remote.urlTemplate`, with `{z}`, `{x}` and `{y}` in any order), the zoom, usually the coarsest the server has, and a start tile that is part of the picture, such as the tile the site's page opens on. The web app checks the request (`isPictureRequest`: an address the downloader allows, `https` or `http` on this computer, with no user name or password, and a start tile inside the world), and the shell's `picture_tiles` command does the rest with the downloader of "Download map images": the same HTTP client, request headers, `User-Agent`, pace settings and activity log, one attempt per tile and no retries. It asks for the start tile first; when that is not an image (a 404, a refusal, an object store's "access denied" before any image, a web page), the answer is "cannot measure" and nothing is kept. From there it asks about the eight neighbours of every tile that exists, ring by ring, never the neighbours of one that does not, and only tiles inside the world of that zoom. After an image, 404 and 410 and an object store's "no such object" (the same narrow test as for downloads) mean "not on the server"; any other answer (another 401 or 403, 429, a server error, a web page, something that is not an image) ends the measurement with no answer. It makes at most 256 requests (`PICTURE_MAX_REQUESTS`); when that is not enough, the answer says it is not complete. A measurement only starts while no download of this app or of another Atlas app on this computer is under way, and holds the computer-wide download lock while it runs, so a download started meanwhile waits for it; it can be stopped (`picture_cancel`, when an import is cancelled). The answer lists the tiles that exist and the neighbours that do not; the web app checks it (`checkPictureTiles`) before the importer gets it, and anything unexpected reaches the importer as `null`.

What a measurement learns is kept in `<app data>/measured/<key>/`, one folder per address template and zoom (`source.json` says which; `tiles/<x>/<y>` are the images found and `tiles/<x>/<y>.404` the tiles not on the server), so no tile is asked for twice: a later measurement goes on from it, and a request with `cachedOnly` answers from it alone, without any request. A rebuild of a pack (**Rebuild**) only ever gets `cachedOnly` answers. When an import is saved, the images found and the "not on the server" markers are copied into every layer of the pack whose remote source has that template and a level at that zoom, at the layer's own tile numbers and only where nothing is yet; status files are not touched, so no level counts as complete until a download records it. **Download map images** then asks for none of those tiles again, and the images on disk count as proof that the host serves this layer (as above), so a first "access denied" from an object store counts as "not on the server". The summary of the import (`summary.picture`, which an importer sets only when the context has `pictureTiles`), the dialog and the activity log say in plain words whether the picture was measured and how many map images were found, or that it could not be and the map was sized from where its places are. `IMPORTER_API_VERSION` stays 1.

**Measuring a map's picture from its page.** Only in a build with downloads, and only when the person asks for it. An importer may also offer to measure the picture from the map's own page (`pageMeasure` in the contract: an optional `matches(url)` and `step`, the source text of a function). **Add a map**, **Update from the site…** and **Update all…** (and the list of a game's pages) then show a tick box, **Measure the map picture from the page (zooms the page out)**, with a hint, when the importer of at least one of the addresses offers it; it is off every time the dialog opens and is not remembered. When it is ticked, the import window of each page is opened maximised (1600 × 1000 before that) and gets a watching script before the page's own scripts run (`src-tauri/src/pagemeasure.rs`; it shares its `fetch` and `XMLHttpRequest` wrappers with "Save map images as I browse", in `pageview/script.rs`). The script only watches: for each `GET` of the page it notes the address without its query or fragment, the status, and enough of the answer to tell an image (the first 16 bytes of a 2xx answer, read from a copy) and an object store's "access denied" document (the start of a 403 answer); it keeps no image. Once the page reader has returned the page data, the shell runs the importer's step once per poll, each time after the page's own requests have settled (none open and none for 1.5 s, or none at all for 5 s, waiting at most 10 s), at most 20 times (`PAGE_MEASURE_MAX_STEPS`) and none after 90 s (`PAGE_MEASURE_MAX_SECONDS`); after the last it waits for the page to settle once more and closes the window as usual. The step gets `{ step, presses }` and answers `{ done, pressed?, note? }`; its contract allows it to press the page's own zoom-out control at most once per run and nothing else: no panning, scrolling, typing, other clicks, navigation, forms, requests, cookies or storage. The shell itself never presses anything, makes no request and changes no request header, cookie or pace. Each step and the end go to the activity log (area `import`), with counts and never the page's data. The shell classifies what the page was answered with the downloader's rules (`image`, `missing` for 404 and 410, `denied` for an object store's "access denied" document, `error` for anything else; at most 4,000 addresses of at most 512 characters, each once) and the importer gets it as `ImportContext.pageObservations` (checked by `checkPageObservations`; never in a rebuild, and only in that import). Closing the window while it measures keeps the page data and hands over what was seen until then.

What the observations mean for a map is the importer's to decide: which addresses are map images of this map (`tileAddressReader` reads tile numbers from an address with the layer's template) and whether "access denied" counts as "not there", which only an image from the same image set in the same run can prove. To make the result last, the importer passes the tiles it worked out to `pictureTiles` as `page: { present, absent }` (usually with `cachedOnly`); the web app refuses the whole request unless every tile fits the observations (`pageTilesFit`), and the shell keeps them in the measurement's folder (`page.json`, next to `tiles/`): from then on they count as known for that template and zoom, without a request and with no image kept, a tile once seen as an image stays one, and every later answer (`cachedOnly` ones in a rebuild or an update without the tick box included) starts from all of them, so a later measurement is never smaller than the page showed. The answer counts the tiles known only from a page (`fromPage`), and the start tile need not be on the server when there are such tiles. Page tiles are not copied into the pack, since no image of them is kept. While a download is under way, `picture_tiles` with page tiles still keeps them and answers from what is known, without any request. The import's summary (`summary.picture.page`: the zoom, images, tiles not there, neighbours not seen, whether the page showed all of the picture and whether it was used) is shown and logged in plain words. `IMPORTER_API_VERSION` stays 1.

The import window's navigation stays on the site of the entered address (the same host or its subdomains, ignoring a leading `www.`, and the same scheme); new windows and downloads are refused. A window kept for a go stays on the site of the go's first page: `import_navigate` refuses a page of another site, and the web app opens such a page in a window of its own. On Windows (WebView2) only top-level navigations are checked; on Linux (WebKitGTK) frames are checked too.

One pack per game: each page becomes a map of its game's pack, so importing a second map of a game adds it to the same pack, and importing a page again replaces that map's data in place (each importer decides how, from the page data kept with the pack, which `context.savedSources` hands back). An importer that goes through many kept pages, a wiki's say, can ask for them one at a time instead: `context.savedPages(packId)` lists them without their data (`library_import_source_list`) and `context.savedSource(packId, key)` gives one page's data (`library_import_source`); both are optional, so an importer checks that they are there and uses `savedSources` otherwise. The manifest's `source` lists every page; the app reads that list without the pages' data. **Rebuild** in the Maps dialog runs `convert` again on the kept page data of the last page, read alone, without visiting the page.

## Activity log

Every Atlas desktop app on the computer writes what it does to one log file in the shared folder, next to `settings.json`:

| System  | Log file                                                              |
| ------- | --------------------------------------------------------------------- |
| Windows | `%LOCALAPPDATA%\Atlas\logs\atlas.log`                                 |
| macOS   | `~/Library/Application Support/Atlas/logs/atlas.log`                  |
| Linux   | `$XDG_DATA_HOME/atlas/logs/atlas.log` (`~/.local/share/atlas/logs/…`) |

One event per line: the time in UTC (ISO 8601, milliseconds), the app's name and version, the area (`app`, `download`, `import`, `library`, `migration`, `saves`), the level (`info`, `warn`, `error`) and a message, for example

```text
2026-11-12T09:12:03.123Z [Atlas 0.3.2] download error: Stopped: the server refused access (HTTP 403) for https://tiles.example.com/5/2/3.jpg | layer Surface (Island), level 2 (remote zoom 5), column 2 of 6, row 2 of 6 (counted from 0; not at an edge) | attempt 1 | this job had saved 0 images before it, 0 of them from tiles.example.com | headers: content-type: application/xml; via: 1.1 example-cache | body: <?xml version="1.0" encoding="UTF-8"?> <Error><Code>AccessDenied</Code><Message>Access Denied</Message></Error> | not retried
```

That is a first request refused: nothing from that server has been saved yet, so the job stops. Once the server has sent images of the layer, the same answer for an image at the edge is counted instead, and the level's summary says so:

```text
2026-11-12T09:14:10.456Z [Atlas 0.3.2] download info: Counting https://tiles.example.com/5/0/0.jpg as not on the server: the store answered "access denied" (HTTP 403 with an AccessDenied error document), as it does for images that do not exist, and it has sent images of this layer in this download. Answers like this are counted in each level's summary; 64 in a row with no image in between stop the download
2026-11-12T09:15:02.789Z [Atlas 0.3.2] download info: Level 3 (remote zoom 6) of Surface (Island) complete: 144 images, 96 saved (3.1 MB), 0 already there, 0 not on the server (404/410), 12 not on the server (the store answered "access denied", as it does for images that do not exist), 36 not asked for, because the area above them is not on the server, 0 failed | answered "access denied", for example: …
```

Line breaks and control characters in messages are replaced, so a line is always one event. When the file would pass 2 MB it is renamed to `atlas.1.log` (replacing the one before) and a new file is started. Apps append under a lock on `atlas.log.lock`, so lines from two apps never mix. If the folder cannot be written, the app carries on and writes to standard error only; every line also goes to standard error.

What is in it: the app starting (version, system, maps folder, packs and importers it comes with, and whether it has map image downloads); each download (pack, layers, detail, images planned, already there and to fetch, the host and the pace), its pauses, resumptions, cancelling, waiting in line or for another app, progress every 30 seconds or 500 images, each level completed (images saved, already there, not on the server by 404 or 410 and by a store's "access denied", not asked for because the area above them is not on the server, and failed, with a few addresses of missing images) and its totals; every answer that was not an image (the address, the attempt and what happens next), and a refusal or web page in full, as above; adding maps (the host and path of the page, not its query, the importer, waiting, timing out or closing, and the outcome with its counts or the error; for several addresses at once, how many and from which sites when the run starts, why it stopped early, and its summary; for a game page or a list of games, the site and the number of pages found by kind, or of games, and how many are added already, for example "Read the list of a game's pages from https://maps.example.com: 3 map pages (2 already added, 1 new), 1 of kind checklists, 17 of kind guides"; for updating games, how many and from which sites); viewing a map page and saving its images as you browse (the page, the totals when saving stops, why the first image at each layer's edge counts as not on the server, and the first few images that could not be saved, were not recognised or were not on the server, with their addresses and the reason); deleting a map or its downloaded images; exporting and importing map pack files (the game, the detail, the file and its size, what the file says about itself, cancelling and errors, and whether a progress export was saved beside it); the maps library (what a scan found, changes to locations and the maps folder, packs installed or updated, packs in use by another app) and moving a version 0.2.0 download; keeping packs up to date in a folder (see that section); game saves (a saves folder or file linked, each save read, by file name, and its version, world and how many places matched). Not in it: progress, the contents of files or of the pages maps were added from, anything from inside a game save beyond those, the paths of saves, and anything from web storage.

**To send it** with a question: open **Maps**, then **View activity log** (or **View log** in the download panel), choose the area and level, and **Copy all shown**; or **Open log folder** and attach `atlas.log` (and `atlas.1.log` if the problem is older). Check it first: it holds the addresses of the map images and pages, and the path of the maps folder.

The dialog reads the last 2,000 lines (at most 512 KB) through `activity_log_read`, shows them as plain text, and is not in the plain web build. The Rust side is `src-tauri/src/activity.rs`; other modules log with `activity::info(Area::Download, "…")`, `activity::warn` or `activity::error`.

## Game saves

The web app reads game saves itself (`packages/saves`, in a worker); the shell only finds and reads the files, so the Android app can do the same with its own file access. In the "Game save" dialog the person links the game's saves folder, another folder or one save file to a profile.

- **Where saves are.** For The Witcher 3, `Documents\The Witcher 3\gamesaves`, with Documents taken from the system (`document_dir`, a Known Folder on Windows), so a Documents folder moved to OneDrive or another drive is found. The dialogs for choosing a folder or a file start there.
- **What is read.** `.sav` files directly in a folder the person chose or in the game's own saves folder, or one file the person chose; never through a link (a symlink is skipped), and at most 64 MB. The game's screenshot next to a save (same name, `.png`, at most 8 MB) is shown in the dialog. Chosen folders and files are remembered in `saves.json` in the app's data folder, so the web app can never name another file.
- **What is never done.** Nothing in a saves folder is written, renamed or deleted. A save is read with the system's ordinary read access, which does not stop the game from writing or replacing it.
- **Saves the game is still writing.** A read that sees the file change under it (size or time) waits a second and reads once more; if the game is still writing, the read gives up with a plain message and the next look tries again. "Follow new saves" asks the shell every 2.5 seconds; the shell announces a save once its size and time have stayed the same for 3 seconds, and the web app reads it then.
- **Commands**: `saves_default_folder`, `saves_choose_folder`, `saves_choose_file`, `saves_list` (newest first), `saves_read` and `saves_screenshot` (raw bytes), `saves_watch`, `saves_watch_status`, `saves_unwatch`, and `saves_report`, which writes how a save was used to the activity log.
- **Activity log** (area `saves`): a folder or file linked (its name), each read (file name, size, time taken, and whether it waited for the game), following started and stopped, and from the web app the save's version, world id and how many locations matched and were newly marked, or why it could not be used. Never a path to a save (it holds the Windows user name) and nothing else from inside a save.

### The game's own map locations

A Witcher 3 save names the locations on its map by the game's own tags, with no position. Where each tag is lives in the game's files, so the shell can read them from the person's own copy of the game (`src-tauri/src/gamefiles.rs`), and the web app builds a table of every map pin of every world from them (`packages/saves`, in the save worker): name, type, position and radius. With it, a save's tags become locations with a position, and a map with no world transform is lined up automatically from every signpost of its world (then from every type of pin that never moves), when the fit passes a clear bar (at least 8 pins land on locations of their type, at least half of the smaller of pins and locations, and closer than half the matching radius on average); otherwise placing yourself from two saves stays the way. In the "Game save" dialog, "Map locations from the game" chooses the folder and reads them; a browser says this needs the desktop app.

- **Which folder.** The person chooses the game's folder in the native dialog, which starts in the folder the game is most likely in: Steam's libraries (from Steam's `libraryfolders.vdf`, also on Linux and in Steam's Flatpak), GOG Galaxy, GOG's offline installer, then the Epic Games store. The shell checks that it is the game's folder (`content\content0\bundles`, and `bin\x64\witcher3.exe` or `bin\x64_dx12\witcher3.exe`, names in any case) and remembers it in `gamefiles.json` in the app's data folder. Nothing in the registry is read or written.
- **What is read.** The header and table of contents of each `.bundle` under `content` and `dlc` (never through a link, at most 8 folders deep, tables of contents of at most 64 MB), and from those, only `.w2em` (a world's map pins), `.w2am` (the game's worlds) and `.reddlc` (a DLC's definition, which names the pin file of each world it adds to) entries, at most 64 MB each; `.w2qm` entries are counted, not read. When a path is in several bundles, a DLC wins over a patch over content, and a higher number over a lower one. Entries are unpacked with zlib (`flate2`, MIT or Apache-2.0), Snappy (`snap`, BSD-3-Clause) or LZ4 (`lz4_flex`, MIT); an entry packed with Doboz is refused with a plain message. Each must unpack to its listed size and start with `CR2W`, or it is refused and the reason is logged.
- **What is never done.** Nothing in the game folder is written, renamed or deleted, nothing is sent anywhere, and nothing from the game is in Atlas or in a pack.
- **The table.** The web app keeps it in the device's settings (never exported, never in a pack), keyed to the size and time of the game's executable, so a patch makes it stale and it is read again the next time the app opens on that game. "Forget" forgets the folder and the table.
- **Not checked on the game yet.** The bundle layout comes from public references that disagree about where the fields of a table of contents entry are; the shell reads both layouts and uses, bundle by bundle, the one whose entries make sense, and the scan line in the log says which. Which compressions the map files use, the precedence of bundles, and that a save's tags are the pins' names are to be confirmed by the first run on a real game.
- **Commands**: `game_folder_get`, `game_folder_choose`, `game_folder_forget`, `game_files_scan` (lists the map files, with counts), `game_files_read` (raw bytes of one listed file), and `game_files_report`, which writes how the table was built or used to the activity log.
- **Activity log** (area `game files`): the folder chosen (its name); one line per scan: bundles, which table of contents layout each used, entries, map files by extension, the files to read by compression, paths in several bundles, entries outside their bundle, bundles that could not be read; a line for each file that could not be unpacked, with its game path, compression and bundle name; from the web app, how the table was built (files read, CR2W versions, pin files, worlds and DLC mounters, pins per world and per type, pins with no world or position) and how a save used it (how many of its tags the table has, and per world how well the pins fit the map). Never a pin's name or position.

## Viewing a map page and saving its images as you browse

Only in a build with downloads, like "Download map images". Plain viewing shares its window, its commands and its state with saving, so a build without downloads has neither: the Maps dialog lists such a pack without **Map page…**.

A pack added from a web page records its pages in its manifest (`source.pages[].url`). In the Maps dialog, such a pack has **Map page…**, which lists each page with:

- **View map page**: opens the page in a window of the app, just to look at it. Nothing is added to the page and nothing is read from it.
- **View map page and save images as I browse**: the same window, and while the person pans and zooms the page's map by hand, the map images that their own browsing loads are kept in the pack, exactly where **Download map images** would put them. A card over Atlas's map counts what was saved, what the pack already had, and what could not be saved, with **Stop saving** and **Close the map page**. Closing the window also stops saving.
- **Open in my browser**: the system's default browser.

Only addresses recorded in that pack's manifest can be opened (`https`, or `http` on `127.0.0.1`/`localhost` for tests); the shell reads them from the manifest itself and refuses anything else. The window has the import window's limits: its own label (`map-page`), no capability (every command it might send is refused), no pack protocol, a private session, navigation kept on the site of the page, new windows and downloads refused. One map page window at a time; opening another closes the first. It is separate from the import window, so "Add a map" works as before, also while a map page is open.

**What saving does, and what it never does.** With saving on, a script is added to the page before its own scripts run (`src-tauri/src/pageview/script.rs`). It wraps `fetch` and `XMLHttpRequest` and, when a `GET` request the page made itself has been answered with status 200 and its address starts like one of the pack's remote image addresses, keeps a copy of the answer's body (`Response.clone()`, or the finished binary `XMLHttpRequest` response). The page's calls, their arguments and their answers pass through unchanged. Saving never makes a request, never asks again, never adds or changes a header or the user agent, and never clicks, scrolls, pans or zooms anything. The copies wait in the page, at most 16 MB per image and about 48 MB in all; more is noted as "too many at once". The shell takes them out from the Rust side with `eval_with_callback`, a few times a second, as it takes an import's page data, so the page still cannot send anything to the app.

**What cannot be saved.** Images a page shows with `<img>` elements or style sheets cannot be read without asking the server again, which Atlas does not do; neither can answers to `no-cors` requests, or binary data a page reads as text. The script only notes their addresses (from the page's resource timing list), and the card says plainly that some images on the page could not be saved this way and that **Download map images** can fetch them. Requests made inside web workers are not visible to the page at all; the card says when the page started a worker. Only the page's top frame is watched.

**How images are matched and written** (`src-tauri/src/pageview/capture.rs`). An address is a map image only when it is exactly an address the downloader would request: one of the pack's layers' `tiles.remote.urlTemplate`, filled in with whole numbers, for a remote level the layer lists, inside the layer's tile grid (both compared in the standard form browsers use for web addresses). A template that counts rows from the bottom (`{-y}` in place of `{y}`: row 2^z - 1 - y of the remote zoom, see `fill_template` in `src/tiles/pyramid.rs`) is matched the same way and the row counted from the top again; the downloader fills it the same way. Such a template is not measured (`ImportContext.pictureTiles` takes `{y}` only). That gives the layer and the tile, and so the file: the layer's own `url` filled in, as the downloader writes it. Everything else is ignored. The bytes must be a JPEG, PNG or WebP image whose header can be read (at most 4096 px a side). A tile already on disk that is a readable image is never replaced, so a good file is never overwritten with a smaller or broken one; a broken file at that place is replaced, and a "missing on the server" marker is removed. Files are written through a `.part` file and a rename, only inside the pack folder and never through a symbolic link. Every few seconds and when saving stops, the levels the downloader builds by shrinking are built above the saved tiles, newly complete levels are recorded in the layer's status file, and the manifest's image summary is updated, as the downloader does. A later **Download map images** then skips what was saved. Tip shown in the dialog: start zoomed out, so the whole map is saved first.

**The map's edges.** A pack's tile grid is padded around the map, so the page's own requests for images at its corners and edges often come back "not there". The script also notes those answers (the address, the status, the type, and for a 403 the first 2 KB of the body, read from a copy), and the shell records such an image as not on the server with the downloader's own marker: on a 404 or 410, or on an object store's "access denied" document (the same narrow test as above) only when the page then gets a real image of that layer from the same host (in the same look at the page or a later one), which shows the server was still serving after that answer; such answers are held in memory until then and forgotten when saving stops, so if a server starts refusing with that document, nothing after its last image is recorded, and images already on disk prove nothing here. Anything else (another 401 or 403, a server error) records nothing and counts as could not be saved; an image already on disk is never marked, an image that arrives later replaces the marker, nothing below a missing image is marked (the downloader does that), and no request is made: the card counts these as "not on the server (the map's edge)", the activity log says once per layer why they count, and levels can complete from them.

**Downloads and other apps.** Saving holds the pack folder's lock for as long as it is on, so a download, an import, a move or a delete of that pack, from this app or another Atlas app, waits until it stops (with the usual "another Atlas window or app is working on this map's files" message), and saving does not start while a download of the pack is running or paused. It only saves into a pack folder the person keeps (the maps folder or an added location).

## Atlas in the background

The desktop app without downloads (`library::READER`) can stay ready beside a game, on Windows for now (`src/background/`). Settings has a group **Atlas in the background** where the shell offers it (`DesktopInfo::background`); the app with downloads, the Android app and Atlas on other systems do not show it, and answer its commands with why not. Every setting is off until the person turns it on, so a person who changes nothing sees no change at all.

- **Keep Atlas running when its window is closed.** Closing the window hides it, and Atlas keeps running with an icon in the notification area (the tray), there whenever Atlas runs while this is on. A press on the icon shows or hides the window. Its menu has **Show Atlas** or **Hide Atlas**, **Stay above other windows** (a tick) and **Quit Atlas**, which ends the app as closing the window always did. While this is on, Settings has **Exit Atlas** at its head too (`app_exit`), which ends the app as **Quit Atlas** does.
- **Hotkey** (offered: Ctrl+Alt+M). Registered with the system (`tauri-plugin-global-shortcut`) only while its switch is on, and taken off at once when it is turned off or changed. It brings Atlas forward, and pressed while Atlas is in front puts it away: hidden while Atlas keeps running, else minimised. Another combination is set by pressing it in the field **Press the keys you want**: at least one of Ctrl, Alt, Shift or the Windows key and one other key (`src/background/hotkey.rs`). A key alone, Shift alone with a key that types or selects text, F12, and the combinations Windows keeps for itself (Ctrl+Alt+Delete, Ctrl+Shift+Esc, Ctrl+Esc, Alt+Tab, Alt+Esc, Alt+F4, Alt+Space, and the Windows key with fewer than two of Ctrl, Alt and Shift) are refused with a sentence. When the system does not take a combination (another program has it), the setting says so and the old one stays. While the person presses new keys the hotkey is paused, so pressing the one it has does not hide the window. The hotkey only shows, hides or minimises Atlas's own window; nothing here starts, presses or reads anything in another program.
- **Back where you left it.** Hiding never unloads anything, so the window comes back with the same game, map, location, zoom and panel, at the same place and size. While any of these settings is on, the window's place, size and whether it was maximised are kept from one run to the next in the app's own data folder (`window.json`, `src/background/place.rs`), read as untrusted (at most 4 KB, bounded numbers); a place whose top edge is on no screen now is not used.
- **Stay above other windows.** The window stays above other windows, such as a game in a borderless window. A game in exclusive full screen covers every window, so its help says to set the game to borderless or windowed.
- **Start Atlas when Windows starts.** An entry in the current user's list of programs started with Windows (`HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run`), named by the app's identifier (so an entry of another program that shares the app's name is never taken for it), started with `--background`, the program's path in quotes; turning it off removes the entry. No administrator rights and nothing for every user. The switch shows what the system says each time Settings is opened, and says so when the entry could not be written or another entry still starts Atlas. This uses the `auto-launch` crate directly, the one the Tauri autostart plugin is made of: the plugin writes the list of every user when Atlas runs as administrator and leaves the path without quotes, with no setting for either.

The settings are kept in the app's own data folder (`background.json`, `src/background/store.rs`), since they describe this computer and this app, not in the shared settings file every Atlas app on the computer reads. The file is read as untrusted: at most 16 KB, another format or version counts as none, and a value that cannot be used is off (a switch) or the combination offered (the hotkey). What a close, a hotkey press, a press on the tray icon and a start do in each state is decided without the system (`src/background/decide.rs`) and unit-tested on Linux; the tray, the hotkey, the entry and the window calls are in Rust (`src/background/shell.rs`), behind the app's own commands (`background_state`, `background_set`, `background_set_hotkey`, `background_pause_hotkey`). The web view gets no permission of the tray, the global shortcut plugin or the entry: no capability grants any of their commands.

**Start options from another program** (`src/receive/args.rs`, the app without downloads on every desktop; the other apps leave them out with a line each):

- `--show-pack <pack id>`: shows the game whose pack has that id (a pack id's syntax only).
- `--show-game <title>`: shows the game whose title matches: its own title, the title its pack file says it is shown under, or a title of the person's games shown under one title (`game-groups.json`). Titles are compared without regard to case, surrounding space and runs of punctuation and space, at most 200 characters (`src/background/titles.rs`). When several games match, the one shown last, else the first in the Library's order; when several sources share the title, the source used last (the web app picks, `state/showRequests.ts`).
- `--no-update-check`: Atlas does not look for an update at this start (see "Updates"); **Check for updates** in Settings still works. It counts as `--background` does when the rest of the request is left out.
- `--background`, with either of these, with a pack file path, or alone: Atlas gets ready without coming to the front and without taking the focus from the program in front. A first start makes the window hidden (while Atlas keeps running when its window is closed) or minimised (otherwise), so the hotkey or the tray brings up the game asked for; a second start leaves the window as it is. On Linux a first start never hides or minimises the window: it is shown without taking the focus (see "Atlas on Linux and the Steam Deck"). Without it, the window comes forward as it does for a pack file.

When Atlas has nothing for the pack id or title, it does nothing and says nothing to the person: one line in the activity log. The same options work on a second start, handed to the Atlas running. An unknown option is still left out with its line; an option missing its value (the next argument, never one that starts with `--`), given twice, or mixed in a way that makes no sense (`--show-pack` with `--show-game`, or either with a pack file path) leaves out what was asked to be shown or opened, with a line, and `--background` still counts when it was given, so that a request gone wrong never brings Atlas in front of a game. Nothing is run or looked up because an argument names it.

Only a real Windows window shows the tray, the hotkey over a game, the start with Windows and a start with `--background` not taking the focus; the browser tests (`apps/web/e2e/background.spec.ts`) cover the Settings group against the stand-in shell.

## Atlas on Linux and the Steam Deck

The same shell runs on Linux on 64-bit PCs (x86_64). The plain viewer is released for Linux as one AppImage, made first for the Steam Deck: in Desktop Mode it runs like any program, and in Game Mode it runs beside a game. SteamOS keeps its system read-only, so there is no deb, rpm or Flatpak of it for the Deck; an AppImage is one file the person keeps in a folder of their own (`~/Applications`) and starts, or adds to Steam.

**The build** (`.github/workflows/linux-appimage.yml`, used by `linux-release.yml`, run by hand from the Actions tab with a trial number, and by `release.yml` for a release). It builds on Ubuntu 22.04, the oldest runner GitHub offers, so nothing in the AppImage asks for a newer C library than glibc 2.35 (SteamOS has a newer one): the plain viewer without downloads (`ATLAS_ENABLE_DOWNLOADS=0`) with the demo pack, as `release.yml` builds it for Windows, and only the AppImage (`pnpm desktop:build --bundles appimage`). Tauri's AppImage bundler (linuxdeploy with its GTK plugin) copies WebKitGTK, GTK and the libraries they use into the AppImage, with WebKit's own helper programs (`WebKitWebProcess`, `WebKitNetworkProcess` and its injected bundle) and WebKitGTK's paths to them rewritten so they are found inside it; the graphics drivers (Mesa on a Steam Deck) and the C library come from the system. Before it publishes anything, the workflow runs the shell's unit tests on Linux (`ci.yml` runs them on Windows only), checks the AppImage (one program, holding no download code; WebKitGTK and its helper programs; the demo pack; no C library newer than 2.35; and, as a warning only, libmanette, through which WebKitGTK offers the Gamepad API) and starts it once on a virtual screen of 1280 by 800 with its folders in a temporary folder: it must keep running for 20 seconds, start WebKit's web process, write its first lines to the activity log and make its packs folder. A picture of that screen, the log and what WebKit's processes were are kept as the workflow artifact `linux-start-up`, and the AppImage, always named `Atlas.AppImage` so that the launch options below can name it, as the artifact `Atlas.AppImage`, with `Atlas.AppImage.sig` when the repository secret `TAURI_SIGNING_PRIVATE_KEY` signed it for updates (a release requires it; a trial signs when the secret is there). A trial then attaches the AppImage alone, never a signature or `latest.json`, to the release `linux-trial-<number>`, "Atlas for Steam Deck, trial <number>": a draft by default (the `draft` input), always a prerelease, never the repository's latest. Its notes say how to install it on a Steam Deck and what to try. To build one on a Linux computer: `pnpm desktop:build --bundles appimage` with the prerequisites above; it lands in `src-tauri/target/release/bundle/appimage/`.

**Folders.** As everywhere on Linux, and never renamed: another app on the computer puts pack files there by contract. Each name is lower case. `$XDG_DATA_HOME` is `~/.local/share` when it is not set, as on SteamOS, where `~` is `/home/deck`.

| What                 | Where on Linux                                                                                                    |
| -------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Packs folder         | `$XDG_DATA_HOME/atlas/packs` (`~/.local/share/atlas/packs`), or the folder `packsFolder` names when one is chosen |
| Maps folder          | `$XDG_DATA_HOME/atlas/maps` (`~/.local/share/atlas/maps`), or the one chosen in the Maps dialog                   |
| Shared settings file | `$XDG_DATA_HOME/atlas/settings.json` (`~/.local/share/atlas/settings.json`)                                       |
| Activity log         | `$XDG_DATA_HOME/atlas/logs/atlas.log`                                                                             |
| The app's own data   | `$XDG_DATA_HOME/dev.atlas.desktop` (`~/.local/share/dev.atlas.desktop`)                                           |

**Change packs folder…** (see "Changing the packs folder") works on Linux as on Windows: the system's folder dialog, `packsFolder` in the shared settings file as a full path, the folder watcher following the new folder. An AppImage changes none of these folders: it reads `$XDG_DATA_HOME` and `$HOME` as any program does.

**The AppImage's path for another app.** Beside `packsFolder`, the shared settings file holds `linuxAppImage` on Linux: the full path of the AppImage the plain viewer last started from, which the AppImage runtime puts in `APPIMAGE` (`src-tauri/src/linux.rs`, `appimage_to_keep`). The viewer writes it at each start from an AppImage, when it is a full path to an existing file that the launch line below can hold, and takes it out when the file it names is gone; it is absent while unknown and never written on Windows or Android, nor by the app with downloads. An older Atlas may leave it out when it writes the file, until the viewer starts again. Another app reads it to write the same launch line into a game's Steam shortcut, checking the path again as Atlas does (see "Starting Atlas with a game in Steam" in `docs/pack-file-format.md`).

**The web view's settings** (`src-tauri/src/linux.rs`). WebKitGTK's newer way of drawing, its DMA-BUF renderer (2.42 and later), leaves the window blank or white under gamescope, the compositor of Game Mode, and with some graphics drivers. So on Linux the shell sets `WEBKIT_DISABLE_DMABUF_RENDERER=1` first thing in `run()`, before any window or thread exists, unless it is set already (to anything: then it is the person's), and writes what it did to the activity log. It does not set `WEBKIT_DISABLE_COMPOSITING_MODE`, which stops WebKitGTK drawing with the graphics chip and makes moving and zooming the map slow; a person whose window stays blank can set it in Steam's launch options of Atlas: `WEBKIT_DISABLE_COMPOSITING_MODE=1 %command%`. No other variable is set.

**Game Mode.** In Game Mode (gamescope) one app shows at a time, an app cannot bring itself to the front, and global hotkeys do not reach Atlas. The window has no frame and no close button there, so on Linux every desktop app has **Exit Atlas** at the head of Settings, and the layout for fingers on a handheld has it first among the tools at the head of the rail (`apps/web/src/library/ExitAtlas.tsx`, the shell's `app_exit`, which ends the app as the tray's **Quit Atlas** does). It asks first, in a dialog the controller answers. Trial T3 tries two ways of calling Atlas there; a quick-menu panel through an unofficial add-on is not made.

- **Started with a game**, so that Steam lists it as a second window of that game, reached with the Steam button. Later another app writes this into a game's Steam shortcut; for the trial the person pastes it into the game's launch options:

  ```sh
  bash -c '"$HOME/Applications/Atlas.AppImage" --background & exec "$@"' -- %command%
  ```

  **Start Atlas with a game in Steam**, a group of Settings in the viewer on Linux (`apps/web/src/library/SteamLaunchSettings.tsx`), shows this line with **Copy** and the steps (in Steam, the game's **Properties**, then **Launch Options** under **General**). The shell builds it (`launch_line` in `src-tauri/src/linux.rs`, the one place that writes it, with unit tests; given to the web app as `DesktopInfo::steam_launch`) from the AppImage Atlas runs from: `APPIMAGE`, the AppImage file's full path, set by the AppImage runtime, used when it is a full path to an existing file. The path goes inside double quotes inside single quotes, so a path holding `'`, `"`, `$`, a backtick, `\` or a control character (a line break among them) gets no line, only a sentence saying to move the AppImage to a folder whose path has none of them. When Atlas does not run from an AppImage, the line names `$HOME/Applications/Atlas.AppImage` and a sentence says to change the path if the file is elsewhere. When the clipboard cannot be written, the line is selected and the group says "Press Ctrl+C to copy it." The app with downloads, which does not take `--background`, the Android app, Windows and a browser do not show the group. The browser tests (`apps/web/e2e/steamLaunch.spec.ts`) cover it against the stand-in shell.

  As far as is known (trial T3 checks it), Steam runs launch options with a shell and puts the game's whole command, quoted, where `%command%` stands; that command starts with Steam's `reaper SteamLaunch AppId=<the game>`. gamescope gives a window the app id of the game it belongs to from the window's `STEAM_GAME` property, from the systemd scope Steam starts the game in, or by walking up the window's process's parents to that `reaper` (`GetAppIdFromPid` in gamescope's `src/Utils/Process.cpp`). Started in front of `%command%` with `&`, Atlas would be a sibling of the reaper, not its child. So `bash` starts Atlas in the background and then replaces itself with the game's command (`exec "$@"`, the words after `--`): Atlas's parent becomes the reaper, and its window counts as the game's. Atlas starts first, so the game's window, shown later, comes up in front (gamescope shows the window of an app that was shown last). `--background` keeps Atlas from asking for the focus. When the game ends, the reaper may wait for Atlas, so the game may still count as running until **Exit Game** in the Steam menu closes both. When Atlas runs already (from its own entry), the new start hands its request over and ends, and that Atlas stays outside the game.

- **Its own entry in Steam** (**Add a Non-Steam Game to My Library**, the AppImage chosen), started by itself and switched to through the Steam button's list of running apps.

The Deck's back grips (L4, L5, R4, R5) are free for the person's own Steam Input bindings.

**Start options on Linux.** `--show-pack`, `--show-game` and `--background` (see "Atlas in the background") work as on every desktop. A second start hands them to the Atlas running over the D-Bus session bus (`tauri-plugin-single-instance`: the name `dev.atlas.desktop.SingleInstance`, the second start ends once the running Atlas took them); without a session bus each start runs on its own. On Linux `--background` never hides or minimises the window at a first start (`background::decide::OUT_OF_SIGHT_AT_START`): Game Mode has no taskbar and no tray, and only a shown window can be chosen with the Steam button, so a window out of sight could never be found again. The window is shown without taking the focus instead (`FirstWindow::Unfocused`; on Linux the window takes the focus normally once it has been drawn). A second start with `--background` leaves the window as it is; without it, Atlas shows its window and asks for the focus, which gamescope does not give: there the person switches with the Steam button.

**Moving around with a controller or the keys** (`apps/web/src/controller.ts`, on every system, with unit tests in `controller.test.ts` and browser tests in `e2e/controller.spec.ts`). In Game Mode Steam gives Atlas either a gamepad (a Gamepad template) or keys and a mouse (a template such as Web Browser or Keyboard (WASD) and Mouse); the touch screen works with the standard layout made for fingers. Its system reports a mouse (the trackpads), so the rule of the web app alone (a touch screen without a mouse) would show the version for a mouse; the setting **Controls** (Settings, under Layout: Automatic, For fingers, For a mouse; `apps/web/src/touch/controls.ts`) starts Automatic made for fingers on Linux with a touch screen (`navigator.maxTouchPoints > 0`) of 1280 by 800, changes to it at the first press of a finger anywhere else, and keeps it there for the run: the trackpads, or a touch screen Steam passes on as a mouse, never change it back. Held in both hands, the sections sit at the foot of the rail (the lower left corner), **Nearest unfound** and the card's **Mark found** and **Next nearest** in the lower right corner, dialogs at the top, above the on-screen keyboard, and every target is at least 44 px (`apps/web/src/styles/handheld.css`); the map pans with one finger and zooms with two, and pressing and holding a location marks it, as a right click does with a mouse. A finger held elsewhere opens no menu of the web view. The browser tests `apps/web/e2e/deckControls.spec.ts` cover this at 1280 by 800 with a touch screen that reports a mouse.

- The arrow keys move the focus to the nearest control in that direction: Android's way of choosing (in line before beside, then the weighted distance), among the controls that can be seen, inside a dialog, a menu or a sheet that is open. They are left as they were in a text field, on a radio button, a slider or a list of choices, in the map (Leaflet's arrow keys move it), in widgets that use them (which stop the key), on a part of the page that scrolls and has the focus, and with nothing focused after a press of the mouse or a finger (they scroll). With nothing focused otherwise, the first one focuses the section shown. When the nearest control that way is out of view and the part of the page around the focus can scroll that way, it scrolls a step first.
- Enter presses check boxes and elements that act as buttons, as well as buttons and links. Esc closes what is on top, as before (Android's Back); with nothing left to close while the map has the focus, the focus leaves the map. Page Up, Page Down, `[` and `]` turn pages where they did.
- On the map with nothing else focused, W, A, S and D move the map, `+` and `-` zoom, Enter opens the location under the crosshair, `0` shows the whole map and L the next level; Q and E switch sections anywhere. So a Steam Input layout that sends keys can do what the controller does.
- While the focus moves with keys or a controller, a wide ring shows it (`data-moving` on the root); a press of the mouse or a finger takes it off. Nothing here acts on a mouse or a finger.
- One table (`apps/web/src/input/bindings.ts`, unit-tested) holds every action with its keys, its controller buttons, its context (Map, Guides and guidebooks, Lists, Menus and dialogs, Everywhere) and its words. The handlers, the hint bar and the guide of keys and controller all read it.

**Controller.** Where the web view offers the Gamepad API (it is detected, never assumed; WebKitGTK reads controllers through libmanette, when it was built with it). On the map, with nothing else focused: the left stick moves the map (faster the further it leans), the right stick moves it slowly, RT zooms in and LT out at the crosshair in the middle, which holds the nearest location within a short distance and names it. A opens that location (again: into its card), X marks it found or not found, the D-pad goes to the next location that way, Y opens the types and filters (B goes back to the map), R3 shows the whole map and L3 the next level. Elsewhere the D-pad or the left stick moves between buttons, A presses and the right stick scrolls; LT and RT turn the pages of a guidebook or a guide read in order, or else scroll a page. Everywhere LB and RB switch to the section before or after, B goes back (with nothing left to close: off the map to the sections, or back to the map), Menu opens Settings and View the guide of keys and controller. A bar at the bottom of the screen shows the buttons that matter there; it shows after the controller is used and hides after the mouse, a finger or a key (Settings › Controller: Automatic, Always, Never). Sony controllers get shapes on their buttons, others letters (or as chosen). If Settings › Controller says no controller is detected, Steam Input is sending keys instead: when Atlas is started by Steam, its **Gamepad** template works; otherwise pick a keyboard template, and the keys above do the same. The first time a run sees a controller, a notice says "A controller is connected" and points at the bar and View.

**Not on Linux.** Atlas in the background (the tray icon, the hotkey and starting with the system) is offered on Windows only, so Settings does not show it on Linux. The AppImage registers no file type: opening a pack file from the file manager does not start Atlas, since an AppImage installs nothing and a desktop entry and MIME file would have to be written outside it (Atlas started with a pack file's path still shows it). The Linux desktop tests of `ci.yml` stay switched off; the release workflow's start-up test and the shell's unit tests run instead. Nothing has been tried on a real Steam Deck before trial T3.

## Updates

The plain viewer updates itself on Windows, and on Linux when it runs from an AppImage (`src-tauri/src/updates/`, the web app's `src/state/updates.ts`, `src/library/UpdateSettings.tsx` and `src/components/UpdateNotice.tsx`; see "Updates" in the main README for what the person sees).

**Which copy updates itself** is decided once at the start (`updates::decide`, unit-tested) and given to the web app as `DesktopInfo::updates`: `{ way: "itself", atStart }` or `{ way: "elsewhere", from }`.

- Windows, the app without downloads: updates itself, and looks at its start unless started with `--no-update-check`. A start with `--background` (with Windows, or by another program beside a game) still looks; the notice waits in the window until the person shows it.
- Linux from an AppImage (`APPIMAGE` names an existing file, as for the Steam launch line): updates itself. It does not look at a start with `--background` (on Linux only the Steam launch line gives it, the line another app writes into a game's launch options too, see "Starting Atlas with a game in Steam" in `docs/pack-file-format.md`), with `--no-update-check`, or when the environment says Steam started it or it runs in Game Mode: `SteamGameId` (Steam sets it for what it starts, a non-Steam entry too), `GAMESCOPE_WAYLAND_DISPLAY` (gamescope), or `SteamDeck=1` (a Steam Deck in Game Mode) (`updates::started_by_steam`). **Check for updates** in Settings still works there, so a person can update the AppImage standalone. The launch line is unchanged: no app has to write anything new.
- Linux without an AppImage (a .deb or .rpm someone built): "Updates for this copy of Atlas come from your system's software updates…". The app with downloads, on any system: "…from where you got it". Other systems (macOS): "…from the Atlas releases page". None of these looks or offers the button.
- The Android app: no updater plugin (it is a dependency on Windows and Linux only), no `updates` in `desktop_info`, and the commands answer why not. The web build has no shell and shows nothing.

**The plugin** (`tauri-plugin-updater`, rustls, without its zip support) is compiled in and registered only where Atlas updates itself: `build.rs` sets `cfg(self_update)` on Windows and Linux without the `downloads` feature. It is used from Rust only; no capability grants the page any of its commands. Its settings are in `tauri.conf.json` (`plugins.updater`): the public key that every update must be signed with, the one endpoint, `https://github.com/DrFlGd/Atlas/releases/latest/download/latest.json`, and the Windows installer's passive mode (a small progress window, no questions). Requests send `Atlas/<version>` as their User-Agent, with a 20-second limit to connect and a 60-second limit between parts of an answer.

**The commands** (granted in `capabilities/main.json` to the main window; they take no address): `update_check` looks and keeps the update found; `update_download` downloads that update and checks its signature against the public key, keeping it in memory, with `update_progress` saying how far it is; `update_install` installs it. On Windows the plugin first runs the hook that keeps the window's place and takes the tray icon away (`background::shell::before_update`), then starts the NSIS installer (passive, with the arguments Atlas was started with, so it starts Atlas again) and ends Atlas at once. On Linux the plugin writes the new AppImage over the file `APPIMAGE` names, under the same name and with the same permissions, keeping the old one aside until the new one is written, and Atlas then starts again from it (`AppHandle::request_restart`, which releases the single-instance name first). A folder Atlas cannot write to gives a sentence asking to move the AppImage to a folder of the person's own. The web app saves first what the person changed and Atlas keeps to save a moment later (`state/saveAll.ts`, which **Exit Atlas** uses too).

**The web app.** A few seconds after the start (`START_DELAY_MS`), while `atStart` and the setting **Check for updates when Atlas starts** (kept with the other settings of this device, on unless turned off) allow it, it calls `update_check` quietly: nothing is said when there is no update or the computer is offline, and a version the person skipped is left out. Settings, **Updates**, has the version, **Check for updates** with what it found or why not, and the switch. The notice of an update covers nothing: the version, the release's notes as plain text, **Install now** (with the download's progress, then "Installing…"), **Later** (until the next start) and **Skip this version**. Unit tests: `src/state/updates.test.ts` and `src/components/UpdateNotice.test.tsx`; browser tests against the stand-in shell: `e2e/updates.spec.ts`.

**Making the update files** (`scripts/build.js`). When `TAURI_SIGNING_PRIVATE_KEY` is set, a build of the plain viewer merges `src-tauri/tauri.updater.conf.json` (`createUpdaterArtifacts`), so Tauri signs the NSIS installer and the AppImage and writes a `.sig` beside each. `ATLAS_UPDATER_ARTIFACTS=1` requires them and stops without the key ("Add the repository secret TAURI_SIGNING_PRIVATE_KEY first…"), `0` leaves them out; a build with downloads or its own name never makes them. Without the key nothing changes: local builds and CI build as before.

**The release** (`.github/workflows/release.yml`). A first job stops the release when the secret `TAURI_SIGNING_PRIVATE_KEY` is missing. The Windows job builds and signs the installer, checks it as before, and publishes the release `v<version>` (a normal release, marked latest) with the installer and its `.sig`. The Linux job (`linux-appimage.yml`, signing required) builds, checks and starts the AppImage, at the same time. The last job runs once the Windows release is out: it attaches `Atlas.AppImage` and `Atlas.AppImage.sig` when the Linux job succeeded, then writes `latest.json` (the version, the notes' "New in <version>" part, the date, and for `windows-x86_64` and, when attached, `linux-x86_64` the file's address in the release and the contents of its `.sig`) and attaches it, and warns when the release is not the repository's latest. Drafts and prereleases (the Android app's `android-v*`, the Linux trials) are never the latest, and the Map Maker's releases are published with `--latest=false`, so `/releases/latest/` always leads to the viewer.

Only a real Windows computer and a real AppImage show the install itself; the tests cover the decision, the commands' answers, the web app and the workflow's files.

- IPC: the web app calls only the shell's own commands, each listed in `build.rs` and granted to the main window only. A build without downloads does not have these commands at all. The only plugin permissions granted to the page are listening to the shell's events and stopping (`core:event:allow-listen`, `core:event:allow-unlisten`), for `library-changed`, `pack-file-opened` and, in a build with downloads, `kept-packs-changed`; the page cannot send events. The dialog, opener, single instance and updater plugins are used from Rust only. Folders are chosen in native dialogs, so the page never names a folder to open, and `library_reveal` opens only the maps folder, a listed pack's folder, a remembered location or the activity log's folder. `activity_log_read` returns only the end of the log file, and `import_report` only writes the outcome of adding a map (importer id, counts, a short message), the figures of a run of several, of a list read from a game page or a list of games (counts by kind), or of an update, and the sites of its pages, to it. `import_open` takes an optional `purpose` (`game` or `catalogue`), used only for the log's wording, and an optional `keep`, which keeps the window for the next pages of a go on the same site; `import_navigate` moves only such a kept window, and only to a page of its own site. The web app finds the shell through `window.__TAURI_INTERNALS__` and has no Tauri dependency, so the plain web build runs without it.
- Files: `save_text_file` and `open_text_file` go through the native save and open dialogs ("Export progress", "Import progress"), and `trial_report_save` through its own save dialog ("Save the 3D trial report", a `.txt` text file), so the page never names a path; opened files are limited to 64 MB of UTF-8 text. `packfile_export` and `packfile_pick` go through native dialogs too ("Export pack file", and "Import pack file" or, in the desktop app without downloads, "Add pack file"). `packfile_inspect` and `packfile_import` take a path, but open only an existing file whose name ends in `.atlaspack`, check it as described under "Map pack files" and write only into the maps folder (in the desktop app without downloads, only a new file in the packs folder, through a `.part` file).
- Game saves: the save commands read only `.sav` files in folders the person chose in a native dialog (or the game's own saves folder under Documents) and files chosen the same way, never through a link, at most 64 MB, and never write anything there (see [Game saves](#game-saves)).
- Game files: the game file commands read only in the game folder the person chose in a native dialog, after checking it is the game's: bundle tables of contents, and the map files listed by the last scan, by index, so the page never names a path; never through a link, with size limits, and never writing anything there (see [The game's own map locations](#the-games-own-map-locations)).
- Content Security Policy (in `tauri.conf.json`): scripts, styles and fonts only from the app; images from the app, `data:`, `blob:` (PMTiles tiles, a CBZ guidebook's pages) and the pack protocol; network requests only to the app and the pack protocol. pdf.js and its worker are scripts of the app's own and need no other rule. Map images are downloaded by the Rust shell, not the page, and only in a build with downloads. Updates are looked for and downloaded by the Rust shell too, so the policy needs no rule for them.
- The import window (see below) gets no commands, no pack protocol and no way to reach the app.
- The map page window (only in a build with downloads) gets the same: no commands, no pack protocol, no way to reach the app. The main window's commands for it are `view_pages`, `view_open`, `view_status`, `view_stop_saving`, `view_close` and `view_open_in_browser`, listed in `build.rs` and granted in `capabilities/downloads/main-downloads.json` like the download commands; `view_open` and `view_open_in_browser` open only addresses recorded in the pack's manifest.
- Links: navigation is limited to the app's own pages. `http` and `https` links to other sites, including guide links with `target="_blank"` and links in a guidebook's PDF, open in the system browser (`open_external`); any other scheme is ignored.
- Guidebooks: a picked PDF or CBZ is served only at a one-time address of the pack protocol (`_picked/<token>/`) until it is added or forgotten; pdf.js runs a PDF's script never, and every file read from a guidebook is bounded (see "Guidebooks").

The bundle identifier is `dev.atlas.desktop` (Tauri warns about identifiers ending in `.app` because of the macOS bundle extension). Change it before the first public release if you prefer another; installed apps keep their data under it.
